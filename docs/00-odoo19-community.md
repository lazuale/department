Этот документ фиксирует техническую границу методики.

Методика рассчитана на **стандартный Odoo 19 Community** и использует только то, что можно настроить штатным интерфейсом без собственного модуля, Odoo Studio и обязательных сторонних дополнений.

Если правило нельзя устойчиво реализовать в этой границе, оно не должно становиться обязательной частью базовой модели.

## 1. Что используется как основа

### Проекты и задачи

Штатный модуль `Проекты` используется как единый рабочий контур:

- проект;
- задача;
- этапы Kanban;
- фиксированные статусы задачи;
- исполнитель;
- приоритет;
- срок;
- теги;
- описание;
- вложения и обсуждение;
- активности;
- подзадачи;
- зависимости;
- повторяющиеся задачи;
- вехи — когда они действительно нужны.

Официальная документация: [Project](https://www.odoo.com/documentation/19.0/applications/services/project.html).

### Этапы и статусы — разные вещи

Этапы проекта настраиваются пользователем и отражают рабочий поток. Статусы задачи фиксированы в Odoo и не настраиваются.

В базовой модели:

- **этап** отвечает на вопрос «где находится работа в нашем потоке»;
- **статус** отвечает на вопрос «задача открыта, ожидает внутреннюю зависимость, согласована, требует изменений, завершена или отменена».

Нельзя проектировать методику так, будто этап и статус — одно и то же.

Официальная документация: [Task stages and statuses](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_stages_statuses.html).

### Свойства задач

Штатные `Properties` позволяют кликами добавлять проектно-зависимые свойства задач через `Действия → Изменить свойства`.

Они подходят для небольшого набора устойчивых аналитических признаков, например:

- `Вид работы`;
- `Процесс`;
- при необходимости — отдельный справочный признак конкретного рабочего контура.

Свойства не следует превращать в копию большой анкеты.

Официальная документация: [Property fields](https://www.odoo.com/documentation/19.0/applications/essentials/property_fields.html).

### Активности

Активность — следующее конкретное действие с собственной датой: проверить ответ, напомнить, позвонить, провести контроль.

**Срок задачи не используется как дата напоминания.** Для напоминаний и follow-up используются активности.

Официальная документация: [Activities](https://www.odoo.com/documentation/19.0/applications/essentials/activities.html).

### Внутренние зависимости

Зависимость `Blocked by` используется, когда продолжение одной задачи реально невозможно до завершения другой задачи Odoo.

Odoo сам переводит зависимую задачу в системный статус `Waiting` до закрытия блокирующих задач.

Официальная документация: [Task dependencies](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_dependencies.html).

### Периодическая работа

Для регулярной работы используется штатная рекуррентность. Следующая задача создаётся после закрытия предыдущей как `Done` или `Canceled`.

Методика **не требует заранее создавать цепочку будущих карточек на горизонт**, потому что штатная рекуррентность Odoo работает иначе.

Официальная документация: [Recurring tasks](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/recurring_tasks.html).

### Аналитика

Базовый контур аналитики строится на штатных возможностях:

- поиск и фильтры;
- группировки;
- сохранённые `Favorites`;
- Kanban и List для оперативной работы;
- Pivot и Graph для анализа;
- стандартный анализ задач;
- при необходимости — штатные Dashboards/Spreadsheet Dashboard после стабилизации показателей.

Официальная документация: [Search, filter, group records](https://www.odoo.com/documentation/19.0/applications/essentials/search.html), [Dashboards](https://www.odoo.com/documentation/19.0/applications/productivity/dashboards.html).

## 2. Что доступно, но не является обязательной основой

### Подзадачи

Используются только когда часть общего результата имеет самостоятельного исполнителя, срок или результат.

### Вехи

Используются для ограниченных по сроку инициатив и проектов с несколькими задачами. Для обычной операционной очереди они не нужны.

### Учёт времени

`Timesheets` может использоваться, если действительно нужно понимать трудоёмкость, стоимость или загрузку. Он не является обязательным условием управления задачами и не используется для рейтинга сотрудников.

### Email alias

Для выбранного проекта можно настроить создание задач из входящих писем. Это полезно только если почтовый канал организован и не создаёт бесконтрольные дубли.

Официальная документация: [Task creation](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_creation.html).

## 3. На чём базовая методика не строится

### Не используется «тип задачи» как отдельная системная сущность

В стандартном `Project` нет требуемых методикой типов `Работа`, `Запрос`, `Идея` с отдельными жизненными циклами.

Если различение нужно для аналитики, используется свойство `Вид работы` в одной и той же модели задачи.

### Не используется «групповой исполнитель»

Штатный исполнитель задачи — пользователь или пользователи, а не рабочая группа как отдельный получатель обязательства.

Общая очередь реализуется **неназначенными задачами** в этапах `Входящие`/`Очередь` и сохранённым фильтром `Без исполнителя`.

После фактического взятия работы у задачи должен быть один ответственный за результат. Дополнительных участников отражают подписчики, активности, комментарии или подзадачи — по смыслу работы.

### Не используется ручной статус `Ожидание` для всех случаев

Системный `Waiting` занят внутренними зависимостями Odoo.

Внешнее ожидание отражается отдельным этапом `Ожидание внешнего` и активностью следующего контроля.

### Не используется отдельный этап `Готово` как единственный способ закрытия

Завершение и отмена фиксируются системными статусами `Done` и `Canceled`, потому что именно они закрывают задачу.

### Не используется ручное создание будущих периодов

Для штатной периодики применяется рекуррентность Odoo.

### Не используется матрица разрешённых переходов по ролям

Базовая методика не предполагает, что стандартный Project будет no-code BPM-движком с отдельным правом на каждый переход этапа.

Роли определяют ответственность и управленческие решения, но не имитируют технические ограничения, которых нет в базовой настройке.

### Не используются обязательные Enterprise-функции как фундамент

Базовый контур не зависит от Studio, Planning, Approvals, Helpdesk, Knowledge, Documents, Gantt и других возможностей, которые не являются частью стандартного ядра Odoo 19 Community.

При появлении такой потребности она рассматривается отдельно: нужен ли собственный модуль, стороннее дополнение или вообще другой способ организации процесса.

## 4. Технический принцип методики

Любое новое правило проходит проверку:

1. Нужно ли оно для управленческого решения?
2. Есть ли для него штатная сущность Odoo?
3. Можно ли настроить и поддерживать её кликами без скрытой ручной бюрократии?
4. Можно ли затем увидеть результат в фильтрах или аналитике?
5. Если нет — правило не включается в базовый контур автоматически.

Это важнее попытки буквально перенести прежнюю терминологию в Odoo.
