Этот документ фиксирует техническую границу методики.

Методика рассчитана на **стандартный Odoo 19 Community** и использует только возможности, которые присутствуют в публичной ветке `odoo/odoo:19.0` и могут быть настроены штатным интерфейсом без собственного модуля, Odoo Studio и обязательных сторонних дополнений.

Официальная документация Odoo описывает продукт в целом и местами показывает функции Enterprise. Поэтому для спорных возможностей граница Community дополнительно проверяется по публичному исходному коду Odoo 19.

## 1. Принцип отбора функций

Наличие функции в Odoo ещё не означает, что её нужно включать в методику.

Каждая возможность получает один из статусов:

- **База** — используется в основном рабочем контуре;
- **По потребности** — включается, когда есть конкретная управленческая задача;
- **После стабилизации** — полезна, но только поверх уже достоверных данных;
- **Не фундамент** — технически доступна, но базовая методика от неё не зависит;
- **За границей CE** — не используется как обязательное условие Community-контура.

## 3. Проекты и задачи

Штатный модуль `Проекты` — основной рабочий инструмент.

Базовые сущности:

- проект;
- задача;
- этап;
- системный статус;
- исполнитель;
- приоритет;
- Deadline;
- Properties;
- Tags;
- Chatter;
- Activities;
- подзадачи;
- зависимости;
- рекуррентность.

Официальная документация: [Project](https://www.odoo.com/documentation/19.0/applications/services/project.html).

## 4. Этап и статус — разные измерения

Этапы задач настраиваются пользователем и отображают рабочий поток. Odoo не задаёт обязательный набор этапов проекта.

Системные статусы задачи фиксированы:

- `In Progress`;
- `Changes Requested`;
- `Approved`;
- `Waiting`;
- `Done`;
- `Canceled`.

В методике:

- **этап** отвечает на вопрос «где находится работа в нашем потоке»;
- **статус** отвечает на системное состояние задачи.

`Done` и `Canceled` закрывают задачу. `Waiting` используется Odoo для внутренней зависимости.

Официальная документация: [Task stages and statuses](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_stages_statuses.html).

## 5. Properties вместо преждевременной разработки полей

`Properties` позволяют добавлять проектно-зависимые поля задач через интерфейс.

В базовом контуре достаточно:

- `Вид работы`;
- `Процесс` — если разрез действительно нужен в управлении и аналитике.

Дополнительные Properties появляются только после подтверждённой потребности.

Properties не должны превращаться в копию Excel-реестра или заменять полноценную связанную модель, если требуется большой постоянно меняющийся справочник.

Официальная документация: [Property fields](https://www.odoo.com/documentation/19.0/applications/essentials/property_fields.html).

## 6. Activities и Activity Plans

### Activity

Activity = одно следующее действие с датой и ответственным:

- проверить ответ;
- напомнить;
- позвонить;
- провести проверку;
- сделать follow-up.

Deadline задачи не используется как дата напоминания.

### Activity Plan

Activity Plan = заранее настроенная последовательность нескольких Activities, которую можно применить к задаче в несколько кликов.

Использовать, если один и тот же **набор контрольных действий** устойчиво повторяется вокруг одного результата.

Пример:

```text
Проверить получение → напомнить → эскалировать
```

Не использовать Activity Plan вместо нескольких самостоятельных результатов. Если шаг имеет собственный результат, срок и ответственного — это задача или подзадача.

Официальная документация по Activities: [Activities](https://www.odoo.com/documentation/19.0/applications/essentials/activities.html).

## 7. Внутренние зависимости

`Blocked by` используется только когда продолжение задачи действительно невозможно до результата другой задачи Odoo.

Odoo устанавливает зависимой задаче системный `Waiting` и не позволяет перевести её в `In Progress`, пока блокирующая задача не будет `Approved`, `Canceled` или `Done`.

Это не заменяет внешнее ожидание.

Официальная документация: [Task dependencies](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_dependencies.html).

## 8. Периодическая задача

Для повторяющегося результата используется `Recurring Tasks`.

Следующий экземпляр создаётся после `Done` или `Canceled` предыдущего и попадает в первый этап проекта.

Odoo копирует основные сведения задачи, но не копирует Activities, Chatter, Milestones, Timesheets и Subtasks.

Поэтому методика не требует вручную создавать будущее периодики на несколько месяцев вперёд.

Официальная документация: [Recurring tasks](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/recurring_tasks.html).

## 9. Rotting — штатный сигнал залежавшейся задачи

У этапа задачи есть `Days to rot` — количество дней без смены этапа, после которого задача считается залежавшейся (`Rotting`). Odoo имеет штатный фильтр и визуальный признак таких задач.

Это полезный **сигнал застоя**, но не новый SLA:

- Rotting измеряет отсутствие смены этапа;
- Deadline измеряет конечный срок результата;
- Activity измеряет срок следующего действия.

Не смешивать эти три даты.

Порог Rotting задаётся отдельно для конкретного этапа и не вводится «на всякий случай» без понимания нормального времени нахождения задачи на этом этапе.

## 10. Личное To-Do не равно общей рабочей очереди

`To-Do` подходит для:

- личной фиксации мысли;
- личного напоминания;
- наблюдения до решения о постановке общей работы.

To-Do можно штатно преобразовать в Project Task.

После того как результат стал обязательным для отдела, он должен быть переведён в задачу общего проекта, а не оставаться только в личной доске.

Personal Stages остаются личным способом организации и не определяют общий этап задачи.

Официальная документация: [To-do](https://www.odoo.com/documentation/19.0/applications/productivity/to_do.html).

## 11. Повторяемая задача и повторяемый проект — не одно и то же

### Recurring Task

Используется, когда периодически повторяется **один результат**.

### Project Template

Используется, когда повторяется **целая структурированная инициатива**:

- несколько задач;
- подзадачи;
- этапы;
- роли;
- зависимости;
- контрольные точки.

Шаблон переносит структуру проекта, а Project Roles позволяют при создании нового проекта сопоставить роли с конкретными сотрудниками и автоматически назначить соответствующие задачи.

Официальная документация: [Project templates](https://www.odoo.com/documentation/19.0/applications/services/project/project_management/project_templates.html).

## 12. Milestones и Project Updates — для инициатив, не для операционной очереди

### Milestones

Веха = значимая контрольная точка проекта с Deadline. Когда все связанные задачи закрыты как `Done` или `Canceled`, Odoo может отметить веху достигнутой.

Для ежедневной операционной очереди вехи не нужны.

### Project Updates

Для самостоятельных проектов Odoo позволяет создавать периодические снимки состояния:

- `On Track`;
- `At Risk`;
- `Off Track`;
- `On Hold`;
- `Done`;
- процент Progress;
- дата, автор и описание.

Это нормальный штатный способ управленческого обзора отдельной инициативы. Не нужно создавать для него кастомный «отчёт по проекту».

Официальная документация: [Project dashboard](https://www.odoo.com/documentation/19.0/applications/services/project/project_management/project_dashboard.html), [Project milestones](https://www.odoo.com/documentation/19.0/applications/services/project/project_management/project_milestones.html).

## 13. Аналитика

Базовый путь:

1. поиск и фильтры;
2. группировки;
3. сохранённые `Favorites`;
4. List/Kanban для оперативного контроля;
5. Pivot/Graph и Task Analysis для периодического анализа;
6. только затем Dashboard.

Стандартное Community-действие задач включает `kanban`, `list`, `form`, `calendar`, `pivot`, `graph`, `activity`. Gantt не используется как обязательный вид Community-методики.

Spreadsheet Dashboard допустим после стабилизации состава показателей.

Официальная документация: [Search, filter, group records](https://www.odoo.com/documentation/19.0/applications/essentials/search.html), [Dashboards](https://www.odoo.com/documentation/19.0/applications/productivity/dashboards.html).

## 14. Automation Rules существуют в Community, но не являются первым шагом

В публичной ветке Odoo 19 есть модуль `base_automation` (`Automation Rules`). Через UI он поддерживает правила, реагирующие на создание, изменение, установку этапа/статуса/приоритета, время и другие события, с последующим запуском действий.

Это значит, что после стабилизации процесса можно накликать точечную автоматизацию.

Но базовая методика **не строится на автоматизации с первого дня**.

Правильный порядок:

1. сначала стабилизировать задачу, этапы, Deadline, Properties и Activities;
2. увидеть повторяющееся ручное действие;
3. доказать, что оно однозначно;
4. только потом автоматизировать его;
5. проверить, что автоматизация не скрывает исключения и не создаёт ложные данные.

Не использовать Automation Rules для имитации сложного BPM, если процесс на самом деле требует отдельной модели, прав или разработки.

## 15. Email alias и автоматические письма по этапу

Проект может создавать задачи из входящей почты через alias.

Этап задачи также может иметь почтовый шаблон для автоматической отправки сообщения при переходе в этап.

Обе возможности полезны для внешнего потока, но могут породить:

- дубли;
- информационные задачи без обязательства;
- лишние автоматические письма.

Поэтому они включаются после определения правил входящего и дедупликации.

Официальная документация: [Task creation](https://www.odoo.com/documentation/19.0/applications/services/project/tasks/task_creation.html).

## 16. Customer Rating

Штатный этап задачи может запускать запрос внешней оценки качества.

Использовать только если реально существует внешний получатель результата и полезна оценка сервиса.

Не использовать Customer Rating как скрытый рейтинг сотрудников подразделения.

## 17. Timesheets

Учёт времени включается только при конкретной задаче управления:

- оценка трудоёмкости;
- стоимость;
- загрузка мощности;
- план/факт трудозатрат.

Не заставлять сотрудников списывать время только потому, что Odoo это умеет.

## 18. На чём базовая методика не строится

### Не используется «тип задачи» как отдельная системная сущность

`Работа`, `Запрос`, `Улучшение` — значения Property `Вид работы`, а не новые модели и не отдельные жизненные циклы.

### Не используется «групповой исполнитель»

Общая очередь = неназначенные задачи. После взятия методика требует одного ответственного за конечный результат.

### Не используется один ручной `Ожидание` для всех причин

- внешняя зависимость → этап `Ожидание внешнего` + Activity;
- внутренняя зависимость → `Blocked by` + системный `Waiting`.

### Не создаётся отдельный этап `Готово` как обязательный способ закрытия

Закрытие задачи выполняется системными `Done` и `Canceled`.

### Не создаётся будущее периодики вручную

Для одного повторяющегося результата используется Recurring Task.

### Не используется матрица переходов как якобы штатный BPM

Роли определяют ответственность и решения, но базовый Project не изображается как сложный no-code workflow engine.

### Не используется Gantt как обязательная функция Community

Официальная документация Odoo может показывать Gantt в примерах Project, но стандартное действие задач публичного Community-модуля не содержит Gantt. Методика должна работать без него.

### Не используются Enterprise-приложения как скрытая зависимость

Базовый контур не требует Studio, Planning, Approvals, Helpdesk, Knowledge, Documents и других Enterprise-возможностей.

## 19. Два режима, которые методика должна различать

### Операционный контур

Для постоянного потока работы:

```text
Один основной проект
→ задачи
→ этапы
→ Deadline / Priority / Properties
→ Activities / Dependencies
→ сохранённые фильтры
→ Task Analysis
```

### Проектная инициатива

Для ограниченного изменения с несколькими результатами:

```text
Отдельный проект
→ при повторяемости Project Template + Roles
→ задачи / подзадачи / зависимости
→ Milestones
→ Project Updates
→ Dashboard / Burndown
```

Не смешивать эти режимы. Операционную очередь не нужно превращать в набор микропроектов, а большую инициативу — в одну бесконечную задачу.

## 20. Технический принцип методики

Любое новое правило проходит проверку:

1. Какую реальную потерю или ошибку предотвращает?
2. Есть ли для него штатная сущность Odoo?
3. Можно ли настроить и поддерживать её кликами?
4. Кто поддерживает данные?
5. Где это видно при контроле?
6. Какое решение принимается по этому признаку?
7. Нужна ли вообще автоматизация или достаточно штатной дисциплины?

Если ответа нет — правило не включается в базовый контур.
