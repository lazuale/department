# Методика управления работой

## 1. Область применения

Методика применяется ко всей обязательной и планируемой работе подразделения независимо от источника её возникновения.

Источниками работы могут быть:

- входящее основание, письмо, документ или обращение;
- самостоятельно инициированный запрос;
- наступление срока регламентной операции;
- поручение руководства;
- проектная деятельность;
- решение по реализации улучшения.

Методика не описывает предметную технологию конкретной функции. Она устанавливает единый способ **фиксировать, исполнять, контролировать и улучшать работу**.

## 2. Базовые принципы

### 2.1. Работа должна быть наблюдаемой

Любое обязательное действие после разбора источника должно существовать в рабочей системе.

Недопустимо считать почту, чат, личные заметки или устную договорённость достаточной фиксацией обязательной работы.

### 2.2. Одна запись — один контролируемый результат

Одна Work Package соответствует одному результату, который можно независимо:

- назначить исполнителю;
- ограничить сроком;
- поставить на ожидание;
- завершить;
- отменить;
- вернуть в работу.

Не создаются отдельные Work Package на каждое письмо, вложение, звонок, строку данных или технический шаг.

Если одно основание порождает несколько независимо управляемых результатов, создаются несколько связанных Work Package.

### 2.3. Состояние должно отражать факт, а не намерение

Статус показывает реальное состояние результата.

- `Очередь` — работа существует, но прямо сейчас не исполняется.
- `В работе` — исполнитель фактически выполняет её сейчас.
- `Ожидание` — выполнение заблокировано внешним условием.
- `Готово` — результат достигнут.
- `Отменено` — результат больше не требуется.

### 2.4. Руководство управляет исключениями

Нормальный поток не требует ручного согласования каждой работы.

Руководитель концентрируется на:

- просроченных работах;
- старых работах в очереди;
- длительном ожидании;
- работах без владельца;
- критичных работах;
- перегрузе потока;
- возвратах после завершения;
- повторяющихся системных проблемах.

### 2.5. Контроль качества не должен тормозить поток

Обычная работа закрывается исполнителем самостоятельно.

Качество контролируется двумя способами:

- целевой риск-контроль;
- выборочный контроль завершённых работ.

При обнаружении ошибки первоначальная работа возвращается в `В работе`.

### 2.6. Идеи не являются обязательствами

Идеи, улучшения и предложения по автоматизации ведутся отдельно от обязательной работы.

Backlog развития является набором вариантов изменений, а не второй очередью исполнения.

## 3. Контуры управления

### 3.1. Операционный контур

Содержит входящие обязательные работы и самостоятельные исходящие запросы.

### 3.2. Регламентный контур

Содержит работы, которые возникают по календарю или установленной периодичности.

Каждый период создаёт отдельный экземпляр работы.

### 3.3. Поручения и проекты

Разовое поручение по умолчанию является одной Work Package.

Если результат состоит из нескольких независимо управляемых частей, используется иерархия Work Package.

Отдельный Project создаётся только если одновременно присутствуют несколько признаков:

- несколько самостоятельных результатов;
- несколько исполнителей или рабочих направлений;
- этапность;
- зависимости;
- значительная продолжительность;
- необходимость отдельного управленческого контура.

### 3.4. Развитие и автоматизация

Сюда попадают:

- идеи;
- повторяющиеся проблемы;
- предложения по изменению процесса;
- кандидаты на автоматизацию;
- инициативы по снижению ручной нагрузки.

## 4. Классификация

### 4.1. Type

Минимальный набор типов:

- `Работа` — обязательный результат;
- `Запрос` — самостоятельный исходящий запрос, который необходимо отдельно контролировать;
- `Идея` — необязательная инициатива развития.

Дополнительный Type создаётся только если объект имеет принципиально другой жизненный цикл.

### 4.2. Category

Category отвечает только на вопрос: **какой устойчивый бизнес-процесс породил работу**.

Категории не используются для кодирования:

- срочности;
- источника;
- статуса;
- подразделения;
- конкретного документа;
- временной кампании.

Список Category является контролируемым справочником и меняется редко.

## 5. Приоритет

Используются три уровня:

- `Обычный`;
- `Высокий`;
- `Критичный`.

`Критичный` применяется только если задержка создаёт непосредственное существенное последствие и требует изменения текущего порядка исполнения.

Приоритет не заменяет срок.

## 6. Порядок выбора работы

Исполнитель берёт работу из очереди в следующем порядке:

1. критичные работы;
2. работы с ближайшим сроком;
3. наиболее старые работы;
4. остальные работы.

Допускается отклонение от порядка только при явной производственной необходимости.

Pull-модель не означает свободный выбор удобных работ.

## 7. WIP-дисциплина

Статус `В работе` используется только для реально активной работы.

Назначенная, но не начатая работа остаётся в `Очередь`.

Для каждого рабочего направления устанавливается локальный ориентир максимального одновременного WIP. Значение лимита определяется по фактической эксплуатации и может различаться для разных процессов.

Цель WIP-ограничения — не запрет, а сохранение достоверности состояния потока.

## 8. Сроки

Каждая обязательная работа должна иметь Finish date.

Если внешний срок отсутствует, срок устанавливается по внутреннему нормативу соответствующего процесса.

Finish date означает дату требуемого конечного результата и не используется как дата следующего напоминания, звонка или проверки ответа.

Изменение срока допускается только при изменении фактических условий и должно быть объяснимо из Activity.

## 9. Definition of Done

Для каждой устойчивой Category устанавливается одно краткое определение готовности.

Definition of Done должен отвечать на вопрос: **какой результат позволяет закрыть работу без дальнейших обязательных действий**.

Definition of Done не превращается в многошаговый чек-лист для каждой карточки, если это не требуется технологией процесса.

## 10. Изменение методики

Новая сущность, статус, категория, поле, роль или обязательное действие добавляются только если устраняют конкретный управленческий риск.

Изменение считается обоснованным, если оно:

- предотвращает потерю работы;
- повышает достоверность состояния;
- сокращает ручную операцию;
- улучшает контроль срока или владельца;
- делает управленческую метрику однозначнее.

Принцип по умолчанию: **не усложнять поток без доказанной необходимости**.
