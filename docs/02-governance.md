# Роли, ответственность и управленческий ритм

## 1. Назначение

Документ определяет роли в системе управления работой. Названия ролей функциональные и не привязаны к штатным должностям.

Один сотрудник может совмещать несколько ролей, если это не разрушает контроль.

## 2. Роли

### 2.1. Исполнитель

Отвечает за фактическое выполнение назначенной или взятой работы.

Обязан:

- переводить работу в `В работе` только после фактического начала;
- своевременно переводить заблокированную работу в `Ожидание`;
- сохранять комментарий с причиной ожидания;
- поддерживать Finish date в актуальном состоянии;
- закрывать работу после достижения Definition of Done;
- перед окончанием смены приводить активные работы к фактическому состоянию.

Не обязан:

- получать отдельное разрешение старшего на обычное закрытие;
- создавать отдельные карточки на каждый технический шаг;
- вести параллельный ручной реестр уже зарегистрированных работ.

### 2.2. Координатор входящего потока

Отвечает за полноту разбора входящей рабочей информации в установленный период.

Функция координатора — определить судьбу входа, а не выполнять каждую работу.

Каждый потенциально рабочий вход должен закончить разбор одним из трёх исходов:

1. создана новая Work Package;
2. информация добавлена в существующую Work Package;
3. установлено, что действий не требуется.

Недопустим четвёртый исход: `оставлено на потом без фиксации`.

### 2.3. Владелец процесса

Отвечает за правила конкретного устойчивого бизнес-процесса.

Определяет:

- Definition of Done;
- Category;
- внутренний норматив срока при отсутствии внешнего;
- допустимый размер пакета работы;
- критерии разбиения крупной работы;
- признаки типовых ошибок;
- кандидатов на автоматизацию.

Не контролирует вручную каждую обычную работу.

### 2.4. Руководитель потока

Отвечает за управляемость общей очереди и исключения.

Фокус:

- просрочка;
- старение очереди;
- длительное ожидание;
- отсутствие владельца;
- перекос нагрузки;
- критичные работы;
- повторные открытия;
- системные причины задержек.

Руководитель не используется как обязательная стадия согласования обычной работы.

### 2.5. Контролёр качества

Выполняет выборочный или целевой просмотр завершённых работ.

Роль может выполняться руководителем потока, владельцем процесса или назначенным сотрудником.

Контроль качества не является стадией обычного workflow.

### 2.6. Администратор рабочего контура

Отвечает за техническую консистентность настроек:

- статусы;
- типы;
- категории;
- роли и права;
- представления;
- доски;
- проекты;
- шаблоны.

Не изменяет методику по собственной инициативе без зафиксированного управленческого основания.

## 3. Матрица ответственности

| Действие | Исполнитель | Координатор входа | Владелец процесса | Руководитель потока | Контролёр качества |
|---|---:|---:|---:|---:|---:|
| Разобрать входящий канал |  | **R** |  | A |  |
| Создать обычную работу | R | **R** |  | A |  |
| Выбрать работу из очереди | **R** |  |  | A |  |
| Выполнить работу | **R** |  |  | A |  |
| Перевести в ожидание | **R** |  |  |  |  |
| Закрыть обычную работу | **R** |  |  |  |  |
| Определить DoD процесса |  |  | **R/A** |  |  |
| Разобрать просрочку и перегруз |  |  | C | **R/A** |  |
| Выполнить выборочный контроль |  |  | C | A | **R** |
| Изменить методику |  |  | R | **A** | C |

`R` — выполняет, `A` — несёт итоговую ответственность, `C` — участвует в разборе.

## 4. Передача между сменами или рабочими периодами

Передача не является отдельным реестром всей работы.

Перед окончанием периода каждая активная Work Package приводится к фактическому состоянию:

| Факт | Состояние в системе |
|---|---|
| Следующий исполнитель продолжает сразу | `В работе`, Assignee меняется |
| Работа будет продолжена позже | `Очередь` |
| Работа заблокирована внешним условием | `Ожидание` |
| Результат достигнут | `Готово` |

Отдельно передаётся только контекст, который невозможно однозначно понять из Work Package.

## 5. Управленческий ритм

### 5.1. На каждом рабочем периоде

Проверяется:

- полнота разбора входа;
- отсутствие бесхозных критичных работ;
- фактическое состояние `В работе`;
- корректность передачи активных работ.

### 5.2. Ежедневный обзор исключений

Просматриваются только:

- просроченные;
- критичные;
- старые в очереди;
- длительно ожидающие;
- без исполнителя;
- очевидный перегруз WIP.

Нормальный поток не обсуждается поштучно.

### 5.3. Еженедельный обзор потока

Разбираются:

- входящий объём;
- завершённый объём;
- изменение остатка;
- старение очереди;
- основные причины ожиданий;
- повторные открытия;
- дубли;
- проблемы классификации;
- кандидаты в backlog улучшений.

### 5.4. Ежемесячный обзор улучшений

Рассматриваются:

- устойчивые узкие места;
- повторяющиеся ручные операции;
- идеи из backlog;
- эффект уже внедрённых изменений;
- необходимость корректировки нормативов сроков и WIP.

## 6. Правило эскалации

Эскалация требуется, если исполнитель не может восстановить нормальный поток своими действиями.

Основания:

- срок находится под угрозой;
- внешняя зависимость не разрешается в разумный срок;
- конфликт приоритетов;
- недостаточно ресурсов;
- отсутствует решение по неоднозначному результату;
- проблема повторяется и выходит за рамки единичной Work Package.

Эскалация не создаёт отдельную стадию workflow. Решение фиксируется в Activity или отдельной связанной работе, если возник новый самостоятельно контролируемый результат.
