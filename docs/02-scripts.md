Сценарии показывают, как использовать штатные механизмы Odoo 19 Community. Они не задают конкретную оргструктуру и не предполагают заранее, кто назначает, проверяет или закрывает работу.

## PS-01. Появилась новая работа

1. Определить предмет: сотрудник, ТС, оборудование, документ, организация или другое.
2. Проверить, есть ли подходящая предметная запись в Odoo.
3. Определить, существует ли отдельный контролируемый результат.
4. Если самостоятельного результата нет — обновить предметную запись, Chatter или другой профильный объект.
5. Если Task на тот же результат уже есть — продолжить её.
6. Если отдельного результата ещё нет — создать Task.
7. Указать только те поля и Properties, которые реально нужны процессу.

## PS-02. Task готова к выполнению

Процесс определяет:

- нужен ли Assignee сразу;
- допустима ли неназначенная общая очередь;
- какой Stage означает готовность к работе;
- нужен ли Deadline при регистрации.

Odoo допускает как заранее назначенные, так и неназначенные Tasks.

## PS-03. Работа началась

При фактическом начале:

- назначить или уточнить Assignees по правилам процесса;
- перевести Task в рабочий Stage;
- проверить Deadline и предметные Properties;
- при необходимости создать Activity на ближайшее действие.

Конкретное название рабочего Stage определяется процессом.

## PS-04. Нужен внешний ответ или событие

Если продолжение зависит от внешнего события:

1. зафиксировать, чего именно ждём;
2. при необходимости использовать отдельный Stage ожидания;
3. при необходимости создать Activity на follow-up;
4. не создавать искусственную внутреннюю dependency, если блокирующей Task нет.

Способ фиксации ожидания может отличаться по процессам.

## PS-05. Ждём другую Task

Если продолжение действительно зависит от результата другой Task:

```text
Blocked by = predecessor Task
```

Odoo вычисляет `Waiting` автоматически.

Predecessor может находиться в другом Project.

## PS-06. Нужен отдельный контролируемый запрос

Если получение документа, подтверждения или материала само является отдельным результатом, создать отдельную Task или Subtask.

Если это обычный follow-up внутри существующей работы, достаточно Activity / Chatter.

Не вводить отдельный тип `Запрос` только потому, что такая категория когда-то использовалась в другой системе.

## PS-07. Изменился срок

Deadline отражает срок результата.

Если срок изменился:

- обновить его, если это соответствует фактическому правилу процесса;
- при необходимости зафиксировать основание в Chatter;
- не использовать Deadline как дату следующего звонка или напоминания.

Кто имеет право менять Deadline и требуется ли согласование — локальное правило процесса.

## PS-08. Передать Task другому исполнителю

Если меняется Assignee:

- обновить Assignees;
- привести Stage к фактическому состоянию работы;
- сохранить значимый контекст в Chatter или Description;
- не создавать новую Task только из-за смены исполнителя, если результат остаётся тем же.

## PS-09. Нужна независимая проверка

Если конкретный процесс требует отдельной приёмки результата, можно использовать:

- отдельный Stage проверки;
- Activity проверяющему;
- `Approved` / `Changes Requested` там, где это соответствует процессу.

Если независимая проверка не нужна, не добавлять её в общий workflow.

## PS-10. Ошибка обнаружена после завершения

Если исходный результат оказался неправильным:

- переоткрыть ту же Task, если процесс это допускает;
- вернуть её в рабочее состояние;
- зафиксировать причину;
- исправить результат.

Если исходный результат был корректным, а позже появился новый самостоятельный объём — создать новую Task.

## PS-11. Дубликат

Если две Tasks описывают один и тот же контролируемый результат:

1. выбрать основную;
2. перенести уникальный контекст;
3. вторую закрыть или отменить способом, принятым в процессе;
4. при необходимости оставить ссылку на основную.

Не удалять историю только ради чистого списка, если она нужна для контроля.

## PS-12. Работа больше не требуется

Использовать `Canceled`, если результат больше не нужен.

Если причина важна для последующего разбора, зафиксировать её в Chatter.

Кто может отменять Task — локальное правило процесса.

## PS-13. Task относится к ТС

Если Fleet подходит как master data:

```text
Property: ТС
Type: Many2one
Model: fleet.vehicle
```

Выбирать существующий Vehicle и не копировать вручную его атрибуты в текстовые Properties без необходимости.

## PS-14. Task относится к сотруднику

Не смешивать:

```text
Assignees = кто выполняет Task = res.users
Property[Сотрудник] = кого касается работа = res.partner
```

Сотрудник как предмет работы не обязан быть пользователем Odoo. Если ему позже выдаётся доступ, используется тот же `res.partner`, связанный с его `res.users`.

Подробно: [17 — Master data: люди](17-master-data-people.md).

## PS-15. Task относится к оборудованию

Если нужен отдельный управленческий результат по Equipment:

```text
Property: Оборудование
Type: Many2one
Model: maintenance.equipment
```

Если событие полностью закрывается Maintenance Request, не создавать параллельную Project Task без отдельной причины.

## PS-16. Один результат касается нескольких объектов

Если результат действительно один, допустима Many2many Property.

Если по объектам различаются сроки, исполнители или результаты — чаще правильнее несколько Tasks/Subtasks.

## PS-17. Появилась типовая разовая работа

Если один и тот же сценарий возникает по событию:

```text
Task Template
```

Шаблон хранит только устойчивую структуру и не должен содержать меняющиеся предметные значения без причины.

## PS-18. Работа повторяется по календарю

Если один и тот же результат повторяется по расписанию:

```text
Recurring Task
```

Проверить на стенде перенос Properties/Subtasks, если процесс от этого зависит.

## PS-19. Повторяется целая инициатива

Если повторяется набор Tasks, ролей, зависимостей и milestones:

```text
Project Template + Project Roles
```

Не заменять такую структуру одной большой recurring Task.

## PS-20. Нужна Subtask

Создать Subtask, если часть работы имеет самостоятельный результат или отдельное управление.

Технические шаги одного исполнения можно оставить в Description или Activities.

## PS-21. Сообщение породило обязательство

Discuss, email или Chatter остаются каналом коммуникации.

Если из сообщения появляется отдельный контролируемый результат — создать Task или дополнить существующую.

## PS-22. Вход через Email Alias / Website / API

Автоматически созданная запись не обязана сразу получать конкретный Stage, Assignee, Priority или Deadline.

Автоматизация допустима только если правило действительно однозначно.

Иначе запись проходит обычный triage по правилам процесса.

## PS-23. Нужен предметный реестр, которого нет в Odoo

Сначала определить, является ли объект самостоятельной сущностью.

Если это просто атрибут Task — использовать Property/Tag/поле.

Если объект имеет собственные номер, даты, lifecycle, права, связи и отчёты — рассматривать отдельную model, а не превращать Task в псевдореестр.

## PS-24. Нужно ограничить действия пользователей

Сначала определить бизнес-правило:

```text
кто видит?
кто создаёт?
кто изменяет?
кто удаляет?
какие records доступны?
```

Затем настраивать:

```text
Groups
Access Rights
Record Rules
Project visibility
```

Не выводить полномочия из названия должности или роли, которой нет в согласованном процессе.
