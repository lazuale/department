# Рабочие сценарии

[Главная](../README.md) · [00 Возможности](00-odoo19-community.md) · [01 Модель](01-methodology.md) · **02 Сценарии** · [03 Аналитика](03-control.md) · [04 Шаблоны](04-templates.md) · [05 Процессы](05-processes.md) · [06 Настройка](06-workspace.md)

---

Сценарии используют только подтверждённые механизмы Odoo 19 Community. Если предметный объект нужен в Task, сначала используется **relational Property**, а не текстовая копия справочника и не custom field.

## PS-01. Разобрать входящее

1. Определить, что пришло: данные об объекте, сообщение, встреча или обязательство.
2. Если нужно только изменить master data — обновить Employees / Contacts / Fleet / Maintenance / Inventory.
3. Если отдельного контролируемого результата нет — Task не создавать.
4. Если Task на тот же результат уже есть — дополнить её.
5. Иначе создать Task в `Входящие`.
6. Определить результат, Deadline и нужные Properties.
7. Готовую работу перевести в `Очередь`; при фактическом старте — назначить владельца и перевести в `В работе`.

## PS-02. Взять Task из общей очереди

Общая очередь:

```text
Stage = Очередь
Assignees = empty
```

При взятии:

1. назначить себя Assignee;
2. проверить результат и Deadline;
3. заполнить предметные Properties, если они нужны процессу;
4. перевести в `В работе` только при реальном начале.

## PS-03. Назначить заранее

Старший может назначить владельца до начала работы.

```text
Stage = Очередь
Assignee = пользователь
```

Назначение не означает фактический старт.

## PS-04. Ждём внешний ответ

1. Выполнить доступное действие.
2. Stage → `Ожидание внешнего`.
3. Владелец результата сохраняется.
4. Создать Activity на следующую контрольную дату.
5. Deadline результата не заменять Activity Due Date.

После ответа:

- требуется обработка → `В работе`;
- нужен повторный follow-up → новая Activity;
- результат достигнут → `Done`.

## PS-05. Ждём другую Task

Если продолжение действительно невозможно до результата другой Task:

```text
Blocked by = другая Task
```

Odoo вычисляет `Waiting` автоматически.

Не использовать `Ожидание внешнего` для внутренней dependency.

## PS-06. Контролируемый запрос

Использовать `Вид работы = Запрос`, если нужно отдельно получить и проконтролировать конкретный результат.

1. Создать Task.
2. Указать результат и Deadline.
3. Отправить запрос.
4. Stage → `Ожидание внешнего`.
5. Создать Activity follow-up.
6. После получения проверить результат.
7. `Done` только после фактического получения/проверки.

## PS-07. Срок под угрозой

- исходный Deadline ошибочен → исправить с пояснением;
- внешний срок подтверждённо изменился → обновить и зафиксировать основание;
- нужен ресурс/решение → эскалировать;
- оснований для переноса нет → Deadline оставить, Task становится overdue.

Не переносить срок ради чистого отчёта.

## PS-08. Urgent прерывает обычную работу

Если пользователь реально переключился:

- прежняя Task остановлена → `Очередь`;
- её продолжает другой → сменить Assignee, оставить `В работе`;
- появилась внутренняя блокировка → `Blocked by`;
- появилось внешнее ожидание → `Ожидание внешнего` + Activity.

## PS-09. Передать работу

| Ситуация | Действие |
|---|---|
| новый владелец продолжает сейчас | сменить Assignee, оставить `В работе` |
| продолжит позже | `Очередь` |
| ждём внешнее | `Ожидание внешнего` + Activity |
| ждём внутреннюю Task | `Blocked by` |
| результат уже готов | `Done` |

## PS-10. Календарная периодика

Для одного регулярно повторяемого результата:

```text
Recurring Task
```

Следующий экземпляр создаётся после закрытия текущего.

## PS-11. Типовая разовая работа

Если один и тот же вид Task появляется по событию, а не по календарю:

```text
Task Template
```

Примеры:

- разобрать расхождение;
- проверить корректировку;
- подготовить типовой ответ.

Шаблон может содержать устойчивое описание, Properties и оправданные subtasks.

## PS-12. Повторяется целая инициатива

Если повторяется структура из нескольких Tasks, ролей, зависимостей и вех:

```text
Project Template + Project Roles
```

Не заменять такую структуру одной огромной recurring Task.

## PS-13. Нужна Subtask

Создать Subtask, если часть имеет самостоятельный:

- результат;
- владельца;
- Deadline;
- dependency;
- контроль.

Технические шаги одного исполнителя лучше оставить в описании/Activities.

## PS-14. Нужна проверка результата

Если независимая проверка — устойчивая часть процесса:

1. Stage → `На проверке`;
2. Activity проверяющему;
3. при необходимости `Approved` / `Changes Requested`;
4. после принятия → `Done`.

Если проверка эпизодическая, отдельный общий Stage не нужен.

## PS-15. Ошибка после Done

Если исходный результат был неправильным:

1. открыть ту же Task;
2. вернуть в рабочий Stage;
3. зафиксировать ошибку;
4. исправить;
5. снова `Done`.

## PS-16. Новый объём после Done

Если исходный результат был корректным, а позже появился новый самостоятельный объём — создать новую Task.

## PS-17. Дубликат

1. Выбрать основную Task.
2. Перенести уникальный контекст.
3. Дубликат → `Canceled`.
4. При необходимости оставить ссылку на основную Task.

## PS-18. Работа больше не нужна

State → `Canceled`.

Причину зафиксировать в Chatter, если она неочевидна.

## PS-19. Task относится к ТС

1. Источник истины по ТС — Fleet.
2. В Task использовать:

```text
Property: ТС
Type: Many2one
Model: fleet.vehicle
```

3. Выбрать существующий Vehicle.
4. Не копировать госномер, модель, водителя и другие Fleet-поля в отдельные текстовые Properties.
5. Для массового контроля использовать Filter / Group By по Property `ТС`.

Custom `vehicle_id` обсуждается только если **реальный пилот** докажет, что relational Property не закрывает производительность, интеграцию, constraint или BI-задачу.

## PS-20. Task относится к сотруднику

Исполнитель работы и сотрудник-объект могут быть разными людьми.

```text
Assignee = кто отвечает за результат
Property[Сотрудник] = hr.employee, которого касается работа
```

Не назначать Employee исполнителем только ради ссылки.

## PS-21. Task относится к оборудованию

Если нужен отдельный управленческий результат поверх Equipment:

```text
Property: Оборудование
Type: Many2one
Model: maintenance.equipment
```

Если событие полностью описывается Maintenance Request — вести его в Maintenance и не дублировать Project Task.

## PS-22. Одна Task относится к нескольким объектам

Сначала решить, не являются ли это несколькими самостоятельными результатами.

Если результат действительно один, допустим Many2many Property, например:

```text
Затронутые ТС → Many2many(fleet.vehicle)
```

## PS-23. Сообщение Discuss породило обязательство

Обсуждение остаётся в Discuss, но самостоятельный результат становится Task.

Чат не является backlog.

## PS-24. Личная To-Do стала обязательством отдела

```text
To-Do → Convert to Task
```

После конвертации назначить Project и привести Task к нормальному состоянию `Входящие` / `Очередь`.

## PS-25. Task создана email alias

Email alias — канал регистрации, не автоматический триаж.

Проверить:

- дубль;
- нужен ли вообще отдельный результат;
- правильный Title;
- Deadline;
- Properties;
- дальнейший Stage.

## PS-26. Task создана Website Form

Использовать тот же triage, что для email.

Форма не определяет автоматически процесс, приоритет или владельца результата.

## PS-27. Массово загрузить справочник

1. Выбрать правильную модель.
2. Подготовить CSV/XLSX.
3. `Actions → Import records`.
4. Сопоставить поля.
5. `Test`.
6. Импортировать.
7. Для повторных update использовать стабильный External ID.

## PS-28. Нужна новая автоматизация

Проверять по порядку:

```text
Property
→ Task Template
→ Activity / chaining
→ Activity Plan
→ Recurring Task
→ Shared View
→ bridge module
→ Automation Rule
→ API/Webhook
```

Automation Rule создаётся только для однозначного события и действия.

## PS-29. Кажется, что нужен custom module

Сначала зафиксировать:

```text
Требование:
<что нужно получить>

Штатная предметная модель:
<какая>

Relational Property:
<проверено / почему недостаточно>

Bridge module:
<проверен / нет>

Standard view/report:
<что уже есть>

Реальный объём:
<данные пилота>

Остаточный gap:
<конкретно что не работает>
```

Отсутствие обычного Python-поля само по себе **не является gap**, если задача закрывается relational Property.
