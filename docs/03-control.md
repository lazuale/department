# Контроль и аналитика

Цель контроля — не собрать отдельный отчёт, а быстро увидеть исключения в тех же данных, в которых ведётся работа.

## 1. Три уровня

| Уровень | Инструмент Odoo | Что решаем |
|---|---|---|
| Личный | `Мои задачи`, Activities | что делать сейчас и что требует следующего действия |
| Оперативный | сохранённые фильтры, List/Kanban | где очередь, просрочка, ожидание, блокировка и неназначенная работа |
| Периодический | Task Analysis, Pivot/Graph, при необходимости Dashboard | где меняется поток, копится хвост и возникает системная проблема |

Не создавать ручной ежедневный отчёт, если тот же вопрос решается сохранённым представлением Odoo.

## 2. Минимальный набор оперативных представлений

### `Входящие`

Условия:

- основной рабочий проект;
- открытые задачи;
- этап `Входящие`.

Задача: не допустить, чтобы зарегистрированная работа осталась неразобранной.

### `Общая очередь`

Условия:

- открытые задачи;
- этап `Очередь`;
- исполнитель не назначен.

Задача: видеть работу, которую ещё никто не взял.

### `Моя очередь`

Условия:

- открытые задачи;
- исполнитель = текущий пользователь;
- этап `Очередь`.

Задача: видеть назначенную, но ещё не начатую работу.

### `Моя работа`

Условия:

- открытые задачи;
- исполнитель = текущий пользователь;
- этап `В работе`.

Задача: список фактически выполняемых результатов.

Если здесь десятки задач, проблема обычно не в отчёте, а в недостоверном ведении этапов.

### `Просрочено`

Условия:

- открытые задачи;
- Deadline раньше текущей даты.

Группировки по необходимости:

- исполнитель;
- этап;
- `Процесс`;
- `Вид работы`.

Просрочка — исключение для разбора, а не повод автоматически переносить Deadline.

### `Ожидание внешнего`

Условия:

- открытые задачи;
- этап `Ожидание внешнего`.

Проверить:

- есть ли ответственный;
- есть ли ближайшая Activity;
- не прошёл ли Deadline конечного результата.

### `Внутренние блокировки`

Условия:

- открытые задачи;
- системный статус `Waiting`.

Проверить блокирующие задачи и сроки. Не смешивать этот список с внешним ожиданием: причины и действия разные.

### `Критичные`

Условия:

- открытые задачи;
- приоритет `Urgent`.

Критичных задач должно быть немного. Если почти всё становится `Urgent`, приоритет перестаёт что-либо означать.

### `Просроченные активности`

Использовать штатный контроль Activities.

Это особенно важно для задач в `Ожидание внешнего`: просроченная Activity означает, что запланированное follow-up действие не выполнено вовремя, даже если Deadline конечного результата ещё не наступил.

## 3. Что старший смотрит ежедневно

Не все задачи подряд, а исключения:

1. неразобранные `Входящие`;
2. `Urgent` без понятного действия;
3. просроченные задачи;
4. неназначенную общую очередь с ближайшими Deadline;
5. `Ожидание внешнего` без следующей Activity или с просроченной Activity;
6. системный `Waiting` и блокирующие задачи;
7. слишком большое фактическое `В работе` у одного исполнителя;
8. задачи, которые давно не меняют этап и требуют внимания;
9. периодические задачи, которые просрочены или перестали нормально создавать следующий экземпляр.

Результат разбора отражается в самой задаче: назначение, этап, Activity, зависимость, Deadline или управленческое решение.

## 4. Что руководитель смотрит периодически

### 4.1 Поток работы

Нужно понимать:

- сколько задач появляется;
- сколько закрывается;
- растёт или сокращается открытый хвост.

Использовать стандартный Task Analysis/Pivot/Graph и временные группировки по созданию/закрытию там, где они доступны.

Не добиваться идеальной «научной» метрики ценой ручного заполнения дополнительных полей.

### 4.2 Структура открытого хвоста

Считать открытые задачи по:

- этапу;
- исполнителю;
- `Процессу`;
- `Виду работы`;
- приоритету.

Цель — найти перегруженный участок процесса, а не построить рейтинг людей.

### 4.3 Просрочка

Смотреть:

- количество просроченных открытых задач;
- в каких процессах они концентрируются;
- у каких этапов возникает хвост;
- повторяются ли одинаковые причины.

Процент просрочки имеет смысл только при стабильном знаменателе и понятном периоде. На старте достаточно абсолютного количества и разбора причин.

### 4.4 Внешнее ожидание и внутренние блокировки

Анализировать отдельно:

- внешний хвост по этапу `Ожидание внешнего`;
- внутренние блокировки по статусу `Waiting`.

Если их смешать, невозможно понять, что лечить: коммуникацию с внешним участником или внутреннюю зависимость процессов.

### 4.5 Скорость прохождения

Стандартный анализ задач Odoo содержит временные показатели, связанные с назначением и закрытием задач. Их можно использовать для поиска аномально медленных процессов и изменения тренда.

Не использовать среднее время закрытия без разбиения по типу/процессу, если задачи сильно различаются по масштабу.

## 5. Минимальный набор управленческих показателей

| Показатель | Источник | Решение |
|---|---|---|
| Новые задачи | дата создания / Task Analysis | изменение входящего потока |
| Закрытые задачи | закрытые задачи / Task Analysis | способность контура завершать работу |
| Открытый хвост | открытые задачи | растёт ли незавершённая работа |
| Просрочено | Deadline + открытый статус | где нарушается срок |
| Общая очередь | `Очередь` + без исполнителя | хватает ли мощности и разбора |
| Внешнее ожидание | этап `Ожидание внешнего` | где зависим от внешней стороны |
| Внутренние блокировки | статус `Waiting` | где процессы блокируют друг друга |
| Urgent | приоритет | сколько реальных критичных исключений |
| Время назначения/закрытия | Task Analysis | где работа системно проходит медленно |

Этого достаточно для первого рабочего контура.

## 6. Что специально не считаем базовой метрикой

### Возвраты после Done

История изменений сохраняется в Chatter, но штатный Task Analysis не следует считать готовым счётчиком всех переоткрытий и переходов.

Не вводить ручной флажок `Возврат` только ради красивого KPI. Если качество станет отдельной управленческой проблемой, способ измерения проектируется отдельно.

### Время в каждом этапе

Не заявлять его базовой метрикой без отдельной технической реализации. `Last Stage Update` полезен для поиска зависших задач, но это не полноценная история длительности каждого этапа.

### Производительность сотрудника по количеству карточек

Не использовать как рейтинг:

- количество закрытых задач;
- число комментариев;
- число Activities;
- количество смен этапа;
- время присутствия в Odoo.

Разные задачи имеют разную трудоёмкость и ценность. Эти данные можно использовать для поиска перегруза и аномалий, но не как автоматическую оценку человека.

### Timesheets без решения

Не заставлять всех списывать время только потому, что такая функция есть. Включать Timesheets, если есть конкретная задача: трудоёмкость, стоимость, планирование мощности или расчёт услуги.

## 7. Сохранённые фильтры раньше дашборда

Порядок внедрения аналитики:

1. рабочие данные ведутся достоверно;
2. создаются сохранённые фильтры и группировки;
3. проверяется, какие вопросы руководитель реально задаёт регулярно;
4. только затем устойчивые показатели выносятся в Pivot/Graph;
5. Dashboard создаётся, когда состав показателей перестал меняться каждую неделю.

Не начинать внедрение с красивой панели поверх неустойчивых данных.

## 8. Как искать системную проблему

Сигналы:

- растёт общий открытый хвост;
- растёт хвост одного процесса;
- постоянно растёт `Ожидание внешнего`;
- повторяются внутренние блокировки одного типа;
- `Urgent` становится нормой;
- Deadline регулярно переносятся перед просрочкой;
- у сотрудников хронически слишком много задач `В работе`;
- большая доля задач остаётся без исполнителя дольше допустимого времени разбора;
- одна и та же ручная операция порождает повторяющиеся задержки.

После подтверждения проблемы создаётся не «отчёт о проблеме», а управленческое решение:

- изменить правило;
- перераспределить ресурс;
- изменить процесс;
- автоматизировать конкретный узкий участок;
- либо признать ограничение и скорректировать обязательство.

Если принято решение что-то изменить, создаётся задача `Вид работы = Улучшение`.

## 9. Признаки плохой настройки Odoo

- этапы дублируют системные статусы;
- есть одновременно `Готово` как этап и `Done` как статус без понятной причины;
- внешний и внутренний `Waiting` смешаны;
- проекты созданы на каждый процесс или сотрудника;
- для аналитики заведено много свойств, которыми никто не пользуется;
- несколько исполнителей используются вместо одного ответственного;
- Activities заменяют конечные задачи или Deadline заменяет Activities;
- регулярные задачи дублируются вручную поверх рекуррентности;
- вся работа отмечена высоким приоритетом;
- дашборд существует, а его цифры не приводят ни к одному решению.
