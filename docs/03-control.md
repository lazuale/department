## 1. Принцип

Контроль и аналитика строятся на тех же Задачах, которыми сотрудники пользуются каждый день.

Не создавать параллельный Excel-реестр, журнал или отдельный ручной отчёт только ради руководителя, если нужный факт уже есть в Odoo.

## 2. Ежедневный контроль Ответственного

Рабочее представление должно быстро отвечать:

- что просрочено;
- что имеет высокий или срочный Приоритет;
- что сейчас `В работе`;
- что лежит в `Очереди`;
- что находится во `Внешнем ожидании`;
- какие Задачи заблокированы внутренними зависимостями;
- какие Активности просрочены или назначены на сегодня.

Цель — выбрать следующее действие, а не заполнить отчёт.

Личные этапы можно использовать для собственного планирования, но они не заменяют общие Этапы и не входят в управленческую картину процесса.

## 3. Ежедневный контроль руководителя

Руководитель или старший работает прежде всего с отклонениями:

- открытые просроченные Задачи;
- Задачи без Ответственного;
- высокий и срочный Приоритет;
- внешнее ожидание без понятного следующего действия;
- внутренние блокировки;
- Задачи, которые долго не менялись;
- `Запросы`, у которых подошёл срок получения;
- перегруженная `Очередь`;
- дубли и ошибочная классификация;
- Задачи без Процесса или обязательного по методике Вида работы.

Руководитель не должен вручную подтверждать каждое обычное действие сотрудника.

## 4. Базовые показатели

Первая версия использует только факты, которые Odoo получает устойчиво без дополнительного ручного учёта.

| Показатель | Смысл |
|---|---|
| Поступило | Задачи, созданные за период |
| Завершено | Задачи, переведённые в `Готово` за период |
| Отменено | Задачи, переведённые в `Отменено` за период |
| Открыто | все незакрытые Задачи на дату |
| Просрочено | открытые Задачи с прошедшим Крайним сроком |
| Очередь | Задачи на Этапе `Очередь` |
| В работе | Задачи на Этапе `В работе` |
| Внешнее ожидание | Задачи на Этапе `Внешнее ожидание` |
| Внутреннее ожидание | Задачи в состоянии `В ожидании` из-за внутренних зависимостей |
| Без Ответственного | открытые Задачи без назначенного пользователя |
| Структура потока | Тип задачи, Процесс, Вид работы, Ответственный, Приоритет, Теги, Веха |

Отдельная метрика времени прохождения не считается базовой, пока не проверено, что она корректно считается при выбранной схеме закрытия через состояние `Готово`.

## 5. Главные аналитические разрезы

### Основные

- Тип задачи `Работа / Запрос`;
- Процесс;
- Вид работы для `Работ`;
- Этап;
- Состояние;
- Ответственный;
- Крайний срок и просрочка;
- Приоритет;
- период создания и закрытия.

### По реальной потребности

- Веха;
- Теги;
- связанный сотрудник;
- внешний контакт или организация;
- оборудование;
- участок или другой локальный объект.

Новый аналитический признак не добавляется только потому, что его можно добавить.

## 6. Что не требуется считать на старте

Без подтверждённой потребности не строить отдельный учёт:

- накопленного времени во всех ожиданиях;
- количества передач между Ответственными;
- количества возвратов после `Готово`;
- точного времени активного выполнения;
- количества комментариев, Активностей или смен Этапов;
- рейтингов сотрудников по числу закрытых Задач.

Если показатель действительно нужен для управленческого решения и штатных данных недостаточно, тогда оценивается способ расчёта или доработка.

## 7. Аналитика `Процесс × Вид работы`

Это основной разрез структуры `Работ`.

Он показывает, чем фактически наполнены Процессы: внесением, проверкой, сверкой, исправлением, мониторингом, анализом или подготовкой.

На пилоте Процесс и Вид работы ведутся через Свойства задачи. Нужно проверить:

- удобно ли фильтровать Задачи по каждому Свойству;
- удобно ли группировать по Свойствам;
- можно ли без лишних действий получить нужную перекрёстную Сводную таблицу или График;
- достаточно ли качества заполнения без жёсткой обязательности на уровне базы.

Если эти пункты выполняются, отдельные поля и модели не нужны.

## 8. Что обязательно проверить на пилоте

### Свойства и Сводная таблица

Проверить реальный разрез `Процесс × Вид работы`, а не только одиночную группировку по Свойствам.

### Время прохождения

Odoo имеет штатные поля рабочего времени до назначения и закрытия, но при нашей схеме завершения через состояние `Готово` их корректность нельзя считать доказанной заранее. До проверки не использовать их как KPI и не строить на них выводы.

### Повторяемость

Проверить на реальных периодических сценариях:

- перенос Ответственных;
- перенос Тегов;
- перенос Свойств задачи;
- сброс Приоритета на низкий;
- попадание нового экземпляра в первый Этап.

### Импорт

Отдельно проверить массовую загрузку и обновление значений Свойств, если они будут использоваться в регулярных импортных сценариях.

## 9. Периодический управленческий разбор

Руководитель смотрит не активность пользователей, а поток и повторяющиеся отклонения.

Минимум:

- поступило / завершено;
- изменение количества открытых Задач;
- просрочки;
- структура `Процесс × Вид работы`;
- Задачи высокого и срочного Приоритета;
- внутренние блокировки;
- внешнее ожидание;
- повторяющиеся причины проблем, которые видны из Задач и истории общения;
- среднее или медианное время прохождения — только после подтверждения корректного источника данных.

## 10. Трудозатраты

Количество Задач не равно человеко-часам.

Табели времени включаются только для тех Процессов, где действительно требуется анализ фактических трудозатрат и пользователи могут вести время достаточно точно без избыточной нагрузки.

Если часы не используются для решения — не делать их обязательными.

## 11. Не использовать как рейтинг сотрудников

Не ранжировать людей по:

- числу закрытых Задач;
- числу комментариев;
- числу Активностей;
- числу смен Этапа или Состояния;
- учтённым часам без контекста;
- числу Задач конкретного Вида работы.

Эти данные нужны для поиска перегруза, узких мест и особенностей Процесса.

## 12. Когда менять Процесс или систему

Изменение должно опираться на повторяемый факт, например:

- количество открытых Задач устойчиво растёт;
- один Вид работы регулярно просрочен;
- одна и та же блокировка повторяется;
- много Задач приходится искать по свободному тексту;
- сотрудники вынуждены дублировать Odoo в Excel или чате;
- стандартный путь требует постоянных лишних действий;
- Процесс или Вид работы системно заполняются неправильно;
- штатной аналитики недостаточно для реального решения.

После изменения сравниваются те же факты.
