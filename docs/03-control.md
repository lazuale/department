Контроль строится по тем же records, в которых ведётся работа. Базовая методика не задаёт универсальные KPI, нормативы WIP или обязательные очереди для всех процессов.

## 1. Уровни контроля

| Уровень | Инструменты Odoo | Вопрос |
|---|---|---|
| личный | My Tasks / Activities | что требует действия пользователя |
| операционный | List / Kanban / Shared Views | какие Tasks требуют внимания сейчас |
| периодический | Task Analysis / Pivot / Graph / My Dashboard | как меняется поток работы |
| предметный | Fleet / Maintenance / Inventory / HR и другие reports | что происходит с предметными объектами |

Task analytics не заменяет аналитику предметной модели.

## 2. Shared Views — сохранённые управленческие вопросы

Shared View создаётся только для устойчивого вопроса, который реально повторяется.

Примеры возможных вопросов:

```text
какие Tasks просрочены?
какие Tasks неназначены?
какие Tasks имеют Urgent Priority?
какие Tasks ждут другую Task?
какие Activities просрочены?
какие Tasks относятся к конкретному объекту?
```

Не требуется создавать все эти views в каждом процессе.

## 3. List и Kanban

### List

Полезен для:

- большого набора records;
- сортировки;
- сравнения нескольких полей;
- массовых действий;
- Deadline / Priority / Activities;
- Properties.

### Kanban

Полезен для:

- визуального движения по Stages;
- понимания распределения records между стадиями;
- работы с небольшими и средними наборами.

Какое представление является основным, определяется фактическим сценарием пользователей.

## 4. Deadline

Deadline позволяет видеть Tasks, результат которых должен быть получен к определённой дате.

Просрочка имеет смысл только там, где Deadline действительно является сроком результата.

Не строить отчёт по просрочке на Tasks, которым сроки не нужны по смыслу процесса.

## 5. Assignees

Аналитика по Assignees показывает распределение Tasks, но сама по себе не измеряет производительность человека.

Не использовать без отдельной методики оценки:

- количество закрытых Tasks;
- количество открытых Tasks;
- Timesheets;
- Activities;

как рейтинг сотрудников.

## 6. Stage

Stage показывает положение Task в конкретно настроенном workflow.

Сравнивать Stages между разными Projects имеет смысл только если их семантика сопоставима.

Количество Tasks в Stage не является автоматически проблемой: сначала нужен контекст процесса.

## 7. State

State полезен для системного разделения open/closed и других штатных состояний.

Не дублировать State отдельной локальной классификацией только ради отчёта.

## 8. Dependencies

Если используются Dependencies, Odoo позволяет анализировать:

- Waiting Tasks;
- blocking Tasks;
- связанные зависимости.

Это отдельный вопрос от внешнего ожидания, которое может быть отражено Stage/Activity/Chatter по правилам процесса.

## 9. Activities

Activity отвечает на вопрос о следующем действии.

Полезные стандартные срезы могут включать:

- My Activities;
- Late Activities;
- Today Activities;
- Future Activities.

Использовать их только там, где процесс реально ведёт follow-up через Activities.

## 10. Rotting

Rotting показывает, что Task долго не меняла Stage.

Это диагностический сигнал, а не универсальное нарушение.

`Days to rot` настраивается только после понимания нормальной длительности конкретного Stage.

## 11. Время в Stage

Odoo показывает длительность нахождения конкретной Task в Stages.

Это полезно при разборе отдельной зависшей работы.

Не считать стандартный Pivot готовым агрегированным SLA-report по каждому Stage. Если такой показатель реально нужен, он проверяется отдельно.

## 12. Relational Properties как аналитические разрезы

Если Task связана с предметной моделью через Property, стандартный Search/Group By позволяет использовать Property в рабочих срезах.

Примеры:

```text
Tasks по ТС
Tasks по Employee-object
Tasks по Equipment
Tasks по контрагенту
```

Такой разрез добавляется только если отвечает на реальный управленческий вопрос.

## 13. Предметная аналитика остаётся в предметном приложении

Примеры:

```text
Fleet       → vehicle / odometer / services / costs
Maintenance → equipment / maintenance requests
Inventory   → stock / serial / movement / location
Employees   → employee data
```

Не пытаться рассчитывать состояние предметного объекта только по количеству связанных Tasks.

## 14. Priority

Priority — сигнал порядка обработки только если процесс определил его смысл.

Odoo поддерживает Low / Medium / High / Urgent.

Не вводить локальную шкалу и KPI по Priority без конкретного правила процесса.

## 15. Task Analysis

Сначала использовать штатные dimensions/measures, доступные в Task Analysis.

Типовые вопросы:

- сколько Tasks создано/закрыто;
- как распределяются Tasks по Project/Stage/State/Assignee/Priority;
- как меняется backlog;
- сколько времени проходит до назначения/закрытия, если этот показатель имеет смысл.

Не превращать наличие measure в обязательный KPI.

## 16. My Dashboard

My Dashboard используется для устойчивого набора уже определённых вопросов.

Правильный порядок:

```text
сначала рабочий вопрос
→ затем Filter / Group By / Pivot / Graph
→ проверить полезность
→ только потом добавить на Dashboard
```

Dashboard не должен становиться отдельной методологией поверх данных.

## 17. Spreadsheet Dashboard

Не входит в гарантированный Community baseline до runtime/edition-проверки.

Основной click-only путь:

```text
Views
→ Task Analysis
→ Pivot / Graph
→ My Dashboard
```

Внешний BI подключается, если штатная аналитика не отвечает на нужный вопрос или требуется объединение данных нескольких систем.

## 18. Контроль качества данных

Для каждого процесса полезнее определить не универсальный KPI, а проверяемые исключения.

Примеры:

```text
Task без ожидаемой предметной ссылки
Task без Deadline там, где процесс требует срок
некорректный Stage
неожиданно пустой Assignee там, где процесс требует назначения
просроченная Activity там, где follow-up обязателен
```

Какие поля обязательны и какие исключения считаются ошибкой, определяет конкретный процесс.

## 19. Аналитический gap

Custom report / BI / model нужен только после формулировки конкретного вопроса, который нельзя надёжно получить штатными средствами.

Не начинать с «нужен dashboard». Начинать с:

> Какое решение должно быть принято по результату этого показателя?
