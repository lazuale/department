# Скрипты бизнес-процессов

## 1. Формат скрипта

Каждый скрипт описывается одинаково:

- **Триггер** — что запускает процесс;
- **Решение** — что необходимо определить;
- **Действия** — последовательность шагов;
- **Фиксация** — что должно остаться в рабочей системе;
- **Выход** — когда сценарий завершён;
- **Исключения** — когда применяется другой сценарий.

---

# PS-01. Разбор входящего рабочего канала

## Триггер

Получено письмо, документ, обращение, сообщение или иная информация, потенциально требующая действия.

## Решение

Необходимо определить один из трёх исходов:

1. новая обязательная работа;
2. продолжение существующей работы;
3. действий не требуется.

## Действия

1. Определить, требуется ли конкретный результат от подразделения.
2. Проверить, существует ли уже открытая Work Package по этому результату.
3. Если работа новая — создать Work Package.
4. Если работа существует — добавить существенную информацию и вложения в неё.
5. Если действий не требуется — Work Package не создавать.

## Фиксация

Для новой работы обязательно определить:

- понятный Subject;
- Type;
- Category;
- Status `Очередь`;
- Assignee, если владелец уже известен;
- Finish date;
- Priority;
- необходимые исходные материалы.

## Выход

Во входящем канале не остаётся сообщения с неясной судьбой, которое потенциально требует действия.

## Исключения

Если определить требуемый результат невозможно, создаётся работа на уточнение смысла обращения только если само уточнение требует отдельного контроля. Иначе вопрос уточняется в рамках разбора входа.

# PS-02. Регистрация обычной работы

## Триггер

Подтверждено наличие нового обязательного результата.

## Действия

1. Создать Type `Работа`.
2. Выбрать устойчивую Category бизнес-процесса.
3. Сформировать Subject по шаблону.
4. Установить `Очередь`.
5. Назначить Assignee, если он известен.
6. Установить Finish date.
7. Установить Priority.
8. Добавить только материалы, необходимые для выполнения или подтверждения основания.

## Выход

Работа видима в очереди и может быть независимо взята, просрочена, поставлена на ожидание, завершена или отменена.

---

# PS-03. Выбор работы из очереди

## Триггер

Исполнитель освобождает рабочую ёмкость и может начать следующий результат.

## Порядок выбора

1. `Критичный` Priority;
2. ближайший Finish date;
3. наиболее старая Work Package;
4. остальные работы.

## Действия

1. Выбрать следующую работу.
2. Убедиться, что её можно фактически начать.
3. Установить себя Assignee, если работа находилась в групповой или общей очереди.
4. Перевести `Очередь → В работе`.
5. Начать выполнение.

## Запрет

Нельзя переводить в `В работе` карточки, которые только планируется выполнить позже.

---

# PS-04. Обычное выполнение и закрытие

## Триггер

Work Package находится `В работе`.

## Действия

1. Выполнить необходимые операции до достижения результата.
2. Промежуточные письма, звонки и файлы не превращать в отдельные Work Package без самостоятельного результата.
3. При необходимости сохранять существенный контекст в Activity.
4. Проверить Definition of Done Category.
5. Если DoD достигнут — `В работе → Готово`.

## Выход

По Work Package не остаётся обязательных действий подразделения.

---

# PS-05. Внешняя блокировка

## Триггер

Исполнитель не может продолжить работу из-за внешнего условия.

Примеры:

- отсутствует документ;
- требуется уточнение;
- ожидаются внешние данные;
- необходим ответ другой стороны;
- техническая возможность временно отсутствует.

## Действия

1. Выполнить действие, необходимое для снятия блокировки.
2. Перевести `В работе → Ожидание`.
3. Не менять Assignee.
4. Оставить комментарий по строгому шаблону ожидания.
5. Не переносить Finish date только из-за факта ожидания.

## После снятия блокировки

- если исполнение продолжается сразу: `Ожидание → В работе`;
- если работа возвращается в общий поток: `Ожидание → Очередь`;
- если ожидаемый ответ сам завершил результат: `Ожидание → Готово`.

---

# PS-06. Самостоятельный исходящий запрос

## Триггер

Необходимо получить самостоятельный контролируемый результат от внешней стороны.

## Критерии отдельной Work Package

Отдельный `Запрос` создаётся, если имеется хотя бы один существенный признак:

- собственный срок;
- отдельный владелец;
- несколько адресатов;
- самостоятельное сопровождение;
- результат используется несколькими работами;
- получение ответа само является конечным результатом.

## Действия

1. Создать Type `Запрос`.
2. Установить Category процесса, который породил потребность.
3. Установить `Очередь`.
4. Установить Assignee и Finish date.
5. При фактической подготовке: `Очередь → В работе`.
6. После отправки и при отсутствии иных действий: `В работе → Ожидание`.
7. После ответа: `Ожидание → В работе` либо `Готово`.

## Запрет

Не создавать отдельный `Запрос` для каждого уточняющего письма внутри обычной работы.

---

# PS-07. Регламентная работа

## Триггер

Наступает плановый период выполнения обязательной операции.

## Подготовка

Регламентные Work Package создаются заранее на установленный горизонт планирования.

## Действия

1. Создать отдельную Work Package на каждый период.
2. Использовать Type `Работа`.
3. Subject должен содержать наименование результата и период.
4. Установить Category, Assignee, Finish date и Priority.
5. Начальный Status — `Очередь`.
6. Далее использовать обычный lifecycle.

## Запрет

Не использовать одну бесконечно переоткрываемую Work Package для всех периодов.

---

# PS-08. Разовое поручение

## Триггер

Получено разовое обязательное поручение.

## Решение

Определить уровень декомпозиции.

### Одна Work Package

Используется, если:

- результат один;
- основной исполнитель один;
- нет самостоятельных частей с отдельными сроками.

### Parent + child Work Package

Используется, если несколько частей имеют собственных владельцев, сроки или независимое завершение.

### Отдельный Project

Создаётся только при наличии нескольких проектных признаков: несколько результатов, участников, этапов, зависимостей и значительная продолжительность.

## Действия

После выбора уровня управления работа проходит стандартный lifecycle.

---

# PS-09. Передача активной работы

## Триггер

Заканчивается рабочий период исполнителя или требуется передача владельца.

## Действия

Для каждой Work Package `В работе` выбрать фактический вариант:

1. следующая сторона продолжает сразу — сменить Assignee, оставить `В работе`;
2. продолжение будет позже — `В работе → Очередь`;
3. продолжение невозможно — `В работе → Ожидание` + комментарий;
4. результат достигнут — `В работе → Готово`.

## Запрет

Нельзя оставлять `В работе` за отсутствующим исполнителем, если фактическое выполнение остановилось.

---

# PS-10. Дополнительная информация по открытой работе

## Триггер

Получено новое письмо, файл или уточнение по существующему результату.

## Действия

1. Найти исходную Work Package.
2. Добавить существенную информацию или вложение.
3. При необходимости скорректировать описание, срок или приоритет.
4. Новую Work Package не создавать.

## Исключение

Если информация создаёт новый независимо контролируемый результат, применяется PS-02.

---

# PS-11. Ошибка после закрытия

## Триггер

После `Готово` установлено, что первоначальный результат выполнен неверно или не полностью.

## Действия

1. Зафиксировать причину возврата.
2. Перевести `Готово → В работе`.
3. Исправить первоначальный результат.
4. После достижения DoD снова установить `Готово`.

## Назначение

Reopen используется как показатель качества первоначального выполнения.

---

# PS-12. Новый объём после закрытия

## Триггер

После корректного завершения возникло новое требование или дополнительный объём.

## Действия

1. Не переоткрывать исходную работу.
2. Создать новую Work Package.
3. При необходимости установить relation с исходной.

## Причина

История исходной работы должна отражать реальную длительность первоначального результата.

---

# PS-13. Обнаружен дубликат

## Триггер

Две Work Package описывают один и тот же самостоятельно контролируемый результат.

## Действия

1. Определить основную запись.
2. Перенести в неё недостающий существенный контекст.
3. Связать вторую как Duplicate.
4. Закрыть/отменить дубликат.
5. Не удалять историю.

---

# PS-14. Отмена работы

## Триггер

Результат больше не требуется.

## Действия

1. Проверить, что отменяется именно потребность в результате, а не просто меняется исполнитель или срок.
2. Установить `Отменено`.
3. Зафиксировать краткую причину.

---

# PS-15. Выборочный контроль качества

## Триггер

Наступил плановый контроль либо требуется целевой риск-контроль.

## Режим A: выборочная проверка

Просматривается обычная выборка завершённых работ без отбора только по подозрительным случаям.

## Режим B: риск-контроль

Целенаправленно проверяются критичные, необычные, ранее возвращавшиеся или потенциально проблемные работы.

## Действия при ошибке

Применяется PS-11.

## Правило интерпретации

Результаты риск-контроля не используются как оценка общей доли ошибок в потоке.

---

# PS-16. Оперативный управленческий обзор

## Триггер

Наступил установленный момент обзора потока.

## Последовательность

1. Просрочено.
2. Критичные.
3. Старые в `Очередь`.
4. Старые в `Ожидание`.
5. Без Assignee.
6. Аномальный WIP.
7. Reopen.
8. Повторяющиеся причины проблем.

## Выход

По каждому исключению должно быть одно из решений:

- продолжать по текущему плану;
- сменить приоритет;
- сменить владельца;
- эскалировать внешнюю зависимость;
- скорректировать срок с основанием;
- создать работу по устранению системной причины;
- создать идею улучшения.

---

# PS-17. Фиксация идеи улучшения

## Триггер

Обнаружено повторяющееся узкое место, ручная операция, дефект процесса или предложение по улучшению.

## Действия

1. Создать Type `Идея` в контуре развития.
2. Описать наблюдаемую проблему, а не только предлагаемое решение.
3. Поместить в `Inbox` backlog.
4. При наличии связанных Work Package добавить relations.

## Движение backlog

`Inbox → Наблюдаем → Разобрать → Кандидат → Готово к реализации`

## Выход

После решения о реализации создаётся обязательная Work Package, иерархия работ или отдельный Project.

---

# PS-18. Разбор backlog улучшений

## Триггер

Наступил плановый обзор улучшений.

## Вопросы

1. Проблема подтверждается фактами?
2. Она повторяется?
3. Какой объём ручной работы или задержек создаёт?
4. Можно ли устранить причину изменением процесса без автоматизации?
5. Если нужна автоматизация, понятен ли ожидаемый эффект?
6. Есть ли ресурс брать инициативу в реализацию?

## Правило

`Готово к реализации` должно оставаться коротким списком реально подготовленных инициатив, а не складом всех хороших идей.
