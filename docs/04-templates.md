Шаблон не должен превращать Task в анкету и не должен копировать данные из Fleet, Employees, Maintenance или Contacts.

## 1. Название Task

```text
<результат> — <объект / основание / период>
```

Примеры:

- `Провести сверку топлива — июль 2026`;
- `Исправить расхождение — основание №45`;
- `Получить подтверждение корректировки`;
- `Обновить правило обработки расхождений`.

Не использовать названия `Срочно`, `Посмотреть`, `Письмо`, `Важно`, `RE:`, `Разобраться` без результата.

## 2. Обычная Task

Штатные поля:

```text
Title: <результат>
Assignee: <владелец результата>
Deadline: <срок результата>
Stage: <фактический Stage>
Priority: <default / Urgent по правилу>
Вид работы: <Property>
Процесс: <Property, если используется>
Allocated Time: <только если нужен>
```

Описание:

```text
Основание:
<что запустило работу>

Результат:
<что должно быть получено>

Условия:
<только существенные ограничения>
```

Не повторять в описании Assignee, Deadline, Stage, Priority и значения структурированных Properties.

## 3. Ссылка Task на ТС

Master data:

```text
Fleet Vehicle
```

Task:

```text
Property: ТС
Type: Many2one
Model: fleet.vehicle
Value: <выбранный Vehicle>
```

В Title можно оставить понятный госномер для быстрого чтения, но структурированная связь должна быть Property, если объект используется системно.

Не создавать Selection со вручную внесёнными тысячами госномеров.

## 4. Ссылка Task на сотрудника

```text
Property: Сотрудник
Type: Many2one
Model: hr.employee
```

Это поле отвечает на вопрос:

> Какого сотрудника касается работа?

Assignee отвечает на другой вопрос:

> Кто отвечает за результат Task?

## 5. Ссылка Task на оборудование

```text
Property: Оборудование
Type: Many2one
Model: maintenance.equipment
```

Не дублировать в Task серийник, категорию и назначение Equipment, если они уже хранятся в Maintenance/Inventory.

## 6. Несколько объектов

Если один результат действительно относится к нескольким объектам:

```text
Type: Many2many
Model: <нужная model>
```

Перед этим проверить, не являются ли это несколькими самостоятельными Tasks.

## 7. Запрос

```text
Title: Получить <что> — <тема>
Вид работы: Запрос
Assignee: <владелец>
Deadline: <дата получения результата>
<предметный Property>: <если нужен>
```

После отправки:

```text
Stage = Ожидание внешнего
Activity = следующий follow-up
```

## 8. Внешнее ожидание

Chatter при необходимости:

```text
Сделано: <что и когда>.
Ждём: <какой внешний результат>.
```

Activity:

```text
Type: <Проверить / Напомнить / Позвонить / Эскалировать>
Due Date: <контрольная дата>
Assigned to: <кто делает follow-up>
Summary: <что проверить>
```

Не создавать отдельное поле `Ждём`, если Chatter + Activity решают задачу.

## 9. Улучшение

После решения `делаем`:

```text
Title: <конкретное изменение>
Вид работы: Улучшение
Assignee: <владелец>
Deadline: <срок результата>
Процесс: <если нужен>
```

Описание:

```text
Проблема:
<что повторяется>

Факты:
<примеры / Tasks / показатели>

Изменение:
<что внедрить>

Проверка эффекта:
<как поймём, что стало лучше>
```

## 10. Task Template

Для типовой разовой работы:

```text
Template Name: Разобрать расхождение

Title pattern:
Разобрать расхождение — <объект>

Description:
Результат:
<что должно быть проверено и исправлено>

Properties:
Вид работы = Работа
Процесс = <если устойчиво>

Subtasks:
<только самостоятельные части>
```

Не помещать в template конкретный Vehicle/Employee/Equipment, если он меняется от случая к случаю.

## 11. Recurring Task

Для календарной периодики:

```text
Title: Провести сверку — <период>
Recurrence: <правило>
```

Структуру recurrence держать простой и проверять, какие данные реально копируются стандартным Odoo.

## 12. Activity Type

```text
Name: Проверить ответ
Default User: <если однозначно>
Schedule: <через N дней>
Chaining: <Suggest / Trigger, если нужно>
Next Activity: <если есть>
```

## 13. Activity Plan

Для устойчивого набора follow-up:

```text
Plan: Контроль внешнего запроса
1. Проверить получение
2. Проверить ответ
3. Напомнить
4. Эскалировать
```

Самостоятельные результаты должны быть Tasks, а не Activities.

## 14. Описание процесса

```text
Название:
<процесс>

Предметные модели:
<Employees / Fleet / Maintenance / Inventory / Contacts / другое>

Источник истины:
<где живёт каждый объект>

Связь Task с объектом:
<Property label → Many2one/Many2many → Model → Domain>

Вход:
<что запускает процесс>

Результат:
<что должно быть получено>

Единица Task:
<что является одной Task>

Когда Task не нужна:
<обычное изменение master data / сообщение / встреча>

Deadline:
<правило>

Внешнее ожидание:
<Stage + Activity>

Внутренние зависимости:
<Blocked by>

Периодика:
<Task Template / Recurring Task / Project Template / нет>

Контроль:
<Shared Views / отчёты>

Остаточный gap:
<только после проверки Property / bridge / standard view>
```
