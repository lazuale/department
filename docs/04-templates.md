Шаблоны не должны превращать задачу Odoo в анкету. Заполняется только информация, которой нет в штатных полях и которая нужна для понимания результата.

## 1. Название задачи

```text
<что должно быть получено> — <объект / основание / период>
```

Примеры:

- `Провести сверку топлива — июль 2026`;
- `Исправить данные по ТС 123 — основание №45`;
- `Получить подтверждение корректировки — объект X`;
- `Обновить правило обработки расхождений`.

Не использовать названия `Срочно`, `Посмотреть`, `Письмо`, `Важно`, `RE:` или `Разобраться` без понятного результата.

## 2. Обычная задача

Штатные поля Odoo:

```text
Название: <результат>
Исполнитель: <один ответственный, если задача взята или назначена>
Deadline: <дата конечного результата>
Приоритет: обычный / Urgent
Этап: <фактический этап>
Вид работы: Работа
Процесс: <если используется>
```

Описание добавляется только если без него неясно, что считать результатом:

```text
Основание:
<что запустило работу>

Результат:
<что должно быть получено>

Условия:
<важные ограничения, если есть>
```

Не повторять в описании исполнителя, Deadline, приоритет и этап: для этого уже есть поля Odoo.

## 3. Запрос

```text
Название: Получить <что> — <тема>
Вид работы: Запрос
Исполнитель: <один ответственный>
Deadline: <когда результат должен быть получен>
Процесс: <если используется>
```

В описании достаточно точно указать, что нужно получить и основание, если оно неочевидно.

После отправки:

- этап `Ожидание внешнего`;
- Activity на следующее действие.

Дата напоминания не подменяет Deadline задачи.

## 4. Внешнее ожидание

При необходимости оставить в Chatter короткий фактический комментарий:

```text
Сделано: <что и когда>.
Ждём: <какое внешнее действие>.
```

Одновременно запланировать Activity:

```text
Действие: <проверить ответ / напомнить / позвонить / эскалировать>
Дата: <дата следующего контроля>
Ответственный: <кто выполнит действие>
```

Не создавать отдельное текстовое поле только для фразы `ждём`.

## 5. Улучшение процесса

После решения `делать`:

```text
Название: <конкретное изменение>
Вид работы: Улучшение
Исполнитель: <ответственный>
Deadline: <дата результата>
Процесс: <какого процесса касается>
```

Описание:

```text
Проблема: <что повторяется или теряется>
Факты: <задачи, показатели, примеры>
Изменение: <что именно нужно внедрить>
Проверка эффекта: <по чему поймём, что стало лучше>
```

Идея без решения о реализации не должна становиться обязательной задачей основного проекта.

## 6. Подзадача

Подзадача оформляется как обычная задача и должна иметь собственный результат, ответственного и при необходимости отдельный Deadline.

Не использовать подзадачи как чек-лист технических действий. Для простого следующего действия лучше Activity.

## 7. Описание процесса

Процесс описывается в репозитории, а не размножается в каждой задаче:

```text
Название: <процесс>
Вход: <что запускает работу>
Результат: <что должно быть получено>
Единица учёта: <что является одной задачей Odoo>
Исполнители: <роль или рабочая группа>
Deadline: <правило конечного срока>
Когда нужна подзадача: <критерий>
Внешнее ожидание: <типовые причины>
Внутренние зависимости: <типовые блокировки задачами Odoo>
Периодичность: <если есть>
Контроль: <какие исключения смотрим>
```

## 8. Локальные настройки

Фиксируются только отклонения от базовой модели:

```text
Рабочий проект: <название>
Процессы: <значения свойства Процесс>
Дополнительные свойства: <поле — зачем нужно>
Дополнительные этапы: <этап — зачем нужен>
Рекуррентные работы: <задача — периодичность>
Дополнительные проекты: <название — почему нужен отдельный контур>
```

Если для настройки нельзя объяснить её управленческое назначение, её лучше не добавлять.
