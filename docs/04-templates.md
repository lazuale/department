# Шаблоны

[Главная](../README.md) · [00 Возможности](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [02 Сценарии](02-scripts.md) · [03 Аналитика](03-control.md) · **04 Шаблоны** · [05 Процессы](05-processes.md) · [06 Настройка](06-workspace.md)

Шаблоны фиксируют устойчивую структуру работы, но не должны навязывать организационные правила, которых нет в конкретном процессе.

## 1. Название Task

Название должно позволять понять ожидаемый результат без открытия карточки.

Универсальная форма:

```text
<действие / результат> — <предмет / основание / период при необходимости>
```

Избегать названий без результата: `Посмотреть`, `Важно`, `Срочно`, `Письмо`, `Разобраться`.

## 2. Минимальная Task

Использовать штатные поля Odoo только по смыслу процесса:

```text
Title
Project
Assignees        [если нужны]
Deadline         [если нужен]
Stage / State
Priority         [если используется]
Properties       [если нужны]
Description
Chatter / Attachments
```

Не повторять в Description значения, которые уже хранятся структурированно.

## 3. Описание Task

Нейтральная структура:

```text
Результат:
<что должно быть получено>

Контекст / основание:
<только то, что нужно для выполнения>

Условия / ограничения:
<если есть>

Критерий завершения:
<если процесс требует формального подтверждения>
```

Не вводить обязательный блок `Критерий завершения`, если для конкретной работы достаточно очевидного результата.

## 4. Предметные ссылки

Если Task системно относится к предметному объекту, использовать relation/Property вместо текстовой копии.

Примеры:

```text
ТС           → Many2one(fleet.vehicle)
Сотрудник    → Many2one(hr.employee)
Оборудование → Many2one(maintenance.equipment)
Контрагент   → Many2one(res.partner)
```

Не переносить в Task все атрибуты target model без отдельной причины.

## 5. Несколько предметных объектов

Если один результат действительно относится к нескольким records, допустима Many2many Property.

Если результаты, сроки или исполнение различаются, разделить работу на Tasks/Subtasks.

## 6. Task Template

Task Template используется для типовой разовой работы по событию.

Шаблон может содержать:

```text
устойчивый Title pattern
Description
Tags
Properties со стабильными значениями
Subtasks, если они действительно самостоятельны
```

Не зашивать в template конкретный Vehicle/Employee/Equipment, если объект меняется при каждом использовании.

## 7. Recurring Task

Используется для календарно повторяемого результата.

```text
Title: <повторяемый результат>
Recurrence: <штатное правило Odoo>
```

Если процесс зависит от копирования Properties или Subtasks, проверить фактическое поведение на установленной сборке Odoo 19.

## 8. Activity

Activity используется для следующего действия по существующей записи.

Пример структуры:

```text
Type: <действие>
Due Date: <когда выполнить>
Assigned to: <кто выполняет Activity>
Summary: <что именно сделать>
```

Конкретный набор Activity Types определяется процессом. Не создавать универсальный обязательный список типов заранее.

## 9. Activity Plan

Activity Plan используется для устойчивого набора follow-up вокруг одной записи.

Если каждый шаг является самостоятельным результатом со своим управлением, вместо Activity Plan нужны Tasks/Subtasks.

## 10. Project Template

Используется, когда повторяется структура целого Project:

- Tasks;
- роли;
- dependencies;
- milestones;
- project-level configuration.

Project Template не является заменой Planning/capacity scheduling.

## 11. Шаблон описания процесса

```text
Название:
<процесс>

Цель / результат процесса:
<зачем он существует>

Предметные сущности:
<какие records участвуют>

Источник истины:
<где живёт каждая сущность>

Task нужна когда:
<что считается отдельным контролируемым результатом>

Task не нужна когда:
<что остаётся в предметной модели / Chatter / Activity>

Связи Task с предметом:
<Property / relation / нет>

Project boundary:
<в каком Project живёт работа и почему>

Stages:
<локальный workflow процесса>

Assignees:
<правило процесса, если оно есть>

Deadline:
<когда нужен и как определяется>

Priority:
<используется ли и что означает>

Activities:
<когда используются>

Dependencies:
<когда используется Blocked by>

Повторяемость:
<Task Template / Recurring Task / Activity Plan / Project Template / нет>

Права:
<какие действия кому разрешены, если это важно>

Контроль:
<какие вопросы должны решать views/reports>

Остаточный gap:
<что не закрывается штатной конфигурацией>
```

## 12. Локальная конфигурация пилота

```text
Projects:
<границы и причина разделения>

Stages по Project:
<список и смысл>

Properties:
<название → тип → model/domain при необходимости → зачем>

Task Templates:
<если нужны>

Recurring Tasks:
<если нужны>

Activity Types / Plans:
<если нужны>

Shared Views:
<вопрос → filter/group>

Security:
<group → права>

Подтверждённые gaps:
<факт пилота → почему штатный механизм не подходит>
```
