# Шаблоны

Шаблон нужен только там, где свободная форма регулярно создаёт путаницу.

Не нужно дублировать в названии то, что уже хранится отдельным полем OpenProject.

## 1. Название обычной работы

Формат:

```text
<действие/результат> — <основание или период>
```

Примеры:

- `Обработать основание №123`;
- `Провести сверку — 2026-08`;
- `Подготовить периодический отчёт — 2026-08`;
- `Уточнить содержание обращения — тема X`.

Плохие названия:

- `Срочно`;
- `Посмотреть`;
- `Письмо`;
- `Сделать`;
- `Важно`;
- `RE:`;
- `Работа по файлу`.

Категория и тип не повторяются в названии, если уже заданы отдельными полями.

## 2. Обычная работа

Обязательный минимум:

```text
Название:
<понятный результат>

Тип:
Работа

Категория:
<устойчивый процесс>

Исполнитель:
<человек или групповая очередь>

Срок:
<дата конечного результата>

Приоритет:
Обычный / Критичный
```

Описание заполняется только если без него нельзя понять результат или ограничения.

Допустимый короткий формат:

```text
Основание: <что запустило работу>
Нужно получить: <конечный результат>
Особые условия: <только если есть>
```

Не копировать переписку целиком.

## 3. Запрос важного документа или материала

Этот шаблон используется только для отдельного контролируемого запроса, когда подразделению самому нужен важный документ, материал или подтверждение и его получение нельзя потерять после отправки.

```text
Название:
Получить <конкретный документ/материал> — <краткая тема>

Тип:
Запрос

Категория:
<процесс, для которого нужен результат>

Исполнитель:
<кто отвечает за получение>

Срок:
<к какой дате документ/материал должен быть получен>

Описание, если нужно:
Нужно получить: <точно что требуется>
Кому направлен запрос: <обобщённо>
Для чего нужен: <кратко, если без этого непонятен приоритет>
Связано с: #<ID, если есть>
```

После отправки:

`В работе → Ожидание`.

Карточка остаётся открытой до фактического получения требуемого результата.

Отправка письма не является завершением.

Если получено не то, неполный комплект или неподходящая версия, запрос не закрывается.

## 4. Комментарий после отправки запроса документа

Минимальный формат:

```text
Запрос направлен: <дата>.
Ждём: <конкретный документ/материал>.
Адресат: <обобщённо>.
```

Повторное действие:

```text
Повторный запрос/эскалация: <дата>.
Причина: <срок прошёл / ответ неполный / документ не получен>.
```

Не создавать новую карточку на каждое повторное письмо.

## 5. Регламентная работа

```text
Название:
<результат> — <период>

Тип:
Регламент

Категория:
<процесс>

Исполнитель:
<человек или группа>

Срок:
<срок этого периода>
```

Каждый период — отдельная карточка.

## 6. Комментарий при обычном ожидании

Минимальный формат:

```text
Ожидание: <что именно ждём>.
Действие: <что сделано и когда>.
```

Если нужен дополнительный контекст:

```text
Ожидание: <результат>.
Действие: <что и когда сделано>.
После ответа: <следующий шаг>.
```

Плохие комментарии:

- `ждём`;
- `нет ответа`;
- `уточняется`;
- `в процессе`.

## 7. Передача работы

Комментарий нужен только если следующему исполнителю недостаточно самой карточки.

```text
Передача: <что уже сделано>.
Следующий шаг: <одно конкретное действие>.
Риск: <только если есть>.
```

Не переписывать всю историю карточки.

## 8. Изменение срока

Если реальный срок изменён:

```text
Срок изменён: <старая дата> → <новая дата>.
Причина: <что изменилось>.
```

Формулировка `не успеваем` сама по себе не является основанием для переноса.

Для запроса документа срок не переносится только потому, что ответа ещё нет. Если внешняя сторона действительно согласовала новый срок, это фиксируется как изменение фактических условий.

## 9. Возврат после закрытия

```text
Возврат в работу: <что в первоначальном результате неверно или не завершено>.
Нужно исправить: <конкретно>.
```

Новый дополнительный объём так не оформляется — для него создаётся новая работа.

## 10. Отмена

```text
Отменено: <почему результат больше не требуется>.
```

Не использовать одно слово `неактуально` без объяснения.

## 11. Дубликат

```text
Дубликат работы #<ID>.
Основная карточка: #<ID>.
```

Если во второй карточке есть уникальная полезная информация, сначала перенести её в основную.

## 12. Идея улучшения

```text
Название:
<проблема или улучшение>

Наблюдение:
<что регулярно происходит>

Потеря:
<время, качество, срок, ручной труд, управляемость>

Гипотеза:
<что можно изменить, если уже понятно>

Факты:
<связанные работы или показатели, если есть>

Ожидаемый эффект:
<что должно стать лучше>
```

Идея без готового решения допустима. Идея без понятной проблемы — нет.

## 13. Когда работу можно закрыть

Для каждого устойчивого процесса хранится короткое правило:

```text
Работа считается готовой, если:
- <конечный результат достигнут>;
- <результат сохранён или передан, если это обязательно>;
- открытых обязательных действий больше нет.
```

Не превращать это правило в длинный чек-лист, если процесс этого не требует.

Для типа `Запрос` правило отдельное:

```text
Запрос считается готовым, если:
- требуемый документ/материал фактически получен;
- он соответствует запросу;
- при необходимости сохранён или привязан к связанной работе;
- сопровождение самого запроса больше не требуется.
```

## 14. Карточка реального бизнес-процесса

```text
Название процесса:
<устойчивое название>

Категория:
<значение в OpenProject>

Что запускает:
<триггер>

Что является одной работой:
<единица результата>

Когда можно закрыть:
<конечный результат>

Кто обычно выполняет:
<роль или группа>

Как определяется срок:
<правило>

Когда делить на несколько работ:
<критерий>

Типовые ожидания:
<только реальные повторяющиеся причины>
```

Этого достаточно для описания процесса. Дополнительные поля добавляются только при реальной необходимости.
