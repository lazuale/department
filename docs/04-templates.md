Шаблоны не должны превращать Task в анкету или копию справочника.

Правило:

> В описании задачи хранится только контекст результата. Структурированные данные по сотруднику, ТС, оборудованию и внешнему субъекту должны жить в штатных сущностях Odoo.

## 1. Название задачи

```text
<что должно быть получено> — <объект / основание / период>
```

Примеры:

- `Провести сверку топлива — июль 2026`;
- `Исправить данные по ТС 123 — основание №45`;
- `Получить подтверждение корректировки — объект X`;
- `Обновить правило обработки расхождений`.

Не использовать:

```text
Срочно
Посмотреть
Письмо
Важно
RE:
Разобраться
```

без понятного результата.

## 2. Обычная Project Task

Штатные поля:

```text
Название: <результат>
Assignee: <один владелец результата, если назначен>
Deadline: <срок результата>
Priority: <базовый / Urgent, если реально критично>
Stage: <фактическое положение в потоке>
Вид работы: Работа
Процесс: <если этот разрез используется>
Allocated Time: <только если оцениваем трудоёмкость>
```

Описание:

```text
Основание:
<что запустило работу>

Результат:
<что должно быть получено>

Условия:
<только существенные ограничения>
```

Не повторять в описании Assignee, Deadline, Priority, Stage и другие штатные поля.

## 3. Ссылка на предметный объект

### ТС

Источник карточки ТС — Fleet.

Пока штатного Task → Fleet Vehicle поля нет, не создавать огромный Selection Property.

Если объект нужен только для понимания единичной задачи, он может быть явно назван в Title/Description. Если нужен системный анализ тысяч задач по ТС — это уже подтверждённое требование к связанной модели.

### Сотрудник

Источник карточки — Employees.

Не назначать человека Assignee, если он не является владельцем результата и нужен только как предмет проверки.

### Оборудование

Источник — Maintenance Equipment.

Само обслуживание оформляется Maintenance Request, а не дублирующей Project Task.

### Внешний субъект

Источник — Contacts.

Не создавать отдельную текстовую карточку организации внутри каждой задачи.

## 4. Запрос

```text
Название: Получить <что> — <тема>
Вид работы: Запрос
Assignee: <владелец результата>
Deadline: <когда результат должен быть получен>
Процесс: <если используется>
```

Описание:

```text
Нужно получить:
<конкретный результат>

Основание:
<если неочевидно>
```

После отправки:

```text
Stage = Ожидание внешнего
Activity = следующее действие / контроль
```

## 5. Внешнее ожидание

В Chatter при необходимости:

```text
Сделано: <что и когда>.
Ждём: <какое внешнее действие>.
```

Activity:

```text
Тип: <проверить / напомнить / позвонить / эскалировать>
Due Date: <дата контроля>
Assigned to: <кто выполняет follow-up>
Summary: <что проверить>
```

Не создавать отдельное поле `Ждём`, если факта в Chatter + Activity достаточно.

## 6. Улучшение процесса

После решения `делаем`:

```text
Название: <конкретное изменение>
Вид работы: Улучшение
Assignee: <владелец>
Deadline: <дата результата>
Процесс: <если используется>
```

Описание:

```text
Проблема:
<что повторяется / теряется / мешает>

Факты:
<задачи, показатели, примеры>

Изменение:
<что именно внедрить>

Проверка эффекта:
<по чему поймём, что стало лучше>
```

До решения `делаем` идея может жить в To-Do/Discuss.

## 7. Subtask

Subtask оформляется как самостоятельный контролируемый результат внутри родительской задачи.

Минимум:

```text
Title: <результат части>
Assignee: <если отличается / нужен отдельный владелец>
Deadline: <если нужен отдельный срок>
```

Не использовать Subtasks как механический чек-лист каждого действия.

## 8. Activity Type

Для устойчивого следующего действия:

```text
Название: Проверить ответ
Action: <штатное действие>
Default User: <если однозначно>
Default Summary: <при необходимости>
Schedule: <через N дней/недель/месяцев>
Chaining Type: <Suggest / Trigger, если нужна цепочка>
Next Activity: <если есть>
```

Сначала пробовать Activity chaining, только потом Automation Rule.

## 9. Activity Plan

Использовать только для повторяемого набора follow-up действий.

```text
Plan: Контроль внешнего запроса

1. Проверить получение
2. Проверить ответ
3. Напомнить
4. Эскалировать
```

Если пункты являются самостоятельными результатами — это Tasks/Subtasks, не Activity Plan.

## 10. Описание процесса

```text
Название: <процесс>

Предметные сущности:
<Employees / Contacts / Fleet / Maintenance / Project / другое>

Источник истины по справочникам:
<где хранится каждый значимый объект>

Вход:
<что запускает процесс>

Результат:
<что должно быть получено>

Единица Task:
<когда создаётся одна Project Task>

Когда Task не нужна:
<какие события являются только изменением справочника / сообщением / встречей>

Исполнители:
<роль / рабочая группа>

Deadline:
<правило конечного срока>

Внешнее ожидание:
<типовые причины + правило Activity>

Внутренние зависимости:
<когда использовать Blocked by>

Периодичность:
<Recurring Task / Project Template / нет>

Контроль:
<какие Shared Views / показатели используются>

Click-only gaps:
<какой связи/поля реально не хватает>
```

## 11. Локальные настройки пилота

```text
Операционный Project: <название>

Stages:
<список>

Properties:
<поле — зачем нужно>

Tags:
<метка — зачем нужна>

Shared Favorites:
<название — фильтр — кому доступен>

Shared Top Bar Views:
<название — управленческий вопрос>

Activity Types:
<тип — назначение>

Activity Plans:
<план — зачем нужен>

Recurring Tasks:
<задача — периодичность>

Предметные модули:
Employees: <используется / нет>
Contacts: <используется / нет>
Fleet: <используется / нет>
Maintenance: <используется / нет>
Calendar: <используется / нет>
Timesheets: <используется / нет и зачем>

Подтверждённые gaps:
<ограничение — почему нельзя решить штатно>
```

Если для настройки нельзя объяснить её управленческое назначение, её не добавляем.
