# Контроль, метрики и управленческие обзоры

## 1. Назначение контроля

Контроль используется не для постоянного ручного надзора за каждым действием, а для раннего обнаружения отклонений потока.

Контроль должен отвечать на вопросы:

- не потеряна ли работа;
- не копится ли очередь быстрее, чем закрывается;
- не зависли ли работы во внешнем ожидании;
- не скрыта ли перегрузка за статусом `В работе`;
- не нарушены ли сроки;
- не повторяются ли одни и те же ошибки;
- не создаёт ли процесс лишний ручной труд.

## 2. Минимальный набор метрик

### 2.1. Входящий поток

**Поступило за период** — количество новых обязательных Work Package, созданных за период.

Используется для оценки фактического входа и сезонности.

### 2.2. Throughput

**Завершено за период** — количество Work Package, переведённых в `Готово` за период.

Сам по себе показатель не используется для сравнения производительности сотрудников.

### 2.3. Остаток очереди

Количество открытых Work Package в `Очередь`.

Рост остатка при стабильном входе — сигнал недостаточной пропускной способности или неверной приоритизации.

### 2.4. WIP

Количество Work Package в `В работе`.

Аномально высокий WIP означает, что статус перестал отражать фактическую активность либо поток чрезмерно распараллелен.

### 2.5. Ожидание

Количество Work Package в `Ожидание`.

Дополнительно контролируется возраст ожидания.

### 2.6. Просрочка

Количество незавершённых Work Package, у которых Finish date меньше текущей даты.

Просрочка анализируется по Category и владельцу, но не используется как автоматический вывод о качестве конкретного сотрудника без разбора причин.

### 2.7. Возраст незавершённой работы

Минимально контролируются:

- самая старая Work Package в `Очередь`;
- самая старая Work Package в `Ожидание`;
- старые Work Package по основным Category.

### 2.8. Reopen

Количество Work Package, возвращённых из `Готово` в `В работе` из-за ошибки первоначального выполнения.

Новый объём после корректного завершения не относится к reopen.

### 2.9. Дубликаты

Количество обнаруженных дубликатов используется как показатель качества регистрации и входящего разбора.

### 2.10. Без владельца

Количество обязательных Work Package без Assignee или группового владельца.

Критичная работа без владельца считается управленческим исключением.

## 3. Что нельзя считать KPI производительности

Запрещено использовать без дополнительного контекста:

- число закрытых Work Package на сотрудника;
- число комментариев;
- число переводов статуса;
- время присутствия в системе;
- количество созданных карточек.

Причина: разные Category и Work Package могут иметь несопоставимую трудоёмкость и внешние зависимости.

Показатели по сотрудникам используются для поиска перегруза, аномалий и потребности в перераспределении, но не как примитивный рейтинг.

## 4. Управленческие представления

Должны существовать как минимум следующие сохранённые представления:

1. `Моя работа`;
2. `Вся активная работа`;
3. `Очередь`;
4. `В работе`;
5. `Ожидание`;
6. `Просрочено`;
7. `Без исполнителя`;
8. `Критичные`;
9. `Старые в очереди`;
10. `Старые в ожидании`;
11. `По Category`;
12. `По Assignee`;
13. `Готово за период`.

## 5. Канбан-доска

Основная доска обязательной работы:

`Очередь | В работе | Ожидание | Готово`

`Отменено` не является рабочей колонкой ежедневного управления и может быть скрыто из основной доски.

Доска используется для визуального состояния потока, но не заменяет табличные представления просрочки, старения и сроков.

## 6. Ежедневный обзор исключений

Разбираются только отклонения:

1. критичные работы;
2. просроченные;
3. работа без владельца;
4. старые в очереди;
5. старые в ожидании;
6. аномальный WIP;
7. срочные конфликты приоритетов.

Для каждой проблемы должно быть принято действие либо подтверждено отсутствие необходимости вмешательства.

## 7. Еженедельный обзор потока

Сравниваются:

- поступило за неделю;
- завершено за неделю;
- изменение остатка очереди;
- изменение ожидания;
- просрочка;
- reopen;
- дубликаты;
- распределение по Category;
- системные причины задержек.

Главный вопрос недели: **где поток стал хуже и почему**.

## 8. Ежемесячный обзор процессов

Рассматриваются не отдельные карточки, а устойчивые закономерности:

- какие Category создают основной объём;
- где очередь растёт системно;
- где ожидание является нормой, а не исключением;
- где много reopen;
- где регулярно создаются дубли;
- какие ручные действия повторяются;
- какие идеи улучшений подтверждены фактами.

Результатом обзора могут быть:

- изменение Definition of Done;
- корректировка внутреннего срока;
- изменение правил разбиения Work Package;
- изменение приоритизации;
- идея улучшения;
- обязательная работа по устранению причины;
- проект автоматизации.

## 9. Контроль качества

### Выборочная проверка

Назначение — получить представление о качестве обычного потока.

Выборка не должна состоять только из подозрительных случаев.

### Риск-контроль

Назначение — предотвратить последствия по конкретным критичным или необычным работам.

Результаты риск-контроля не интерпретируются как общая доля ошибок.

### Результат ошибки

Если первоначальный результат неверен — Work Package переоткрывается.

## 10. Контроль входа

Рабочая система не может контролировать то, что в неё не попало.

Поэтому отдельно проверяется качество входящего разбора:

- остались ли сообщения с неопределённой судьбой;
- создаются ли дубли по одной теме;
- создаются ли Work Package на информационные сообщения;
- не остаются ли обязательные действия только в переписке.

Полнота входа является первичной метрикой над всеми остальными.

## 11. Контроль регламентных работ

Регламентный контур проверяется на горизонт планирования.

Для каждого установленного регламента должны существовать будущие экземпляры Work Package на принятый период планирования.

Отсутствие будущего экземпляра считается риском потери работы до наступления срока.

## 12. Контроль backlog развития

Backlog не должен превращаться в архив пожеланий.

Периодически проверяется:

- есть ли дублирующие идеи;
- подтверждена ли проблема фактами;
- остаётся ли инициатива актуальной;
- не разросся ли `Готово к реализации` сверх реальной ёмкости;
- существует ли ожидаемый эффект.

Неактуальные идеи закрываются или архивируются, а не хранятся бессрочно в активном backlog.

## 13. Принцип управленческого решения

Любой показатель является поводом задать вопрос, а не автоматическим диагнозом.

Например:

- рост `Ожидание` может означать внешнюю зависимость, а не низкую производительность;
- рост WIP может означать неверное использование статуса;
- рост reopen может быть связан с изменившимся входом или сложностью процесса;
- большое число завершённых Work Package может быть следствием чрезмерного дробления.

Контроль должен улучшать систему, а не стимулировать манипуляцию метриками.
