Этот файл описывает, какая модель должна получиться в системе. Техническая матрица прав пользователей сюда не входит.

## 1. Постоянные проекты

```text
Работа подразделения
Развитие и автоматизация
```

В `Работа подразделения`:

- `Работа`;
- `Запрос`;
- `Регламент`;
- разовые поручения.

Отдельный проект — только когда одной карточки или иерархии недостаточно.

## 2. Типы

| Тип | Для чего |
|---|---|
| `Работа` | обычный обязательный результат |
| `Запрос` | отдельно контролировать получение документа/материала по критериям основного регламента |
| `Регламент` | периодическая работа |
| `Идея` | улучшение в отдельном проекте развития |

Тип не заменяет категорию: тип описывает характер карточки, категория — бизнес-процесс.

## 3. Состояния

```text
Очередь
В работе
Ожидание
Готово
Отменено
```

Основной путь:

```text
Очередь → В работе → Готово
              ↕
          Ожидание
```

Для `Запроса`:

```text
Очередь → В работе → Ожидание → В работе → Готово
```

`Ожидание → Готово` не используется.

## 4. Приоритет

Использовать только:

- `Обычный`;
- `Критичный`.

Порядок внутри каждого уровня: ближайший срок → более старая карточка.

Критичность определяется по разделу 7 [основного регламента](01-methodology.md#7-порядок-очереди-и-критичность).

## 5. Категории

Категория = устойчивый бизнес-процесс.

Не использовать категории для:

- статуса;
- срочности;
- сотрудника;
- отдельного документа;
- временной темы.

Каждой категории должна соответствовать карточка процесса.

## 6. Исполнитель и групповая очередь

Открытая карточка имеет конкретного исполнителя или контролируемую группу.

Из групповой очереди сотрудник назначает себя только при фактическом начале.

Передачу уже назначенной карточки делает старший.

Для `Запроса` после отправки обязательно остаётся конкретный владелец.

## 7. Поля карточки

Минимум:

- название;
- тип;
- категория;
- состояние;
- исполнитель или группа;
- срок;
- приоритет;
- описание и вложения — при необходимости.

После создания параметры меняются по правилам [основного регламента](01-methodology.md#4-параметры-карточки).

## 8. Доска

```text
Очередь | В работе | Ожидание | Готово
```

`Отменено` можно скрыть из ежедневной доски.

## 9. Списки исполнителя

`Моя работа`:

- только открытые;
- исполнитель = текущий пользователь или его группа;
- колонки: ID, название, тип, категория, состояние, приоритет, срок.

Сортировка:

1. критичные — ближайший срок → старые;
2. обычные — ближайший срок → старые.

`Запросы — ожидаем`:

- тип = `Запрос`;
- состояние = `Ожидание`;
- исполнитель = текущий пользователь;
- ближайшие сроки сверху.

## 10. Контрольные списки

- `Вся активная работа`;
- `Просрочено`;
- `Без исполнителя`;
- `Критичные`;
- `Старые в очереди`;
- `Старые в ожидании`;
- `Запросы — ожидаем`;
- `Запросы — просрочено`;
- `По категориям`;
- `По исполнителям`;
- `Готово за период`.

Неиспользуемые списки удаляются.

## 11. Регламенты

Каждый период — отдельная карточка типа `Регламент`.

Будущие карточки создаются на горизонт, установленный для процесса.

## 12. Родительские, дочерние и связанные карточки

Дочерние карточки — только для независимо контролируемых частей.

Связи используются для:

- нового объёма после предыдущей работы;
- запроса документа, связанного с другой работой;
- идеи и её реализации;
- дубликатов.

Закрытие дочерних карточек не закрывает родительскую автоматически.

## 13. Развитие и автоматизация

```text
Входящие идеи → Наблюдаем → Кандидат → Готово к решению
```

После решения `делаем` создаётся обязательная работа: одна карточка, иерархия или отдельный проект.

## 14. Разграничение действий

- автор задаёт параметры при создании;
- исполнитель ведёт состояние;
- старший исправляет параметры по основанию;
- руководитель принимает управленческие решения;
- старший не согласует обычное закрытие.

## 15. Антипримеры настройки

Не настраивать так:

| Плохая настройка | Почему ломает регламент |
|---|---|
| все назначенные карточки сразу `В работе` | нельзя увидеть реальное выполнение |
| `Ожидание` используется как «сделаю позже» | внешняя блокировка смешивается с очередью |
| категория = сотрудник / срочность / документ | процессная аналитика становится мусорной |
| отдельный `Запрос` на каждое письмо | один результат распадается на переписку |
| срок используется как напоминание | исчезает дата обязательного результата |
| много статусов под каждую мелочь | состояние перестаёт читаться одинаково |
| отдельный проект на каждую функцию | единый операционный поток дробится без необходимости |
| обязательное согласование старшим перед каждым закрытием | старший превращается в узкое место |

## 16. Проверка готовности к запуску

Контур готов к эксплуатации, если выполнено всё:

- [ ] созданы основные проекты;
- [ ] настроены типы `Работа`, `Запрос`, `Регламент`, `Идея`;
- [ ] настроены пять состояний и разрешённые переходы;
- [ ] используются только `Обычный` и `Критичный`;
- [ ] создан короткий список категорий реальных процессов;
- [ ] для каждой категории есть карточка процесса;
- [ ] рабочие группы и владельцы определены;
- [ ] настроены `Моя работа` и контрольные списки;
- [ ] определены локальные внутренние сроки, где нет внешних;
- [ ] для периодических процессов определён горизонт будущих карточек;
- [ ] определено контрольное время разбора входящих, если оно используется;
- [ ] определена периодичность выборочного контроля качества, если он применяется;
- [ ] протестированы обычная работа, `Ожидание`, `Запрос`, передача, возврат после ошибки и регламентная работа;
- [ ] новый сотрудник по документации может определить тип, категорию, состояние, срок и следующий шаг без устного пояснения.

Если любой из обязательных пунктов не выполнен, контур считается не полностью подготовленным.

## 17. Не добавлять без необходимости

- новые статусы;
- новые типы;
- десятки категорий;
- обязательные согласования;
- отдельный проект на каждую функцию;
- отдельный отчёт поверх данных OpenProject;
- обязательные поля без применения;
- `Запрос` на каждое уточняющее письмо.
