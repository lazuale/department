# Рабочий контур в OpenProject Community

Этот документ описывает, **какая модель должна получиться в системе**. Он не заменяет техническую инструкцию администратора и не задаёт конкретную матрицу прав.

Конфигурация должна быть проще методики, а не сложнее её.

## 1. Постоянные проекты

На старте достаточно двух:

```text
Работа подразделения
Развитие и автоматизация
```

В `Работа подразделения` ведутся:

- обычные обязательные работы;
- запросы важных документов и материалов;
- регламентные работы;
- разовые поручения.

Отдельный проект создаётся только для настоящей проектной работы, когда одной карточки или простой иерархии работ недостаточно.

## 2. Типы работ

В основном рабочем проекте:

| Тип | Когда использовать |
|---|---|
| `Работа` | обычный обязательный результат |
| `Запрос` | нужно по нашей инициативе получить важный документ, материал или подтверждение и довести получение до результата |
| `Регламент` | работа возникает по календарю или установленной периодичности |

В проекте развития используется тип `Идея`.

`Запрос` не используется для обычной переписки и уточнений внутри уже открытой работы.

## 3. Состояния

Единый набор обязательной работы:

1. `Очередь`;
2. `В работе`;
3. `Ожидание`;
4. `Готово`;
5. `Отменено`.

`Готово` и `Отменено` — закрытые состояния.

Дополнительные статусы не вводятся без изменения методики.

## 4. Переходы

Обычный жизненный цикл:

```text
Очередь → В работе → Готово
              ↓
          Ожидание
              ↓
       В работе / Очередь
```

Для `Запроса` нормальный путь:

```text
Очередь → В работе → Ожидание → В работе → Готово
```

Прямое `Ожидание → Готово` не используется.

Возврат `Готово → В работе` нужен только для исправления ошибки первоначального результата.

## 5. Приоритет

Методика использует два смысловых уровня:

- `Обычный`;
- `Критичный`.

`Критичный` должен реально менять порядок очереди, а не просто означать «важно».

Внутри критичных и обычных работ порядок одинаковый: ближайший срок, затем более старая карточка.

Сам тип `Запрос` не делает карточку критичной автоматически.

## 6. Категории

Категория отвечает только на вопрос: **какой устойчивый бизнес-процесс породил работу**.

Правила:

- список короткий и стабильный;
- не кодировать срочность, статус, сотрудника или временную тему;
- не создавать новую категорию под конкретный документ;
- каждой категории соответствует одно понятное описание процесса.

Обычные работы, запросы и регламенты находятся в одном постоянном проекте, поэтому один и тот же справочник процессов не приходится дублировать.

## 7. Владелец и групповая очередь

Открытая карточка должна иметь:

- конкретного исполнителя; или
- контролируемую рабочую группу.

Если работа лежит в групповой очереди, сотрудник назначает себя исполнителем только в момент фактического взятия.

Если уже назначенную конкретному человеку работу нужно передать другому, действует порядок корректировки параметров через старшего.

Для `Запроса` групповая очередь допустима только до фактического взятия на подготовку. После отправки сохраняется конкретный владелец сопровождения.

Карточка без владельца — только временное исключение и должна попадать в отдельный контрольный список.

## 8. Минимум полей

Для обязательной работы достаточно:

- название;
- тип;
- категория;
- состояние;
- исполнитель или группа;
- срок;
- приоритет;
- описание и вложения только по необходимости.

При создании автор задаёт известные параметры. Если внешнего срока нет, используется внутренний срок процесса по правилам методики. После регистрации параметры считаются исходной постановкой и изменяются только по установленному порядку.

Для `Запроса` смысл фиксирован:

- название — что нужно получить;
- исполнитель — кто отвечает за получение;
- срок — когда результат должен быть получен;
- `Ожидание` — запрос отправлен и сейчас требуется внешнее действие.

## 9. Основная доска

```text
Очередь | В работе | Ожидание | Готово
```

`Отменено` не обязательно показывать в ежедневной доске.

Доска показывает текущее состояние, но не заменяет списки со сроками и старением.

## 10. Рабочий список исполнителя

Основной список `Моя работа`:

- только открытые карточки;
- назначенные текущему пользователю или его рабочей группе;
- колонки: ID, название, тип, категория, состояние, приоритет, срок.

Порядок чтения:

1. критичные — ближайший срок, затем старые;
2. обычные — ближайший срок, затем старые.

Для сопровождающих запросы нужен отдельный список:

### `Запросы — ожидаем`

- тип = `Запрос`;
- состояние = `Ожидание`;
- исполнитель = текущий пользователь;
- ближайшие сроки сверху.

После отправки запрос не должен оставаться только на рабочей группе.

## 11. Контрольные списки

Минимально нужны:

- `Вся активная работа`;
- `Просрочено`;
- `Без исполнителя`;
- `Критичные`;
- `Старые в очереди`;
- `Старые в ожидании`;
- `Запросы — ожидаем`;
- `Запросы — просрочено`;
- `По категориям`;
- `По исполнителям`;
- `Готово за период`.

Неиспользуемые и дублирующие списки удаляются.

## 12. Регламентные работы

Каждый период — отдельная карточка типа `Регламент` с периодом в названии и собственным сроком.

Будущие экземпляры создаются заранее на горизонт, установленный для процесса.

## 13. Родительские, дочерние и связанные работы

Родительская и дочерние карточки используются, когда одна крупная работа состоит из независимо контролируемых результатов.

Технические шаги одного человека дочерними карточками не становятся.

Связи используются для:

- нового объёма после предыдущей работы;
- запроса документа, связанного с другой работой;
- идеи, подтверждённой рабочими случаями;
- дубликатов.

Получение документа закрывает `Запрос`, но не закрывает автоматически связанную работу.

## 14. Развитие и автоматизация

Идеи находятся отдельно от обязательного потока.

Достаточно четырёх стадий:

```text
Входящие идеи → Наблюдаем → Кандидат → Готово к решению
```

После решения `делаем` создаётся обязательная работа, а дальше её масштаб определяется обычным правилом: одна карточка, иерархия работ или отдельный проект.

Список идей не используется как вторая обязательная очередь.

## 15. Разграничение действий

Техническая реализация прав пользователей может отличаться, но итоговое поведение должно соответствовать регламенту:

- автор задаёт параметры при создании;
- исполнитель ведёт фактическое состояние работы;
- исполнитель может взять карточку на себя из контролируемой групповой очереди;
- корректировку уже зафиксированных параметров выполняет старший по основанию;
- управленческое решение принимает руководитель;
- старший не становится обязательным согласующим перед закрытием.

## 16. Что не включать без необходимости

Не нужны заранее:

- дополнительные статусы;
- десятки категорий;
- сложная иерархия постоянных проектов;
- отдельный проект на каждую функцию;
- обязательное согласование обычной работы;
- сложная оценка трудоёмкости каждой мелкой карточки;
- отдельный отчёт поверх данных, уже видимых в системе;
- обязательные поля без управленческого применения;
- отдельный `Запрос` на каждое уточняющее письмо.

## 17. Порядок запуска

1. Создать основной рабочий проект и проект развития.
2. Настроить типы и пять состояний.
3. Настроить разрешённые переходы.
4. Создать короткий список категорий реальных процессов.
5. Создать рабочие группы.
6. Создать основную доску и минимальные контрольные списки.
7. Описать конечный результат, правило срока и при необходимости горизонт регламентных работ для каждой основной категории.
8. Проверить модель на нескольких реальных работах, запросах и регламентах.
9. Добавлять новое только после подтверждённой необходимости.

Конфигурация считается хорошей, если сотрудник поддерживает достоверное состояние работы несколькими очевидными действиями, а обязательная работа и отправленный запрос не могут исчезнуть из контроля.
