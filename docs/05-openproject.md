# Настройка OpenProject Community

Конфигурация должна быть проще методики, а не сложнее её.

## 1. Структура проектов

На старте достаточно двух постоянных проектов:

```text
Работа подразделения
Развитие и автоматизация
```

В `Работа подразделения` ведутся:

- входящие обязательные работы;
- запросы важных документов и материалов, получение которых подразделение обязано довести до результата;
- регламентные работы;
- разовые поручения.

Отдельный Project создаётся только для настоящей проектной работы с несколькими результатами, участниками, этапами и зависимостями.

Такой подход сохраняет единый список категорий процессов и не заставляет дублировать одинаковую классификацию между несколькими постоянными проектами.

## 2. Типы работ

В основном рабочем проекте:

| Тип | Когда использовать |
|---|---|
| `Работа` | обычный обязательный результат |
| `Запрос` | по нашей инициативе нужно получить важный документ, материал или подтверждение и нельзя потерять контроль после отправки |
| `Регламент` | работа, которая возникает по календарю или периодичности |

В проекте развития используется тип `Идея`.

`Запрос` не используется для обычной переписки, уточнений и мелких недостающих материалов внутри уже открытой работы.

Новый тип создаётся только если у объекта действительно другой смысл или lifecycle.

## 3. Статусы

Единый набор обязательной работы:

1. `Очередь`;
2. `В работе`;
3. `Ожидание`;
4. `Готово`;
5. `Отменено`.

`Готово` и `Отменено` — закрытые состояния.

Дополнительные статусы без изменения методики не добавляются.

## 4. Workflow

Основные переходы исполнителя:

- `Очередь → В работе`;
- `В работе → Ожидание`;
- `В работе → Готово`;
- `Ожидание → В работе`;
- `Ожидание → Очередь`.

Для типа `Запрос` нормальный путь после отправки:

`Очередь → В работе → Ожидание → В работе/Готово`.

`Готово` для `Запроса` означает фактическое получение требуемого документа или материала, а не отправку письма.

Право отмены, изменения чужого исполнителя и спорного reopen можно оставить руководящей роли.

Возврат `Готово → В работе` должен быть доступен тем ролям, которые реально исправляют ошибки после закрытия.

## 5. Приоритет

Методика использует только два смысловых уровня:

- `Обычный`;
- `Критичный`.

Если в интерфейсе остаются дополнительные стандартные уровни, в рабочем порядке они не используются без отдельного решения.

`Критичный` означает реальное изменение порядка очереди, а не просто «важно».

Сам факт, что карточка имеет тип `Запрос`, не делает её автоматически критичной. Срочность определяется реальным последствием задержки.

## 6. Категории

Категория отвечает только на вопрос: **какой устойчивый бизнес-процесс породил работу**.

Принципы:

- список короткий и стабильный;
- не кодировать в категории срочность, статус, сотрудника, отдельный документ или временную кампанию;
- разовая тема не становится новой категорией;
- каждой рабочей категории соответствует одно понятное описание процесса.

Так как основная обязательная работа находится в одном постоянном проекте, справочник категорий не приходится дублировать между операционкой и регламентами.

## 7. Исполнитель и групповая очередь

Открытая работа должна иметь:

- конкретного исполнителя; или
- понятную рабочую группу, из которой работу забирают по pull-модели.

Для типа `Запрос` после фактической отправки должен сохраняться **конкретный владелец сопровождения**. Запрос не должен становиться безличным только потому, что сейчас ожидается внешняя сторона.

Карточки без владельца допускаются только как краткое исключение и должны попадать в отдельное представление `Без исполнителя`.

## 8. Минимум полей в карточке

Для обычной обязательной работы достаточно:

- название;
- тип;
- категория;
- статус;
- исполнитель или группа;
- срок;
- приоритет;
- описание и вложения только по необходимости.

Для типа `Запрос` смысл этих полей фиксирован:

- название — что именно нужно получить;
- исполнитель — кто отвечает за доведение до получения;
- срок — когда результат должен быть получен;
- `Ожидание` — запрос уже направлен и сейчас требуется внешнее действие.

Не добавлять поля только потому, что их можно добавить.

## 9. Основная доска

Рабочая доска по статусам:

```text
Очередь | В работе | Ожидание | Готово
```

`Отменено` можно не показывать в ежедневной доске.

Доска показывает текущее состояние, но не заменяет таблицы со сроками и старением.

## 10. Представления исполнителя

Главное представление `Моя работа`:

- только открытые карточки;
- исполнитель = текущий пользователь или его рабочая группа;
- колонки: ID, название, тип, категория, статус, приоритет, срок.

Порядок чтения должен поддерживать методику: сначала критичные, затем ближайший срок, затем старые.

Для сотрудников, сопровождающих запросы документов, дополнительно требуется одно представление:

### `Запросы — ожидаем`

Фильтры:

- тип = `Запрос`;
- статус = `Ожидание`;
- исполнитель = текущий пользователь или его группа.

Сортировка:

1. срок;
2. дата создания/возраст.

Его задача одна: не дать отправленному запросу исчезнуть из внимания.

## 11. Представления руководителя

Нужны:

- `Вся активная работа`;
- `Просрочено`;
- `Без исполнителя`;
- `Критичные`;
- `Старые в очереди`;
- `Старые в ожидании`;
- `Запросы — ожидаем`;
- `Запросы — просрочено`;
- `По категориям`;
- `По исполнителям`;
- `Готово за период`.

### `Запросы — просрочено`

Фильтры:

- тип = `Запрос`;
- состояние открыто;
- срок раньше текущей даты.

Просроченный запрос должен требовать решения: повторного контакта, эскалации, подтверждения нового реального срока либо отмены потребности.

Если представление перестало использоваться, его удаляют, а не оставляют «на всякий случай».

## 12. Регламентные работы

Тип `Регламент` живёт в основном проекте.

Каждый период — отдельная карточка с периодом в названии и собственным сроком.

Будущие экземпляры создаются или дублируются заранее на принятый горизонт планирования.

## 13. Parent/child и связи

Parent/child используется только для составной работы с независимыми результатами.

Обычные технические шаги одного исполнителя дочерними карточками не становятся.

Связи используются для:

- нового объёма после предыдущей работы;
- запроса важного документа, который нужен для другой рабочей карточки;
- идеи, подтверждённой несколькими рабочими случаями;
- дубликатов.

Получение документа закрывает карточку `Запрос`, но не закрывает автоматически связанную работу, если по ней ещё требуется обработка.

## 14. Развитие и автоматизация

Идеи находятся отдельно от обязательной работы.

Достаточно четырёх стадий:

```text
Inbox → Наблюдаем → Кандидат → Готово к решению
```

После решения «делаем» создаётся обязательная работа или отдельный Project.

Backlog не используется как ещё одна обязательная очередь.

## 15. Роли и права

### Исполнитель

Нужно право:

- видеть рабочий контур;
- создавать работу там, где это предусмотрено;
- редактировать доступные карточки;
- менять статус по разрешённому workflow;
- комментировать и прикладывать материалы;
- назначать работу на себя при pull-модели.

### Руководящая роль

Дополнительно:

- перераспределение работы;
- изменение приоритета;
- изменение срока;
- отмена;
- reopen;
- управление рабочими представлениями и досками.

### Администратор

Технически управляет типами, статусами, workflow, ролями, проектами и системной конфигурацией.

Администратор не является отдельной ступенью бизнес-процесса.

Удаление рабочих карточек не является обычным правом исполнителя.

## 16. Что не включать на старте

Без доказанной необходимости не нужны:

- дополнительные статусы;
- десятки категорий;
- сложная иерархия постоянных проектов;
- отдельный проект на каждую функцию;
- обязательное согласование обычной рутины;
- сложная оценка трудоёмкости каждой мелкой работы;
- отдельный отчёт поверх данных, которые уже видны в OpenProject;
- обязательные поля без управленческого применения;
- отдельная карточка `Запрос` на каждое уточняющее письмо.

## 17. Порядок запуска

1. Создать основной рабочий проект и проект развития.
2. Настроить типы и пять статусов.
3. Настроить workflow.
4. Создать короткий список категорий реальных процессов.
5. Создать рабочие группы.
6. Создать доску и минимальные представления, включая два контрольных списка запросов.
7. Описать, когда можно закрывать каждую основную категорию и тип `Запрос`.
8. Загрузить несколько реальных работ и запросов документов и проверить процесс на практике.
9. Только после пилота добавлять то, чего действительно не хватает.

Конфигурация считается хорошей, если сотрудник может поддерживать достоверное состояние работы несколькими очевидными действиями, а отправленный запрос важного документа физически не может исчезнуть из контрольных представлений.
