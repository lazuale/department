## 1. Что такое Процесс

Процесс — устойчивый рабочий поток, который регулярно создаёт Задачи.

В Odoo Процесс **не равен Проекту**. Постоянная операционная работа остаётся в одном рабочем Проекте, а Процесс используется как классификационный и аналитический признак Задачи.

## 2. Карточка Процесса

```text
Название: <процесс>
Назначение: <зачем существует>
Вход: <что запускает работу>
Результат: <что должно быть получено>
Одна Задача: <что считается одним самостоятельно контролируемым результатом>
Кто обычно выполняет: <роль / группа>
Крайний срок: <внешнее правило или внутренний ориентир, если есть>
Допустимые Виды работы: <поднабор из общего ядра>
Типовые блокировки: <что обычно мешает>
Связанные объекты: <что полезно связывать структурированно>
Периодика: <если есть>
Веха: <если несколько Задач имеют общую контрольную точку>
Готово: <критерий завершения>
Когда делить: <когда нужна отдельная Задача или Подзадача>
```

Не все строки обязаны быть заполнены. Карточка нужна, чтобы одинаково понимать рабочую единицу и результат, а не для создания регламента ради регламента.

## 3. Процесс и Вид работы

Они отвечают на разные вопросы:

- **Процесс** — где возникла Задача;
- **Вид работы** — какой характер имеет конечный результат `Работы`.

Общее ядро Видов работы:

`Внесение` · `Проверка` · `Сверка` · `Исправление` · `Мониторинг` · `Анализ` · `Подготовка`

Для каждого Процесса можно зафиксировать типичный или допустимый набор Видов работы. На старте это методическое правило, а не обязательная программная матрица.

Жёсткое ограничение `Процесс × Вид работы` имеет смысл только если пилот показывает системные ошибки выбора и из-за них портится аналитика.

## 4. Что Процесс должен определять

Описание должно помогать понять:

- что считается одной Задачей;
- какой результат считается завершением;
- какой Крайний срок ожидается;
- какие Виды работы для него типичны;
- какие блокировки повторяются;
- какие связанные объекты действительно нужны;
- есть ли стабильная периодика;
- нужна ли общая Веха;
- требуется ли отдельная проверка результата через `Требуются изменения / Одобрено`.

Не нужно превращать описание Процесса в анкету из десятков полей.

## 5. Связанные объекты

Если Процесс регулярно работает с конкретными сущностями, имеет смысл связывать Задачу с ними структурированно.

Приоритет штатных вариантов:

- внутренний сотрудник → **Сотрудники**;
- внешнее лицо или организация → **Контакты**;
- физическое оборудование → **Обслуживание**, если семантика подходит;
- небольшой стабильный перечень вроде участков → Свойство типа `Выбор`;
- другой объект → сначала проверить Свойство или штатную модель, только потом думать о своей модели.

## 6. Периодические Процессы

Если один и тот же результат требуется по стабильной последовательной периодике:

- используется Повторяющаяся задача;
- каждый период остаётся отдельной Задачей;
- следующий экземпляр появляется после закрытия предыдущего;
- новый экземпляр попадает в первый Этап Проекта;
- его Приоритет штатно сбрасывается на низкий.

Если будущая Задача должна появляться по календарю независимо от закрытия предыдущей, нужна другая механика. Не пытаться скрыть этот случай под штатной повторяемостью.

## 7. Общая контрольная точка

Если несколько Задач должны совместно обеспечить общий результат к одной дате — используется Веха.

Примеры:

- закрытие периода;
- общий пакет результатов;
- контрольная дата;
- ограниченная по времени инициатива.

Веха не заменяет Процесс и индивидуальные Крайние сроки.

## 8. Когда выделять отдельный Процесс

Отдельный Процесс нужен, если есть устойчивые:

- вход;
- результат;
- единица Задачи;
- правила срока или готовности;
- повторяемая управленческая граница.

Не являются отдельным Процессом:

- конкретный сотрудник;
- разовый документ;
- единичная тема;
- Вид работы;
- временная срочная Задача.

## 9. Когда нужен отдельный Odoo Проект

Для обычной операционной работы отдельные Проекты по Процессам не создаются.

Отдельный Проект оправдан только для действительно самостоятельной инициативы, если ей нужны собственные границы, отдельный набор Задач, Вехи, сроки и контекст управления.

Наличие нескольких Задач, Ответственных, Этапов или зависимостей само по себе не является причиной создавать новый Проект.

## 10. Улучшение Процесса

Процесс меняется по повторяющимся фактам:

- растёт количество открытых Задач;
- повторяются просрочки;
- одна и та же блокировка возникает снова;
- стандартный путь требует лишних ручных действий;
- данные приходится дублировать вне Odoo;
- классификация регулярно заполняется неправильно;
- нужный объект трудно искать;
- аналитика не позволяет принять решение.

После изменения проверяются те же признаки.

## 11. Проверка описания

- [ ] понятны вход и результат;
- [ ] определено, что считается одной Задачей;
- [ ] понятны Крайний срок и критерий `Готово`;
- [ ] указан типичный набор Видов работы;
- [ ] понятно, когда использовать Подзадачу или внутреннюю зависимость;
- [ ] выбраны только реально полезные связанные объекты;
- [ ] периодика и Веха используются только где они нужны;
- [ ] понятно, требуется ли отдельная проверка результата;
- [ ] Процесс можно анализировать без чтения каждой Задачи вручную.
