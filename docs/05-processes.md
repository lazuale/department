Описание процесса должно отдельно фиксировать:

1. **бизнес-смысл** — что реально происходит;
2. **реализацию в Odoo** — какими штатными сущностями это представлено;
3. **локальные правила** — роли, сроки, переходы и права только там, где они действительно существуют.

Не выводить бизнес-правило только из того, что Odoo имеет соответствующую кнопку или поле.

## 1. Сначала предмет, потом workflow

До настройки Kanban определить:

> С какими реальными сущностями работает процесс и где находится источник истины?

Примеры:

| Предмет | Возможный источник истины |
|---|---|
| сотрудник / человек | Contacts / `res.partner` |
| пользователь с доступом | `res.users` |
| ТС | Fleet, если подходит |
| оборудование | Maintenance Equipment |
| обслуживание | Maintenance Request |
| serial / lot / location / movement | Inventory |
| закупка | Purchase |
| расход | Expenses |

Для людей текущего контура действует [17 — Master data: люди](17-master-data-people.md): Employees / HR не включается только ради справочника сотрудников.

Если подходящей штатной модели нет, это не означает автоматически, что объект надо хранить в Task.

## 2. Решение по собственной предметной сущности

```text
Есть предметная сущность
        ↓
Подходит штатная Odoo model?
        │
     да ───→ использовать её
        │
       нет
        ↓
Объект нужен только как атрибут работы?
        │
        ├─ да → Property / Tag / данные Task
        │
        └─ нет
             ↓
Нужны собственный реестр / уникальность / lifecycle / права / связи / аналитика?
        │
        ├─ нет → не создавать отдельную сущность
        └─ да  → кандидат на минимальную custom model
```

## 3. Затем определить единицу Task

Task создаётся не на каждый входящий объект, а на отдельный контролируемый результат.

Хорошая единица Task позволяет отдельно ответить:

- что должно быть получено;
- кто выполняет в рамках процесса;
- нужен ли срок;
- где работа находится в workflow;
- когда результат считается завершённым.

Если эти вопросы относятся к нескольким независимым результатам, вероятно, нужны несколько Tasks/Subtasks.

## 4. Когда Task не нужна

Task не создаётся только ради:

- хранения master data;
- файла;
- сообщения;
- звонка;
- одной технической операции;
- дублирования профильного workflow.

Если событие полностью закрывается Maintenance Request, Purchase Order, Expense или другой штатной сущностью, Project Task не нужна без отдельного управленческого результата.

## 5. Связь Task с предметом

Если Task должна системно ссылаться на объект, сначала проверить штатную relation или relational Property.

Примеры текущего контура:

```text
ТС           → Many2one(fleet.vehicle)
Сотрудник    → Many2one(res.partner)
Оборудование → Many2one(maintenance.equipment)
```

Не копировать большой справочник в Selection Property.

## 6. Project boundary определяется процессом

Не существует универсального правила «один отдел = один Project» или «каждый процесс = отдельный Project».

Отдельный Project оправдан, когда реально различаются:

- visibility;
- lifecycle;
- project-level управление;
- milestones;
- существенно отличающийся workflow;
- структура, повторяемая через Project Template.

Если различия нужны только для фильтрации, чаще достаточно Properties/Tags/Views.

## 7. Stages — локальная схема процесса

Базовая методика не задаёт обязательные названия Stages.

Для каждого Project определить только те Stages, которые отражают реальные состояния прохождения работы.

Не создавать Stage только потому, что он присутствовал в другой системе или предыдущей версии методики.

Не дублировать системные `Done`, `Canceled` и dependency-driven `Waiting` без отдельного смысла.

## 8. Assignees — локальное правило ответственности

Процесс определяет:

- требуется ли Assignee при создании;
- допустимы ли неназначенные Tasks;
- используется один или несколько Assignees;
- кто имеет право назначать и передавать работу.

Odoo предоставляет механизм, но не определяет организационное правило.

Assignee — это пользователь `res.users`; он не является общим master record человека.

## 9. Deadline — локальное правило срока

Процесс определяет:

- нужен ли Deadline;
- откуда он берётся;
- кто и когда может его менять;
- требуется ли фиксация основания изменения.

Базовое техническое правило одно:

```text
Deadline = срок результата
Activity Due Date = срок следующего действия
```

## 10. Priority используется только если имеет последствия

Odoo имеет Low / Medium / High / Urgent.

Процесс должен определить смысл используемых значений и действие, которое они меняют.

Если различие ничего не меняет, не вводить лишнюю локальную шкалу.

## 11. Внешнее ожидание

Если процесс содержит ожидание внешнего события, определить, как оно отражается:

- отдельный Stage;
- Activity на follow-up;
- запись в Chatter;
- сочетание этих механизмов.

Не объявлять конкретный вариант обязательным для всех процессов.

## 12. Внутренняя зависимость

Если Task зависит от другой Task:

```text
Blocked by
→ Waiting
```

Это штатная dependency и не требует отдельного локального Stage `Waiting` без другой причины.

## 13. Проверка результата

Если независимая проверка является реальной частью процесса, описать:

- кто проверяет;
- когда возникает проверка;
- как отражается возврат;
- какое состояние означает принятие.

Если такой проверки нет, не добавлять её искусственно.

## 14. Повторяемость

Процесс выбирает один из штатных механизмов по смыслу:

```text
Task Template
Recurring Task
Activity Plan / chaining
Project Template + Roles
```

Не включать повторяемость только потому, что функция доступна.

## 15. Права

Права описываются как реальные действия, а не названия должностей.

Пример:

```text
может видеть Task
может создавать Task
может изменять Task
может удалять Task
может менять master data
может видеть все records данного Project
```

После этого правило отображается на Groups / Access Rights / Record Rules / Project visibility.

## 16. Контроль процесса

Для процесса определить несколько вопросов, на которые должен отвечать Odoo.

Примеры:

- какие Tasks требуют внимания;
- какие сроки нарушены;
- какие records не имеют требуемой классификации;
- какие Tasks заблокированы;
- где появились просроченные Activities;
- как меняется backlog;
- какие Tasks относятся к конкретному предметному объекту.

Из этих вопросов строятся Shared Views, Pivot/Graph и Dashboard.

## 18. Что считается корректной адаптацией

Корректная адаптация меняет привычный способ работы, если штатная модель Odoo решает тот же управленческий вопрос проще.

Некорректная адаптация требует отказаться от необходимой ответственности, срока, истории, прав или достоверности данных только ради отсутствия доработки.

В последнем случае фиксируется конкретный технический gap.
