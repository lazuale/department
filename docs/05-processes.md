# Описание процессов

[Главная](../README.md) · [00 Возможности](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [02 Сценарии](02-scripts.md) · [03 Аналитика](03-control.md) · [04 Шаблоны](04-templates.md) · **05 Процессы** · [06 Настройка](06-workspace.md)

Процесс описывает, **какие штатные сущности Odoo используются, когда создаётся Task и как она связывается с предметными объектами**.

Odoo хранит фактические данные и исполнение. Репозиторий хранит устойчивое правило процесса.

## 1. Сначала определить предметные модели

До Kanban ответить:

> С какими реальными объектами работает процесс и где находится источник истины?

Примеры:

| Объект | Модель |
|---|---|
| обязательство | Project Task |
| сотрудник | Employees |
| внешний субъект | Contacts |
| ТС | Fleet |
| оборудование | Maintenance Equipment |
| обслуживание | Maintenance Request |
| serial/location/movement | Inventory |
| встреча | Calendar |

## 2. Затем определить связь Task с объектом

Если Task должна системно относиться к предметному объекту, сначала использовать relational Property.

Примеры:

```text
ТС           → Many2one(fleet.vehicle)
Сотрудник    → Many2one(hr.employee)
Оборудование → Many2one(maintenance.equipment)
```

Для нескольких объектов допустим Many2many, если результат действительно один.

Не копировать справочник в Selection Property.

## 4. Решение «создавать Task или нет» — часть процесса

### Только изменение предметных данных

```text
получили новый госномер
→ обновить Fleet Vehicle
```

Если отдельного результата для контроля нет, Task не нужна.

### Появилось обязательство

```text
обнаружено расхождение по ТС
→ проверить причину и исправить
```

Создаётся Task, а `Property[ТС]` ссылается на Vehicle.

## 5. Единица Task

Хорошая единица:

- одна сверка за период;
- одно исправление самостоятельного основания;
- одно получение конкретного подтверждения;
- один итоговый отчёт;
- одно изменение процесса.

Плохая единица:

- одно письмо;
- один файл;
- один комментарий;
- одна строка независимо от смысла;
- весь вечный процесс в одной Task.

Если единица выбрана плохо, аналитика будет ложной независимо от Dashboard.

## 6. `Процесс` Property — классификация, а не справочник объектов

Если разрез процессов нужен в контроле:

```text
Property: Процесс
Type: Selection
```

Он нужен для фильтрации/группировки Tasks.

ТС, Employees и Equipment должны ссылаться на свои модели через relational Properties, а не становиться значениями `Процесс`.

## 7. Связь с ТС

Если процесс работает с Fleet:

```text
Fleet Vehicle = master data
Task Property[ТС] = Many2one(fleet.vehicle)
```

Процесс должен определить:

- когда Property обязательно;
- какой Domain используется;
- кто может создавать/редактировать Vehicle;
- какие views строятся по ТС.

Не объявлять отсутствие Python-поля `vehicle_id` click-only gap до теста relational Property.

## 8. Связь с Employee

Разделять:

```text
Assignee = владелец результата
Property[Сотрудник] = предмет работы
```

Если процесс обрабатывает данные сотрудников, Employee Property может быть обязательным для этого процесса, но не для всех Tasks отдела.

## 9. Связь с Equipment

Если отдельная Task относится к Equipment:

```text
Property[Оборудование] → maintenance.equipment
```

Если процесс полностью является ремонтом/ТО, использовать Maintenance Request без параллельной Task.

## 10. Inventory + Maintenance

Для серийного оборудования сначала проверить штатную связку:

```text
Inventory serial/lot/location
+ Maintenance Equipment
+ stock_maintenance
+ hr_maintenance
```

Собственный реестр активов появляется только после подтверждённого остаточного ограничения.

## 11. Входящий канал не определяет процесс

Работа может появиться:

- вручную;
- email alias;
- Website Form;
- Discuss;
- To-Do → Convert to Task;
- API/webhook.

Канал регистрации не определяет автоматически:

- процесс;
- Priority;
- Deadline;
- Assignee;
- предметный Property;
- необходимость Task.

Все автоматические входящие проходят triage, если правило не является полностью детерминированным.

## 12. Внешнее ожидание

```text
Stage = Ожидание внешнего
Activity = следующая контрольная точка
```

Процесс должен определить типовой follow-up и правило эскалации.

## 13. Внутренняя зависимость

```text
Blocked by = другая Task
→ Waiting
```

Не объединять с внешним ожиданием.

## 14. Типовая разовая работа

Если одинаковая Task появляется по событию:

```text
Task Template
```

В process description указать, какой шаблон использовать.

## 15. Календарная периодика

Если один результат повторяется по расписанию:

```text
Recurring Task
```

## 16. Повторяемая проектная инициатива

Если повторяется несколько Tasks/ролей/вех:

```text
Project Template + Project Roles
```

## 17. Activity chain

Если follow-up устойчив:

```text
Activity Type chaining / Activity Plan
```

Это предпочтительнее Automation Rule, если задачи достаточно.

## 18. Automation Rule

Процесс может использовать Automation только если:

1. событие однозначно;
2. действие всегда одинаково;
3. данные для условия надёжны;
4. результат можно проверить;
5. более простой штатный механизм не подходит.

## 19. Специализированный workflow

Если процесс по предмету является:

- Maintenance;
- Time Off;
- Expense;
- Purchase;
- Recruitment;
- Survey;

использовать штатный workflow приложения.

Project Task создаётся только для отдельного управленческого результата поверх него.

## 20. Bridge modules входят в описание процесса

Если процесс пересекает приложения, проверить штатные bridges.

Примеры:

```text
Employees + Fleet        → hr_fleet
Employees + Maintenance  → hr_maintenance
Inventory + Maintenance  → stock_maintenance
Project + Purchase       → project_purchase
Project + Inventory      → project_stock
Project + Accounting     → project_account
```

Если bridge уже решает связь, не дублировать её Property/custom field без причины.

## 21. Контроль процесса

Для каждого процесса определить небольшой набор вопросов, например:

```text
Что создано?
Что закрыто?
Что open?
Что overdue?
Что Waiting?
Что ждёт внешнего?
По каким предметным объектам копится backlog?
Сколько времени до назначения/закрытия?
```

Предметные показатели берутся из предметного приложения, а обязательства — из Project.

## 22. Пример: сверка по ТС

```text
Название:
Сверка данных по ТС

Master data:
Fleet Vehicle

Связь:
Property[ТС] → Many2one(fleet.vehicle)

Вход:
наступил период и доступны исходные данные

Результат:
сверка завершена; расхождения исправлены или вынесены в самостоятельные Tasks

Единица Task:
одна сверка по выбранному масштабу процесса

Вид работы:
Работа

Периодика:
Recurring Task, если цикл календарный

Внешнее ожидание:
Ожидание внешнего + Activity

Внутренняя зависимость:
Blocked by

Контроль:
Deadline, overdue, Waiting, external waiting, backlog by Property[ТС]

Gap:
фиксируется только если Many2one Property или стандартная аналитика не выдерживают фактическую задачу/объём
```

## 23. Когда Property недостаточно

Процесс может зафиксировать residual gap только после проверки:

```text
Property настроено
→ filter/group работает или не работает
→ bridge проверен
→ права проверены
→ API/Import проверены
→ измерен реальный объём
```

Только затем обсуждается custom schema field или другая доработка.
