# Строгие шаблоны

## 1. Общие правила именования

Subject должен позволять понять результат без открытия карточки.

Базовая схема:

`[Категория] Краткий результат — основание/период`

Примеры обезличены:

- `[Процесс A] Обработать основание — №123`;
- `[Процесс B] Провести сверку — 2026-08`;
- `[Отчётность] Подготовить отчёт — 2026-08`;
- `[Запрос] Получить подтверждение — тема X`.

Запрещённые Subject:

- `Срочно`;
- `Письмо`;
- `СЗ`;
- `Сделать`;
- `Посмотреть`;
- `Важно`;
- `RE:`;
- `Работа по файлу`.

Subject не используется как единственный идентификатор: идентичность Work Package задаётся её системным ID.

---

# 2. Шаблон обычной работы

```text
Subject:
[Категория] <результат> — <основание/период>

Type:
Работа

Category:
<устойчивый бизнес-процесс>

Status:
Очередь

Assignee:
<исполнитель или группа>

Finish date:
<дата результата>

Priority:
Обычный / Высокий / Критичный

Description:
Основание: <краткое указание>
Результат: <что должно существовать после выполнения>
Контекст: <только если без него невозможно выполнить работу>
```

Правило: описание не дублирует переписку целиком.

# 3. Шаблон самостоятельного исходящего запроса

```text
Subject:
[Запрос] Получить <результат> — <тема>

Type:
Запрос

Category:
<процесс, породивший запрос>

Status:
Очередь

Assignee:
<владелец сопровождения>

Finish date:
<когда результат должен быть получен>

Description:
Цель: <какой результат требуется>
Адресат/сторона: <обобщённое обозначение>
Основание: <почему запрос возник>
Связанные работы: <ID при наличии>
```

После отправки запроса и при отсутствии активных действий:

`В работе → Ожидание`

```text
Subject:

Type:
Работа

Status:
Очередь

Assignee:
<исполнитель/группа>

<срок текущего периода>

Description:
Регламент: <название устойчивой операции>
```

Каждый период — отдельная Work Package.

```text
Subject:

Работа

Category:
<ближайший устойчивый процесс или Прочее>
```

# 6. Шаблон идеи

```text
Subject:
[Идея] <краткое название проблемы/улучшения>

Type:
Идея

Backlog bucket:
Inbox

Description:
Наблюдение:
<что происходит сейчас>

Проблема:
<что теряем: время, качество, управляемость, срок>

Гипотеза:
<что можно изменить>

Факты:
<ссылки на связанные работы, показатели или примеры при наличии>

Ожидаемый эффект:
<что должно улучшиться>
```

Идея без готового решения допустима. Идея без сформулированной проблемы — нет.

# 7. Шаблон комментария при ожидании

Строгая форма:

```text
Ожидание с <дата/время>.
Ждём: <конкретный результат>.
Действие выполнено: <что и когда направлено/сделано>.
Следующее действие после ответа: <кратко>.
```

Короткий вариант, если контекст очевиден:

```text
Ожидание: <что ждём>. Запрос направлен <дата>.
```

Запрещённые комментарии:

- `ждём`;
- `пока нет ответа`;
- `уточняется`;
- `в процессе`.

---

# 8. Шаблон передачи работы

```text
Передача.
Состояние: <что уже выполнено>.
Следующий шаг: <одно конкретное действие>.
Риск/ограничение: <если есть>.
```

Передача не используется для переписывания всей истории Work Package.

---

# 9. Шаблон отмены

```text
Отменено: <краткая причина, почему результат больше не требуется>.
```

Запрещено:

```text
Неактуально.
```

без пояснения, что изменилось.

---

# 10. Шаблон reopen

```text
Возврат в работу.
Причина: <какой элемент первоначального результата выполнен неверно/не полностью>.
Необходимо: <что исправить>.
```

Reopen не используется для нового дополнительного объёма.

---

# 11. Шаблон дубликата

```text
Дубликат Work Package #<ID>.

```

# 12. Шаблон Definition of Done процесса

Для каждой Category хранится максимум несколько коротких условий.

```text
Category: <процесс>

Работа считается готовой, если:
1. <конечный результат выполнен>;
2. <результат сохранён/передан, если это часть процесса>;
3. открытых обязательных действий подразделения по этому результату нет.
```

DoD не должен содержать очевидные технологические шаги, если их пропуск не является устойчивым риском.

---

# 13. Шаблон еженедельного разбора потока

```text
Период: <даты>

1. Вход:
   - поступило: <значение>
   - завершено: <значение>
   - изменение очереди: <значение>

2. Исключения:
   - просрочено: <значение>
   - старые в очереди: <перечень/значение>
   - старые в ожидании: <перечень/значение>
   - без владельца: <значение>
   - reopen: <значение>
   - дубли: <значение>

3. Системные причины:
   - <проблема>
   - <проблема>

4. Решения:
   - <действие / владелец / срок>

5. В backlog улучшений:
   - <идея или нет>
```


# 15. Контрольный шаблон создания новой Category

Новая Category допускается только при ответе `да` на все вопросы:

```text
1. Это устойчивый бизнес-процесс, а не разовая тема? Да/Нет
2. Он будет использоваться многократно? Да/Нет
3. Его нельзя корректно отнести к существующей Category? Да/Нет
4. Категория улучшит фильтрацию или управленческий анализ? Да/Нет
```

Если хотя бы один ответ `Нет`, новая Category не создаётся.

---

# 16. Контрольный шаблон создания отдельного Project

```text
Самостоятельных результатов: <да/нет>
Несколько владельцев/направлений: <да/нет>
Есть этапность: <да/нет>
Есть зависимости: <да/нет>
Продолжительность существенно выше обычной работы: <да/нет>
Нужен отдельный управленческий обзор: <да/нет>
```

Отдельный Project создаётся только при наличии нескольких одновременно подтверждённых признаков.
