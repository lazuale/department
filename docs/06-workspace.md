## 1. Принцип реализации

Базовая версия строится на штатной **русской Odoo Community 19.0** без собственного модуля.

Доработка рассматривается только после пилота, если подтверждено, что штатный вариант:

- регулярно мешает ежедневной работе;
- приводит к системным ошибкам данных;
- не позволяет получить нужную управленческую аналитику;
- требует повторяющихся ручных действий, стоимость которых заметно выше стоимости доработки.

Цель — не сохранить исходную методику любой ценой и не подчинить работу терминологии Odoo, а собрать рабочую модель из сильных сторон обоих подходов.

## 2. Базовые приложения

### Используются

- **Проекты** (`project`) — Задачи, Этапы, Состояния, Приоритет, Крайний срок, Подзадачи, зависимости, Повторяющиеся задачи, Вехи, Канбан, Список, Календарь, Сводная таблица и График;
- **Обсуждения** (`mail`) — история общения, Подписчики, Активности, письма, заметки и вложения;
- **Контакты** (`contacts`) — внешние люди и организации;
- **Сотрудники** (`hr`) — внутренний справочник сотрудников;
- **Обслуживание** (`maintenance`) — только если его модель оборудования естественно подходит для нужных физических объектов.

### Только по доказанной потребности

- **Табели времени** (`hr_timesheet`) — если нужны фактические человеко-часы и пользователи могут вести их без избыточной нагрузки.

Остальные приложения не устанавливаются только ради наличия.

## 3. Один рабочий Проект

Для постоянной операционной работы используется один основной Odoo Проект.

**Проект = общее рабочее пространство.**

**Процесс = Свойство Задачи, а не отдельный Проект.**

Это даёт:

- одну рабочую доску;
- единый список открытой работы;
- прямые связи между Задачами разных Процессов;
- общую аналитику без предварительного склеивания нескольких Проектов.

Отдельный Проект создаётся только для действительно самостоятельной инициативы, а не для каждого Процесса или Вида работы.

## 4. Карта методики на русскую Odoo

| Методика | Штатная Odoo 19 | Решение |
|---|---|---|
| самостоятельно контролируемый результат | **Задача** | использовать штатно |
| `Работа / Запрос` | Свойство `Тип задачи` | `Выбор` |
| Процесс | Свойство `Процесс` | `Выбор` на пилоте |
| Вид работы | Свойство `Вид работы` | `Выбор` на пилоте |
| текущий владелец результата | `Ответственные` | штатно; обычно один основной |
| срок результата | `Крайний срок` | штатно |
| порядок важности | `Приоритет` | штатные четыре уровня |
| принятая, но не активная работа | Этап `Очередь` | штатно |
| активное выполнение | Этап `В работе` | штатно |
| внешнее ожидание | Этап `Внешнее ожидание` | штатно |
| внутренняя блокировка | `Блокирующие задачи` → состояние `В ожидании` | штатно |
| завершение | состояние `Готово` | отдельный Этап не нужен |
| отмена | состояние `Отменено` | отдельный Этап не нужен |
| отдельная проверка результата | `Требуются изменения / Одобрено` | только где реально нужна |
| следующий шаг | Активность | штатно |
| переписка и файлы | история общения и вложения | штатно |
| самостоятельная часть результата | Подзадача | штатно |
| общий срок нескольких Задач | Веха | штатно |
| стабильная последовательная периодика | Повторяющаяся задача | штатно с оговорками |
| дополнительные признаки | Теги | только поперечные признаки |
| личное планирование | Личные этапы | штатно, вне управленческого статуса |

## 5. Свойства первого пилота

В рабочем Проекте создаются три основных Свойства задачи.

### `Тип задачи`

Тип: `Выбор`.

Значения:

- `Работа`;
- `Запрос`.

По умолчанию — `Работа`, если интерфейс позволяет задать значение без лишних действий.

### `Процесс`

Тип: `Выбор`.

Значения — только реально описанные Процессы. Не плодить варианты в свободном режиме.

### `Вид работы`

Тип: `Выбор`.

Значения:

- Внесение;
- Проверка;
- Сверка;
- Исправление;
- Мониторинг;
- Анализ;
- Подготовка.

Для `Запроса` значение можно оставлять пустым.

### Ограничения Свойств

У штатных Свойств Odoo 19 нет полноценного признака `обязательное поле`. Поэтому на пилоте нельзя жёстко запретить сохранение Задачи без Процесса или Вида работы обычной настройкой Свойства.

Также штатный `Выбор` не позволяет динамически ограничить Вид работы в зависимости от выбранного Процесса.

На старте это не причина писать модуль. Сначала проверяется реальное качество данных:

- если сотрудники почти не ошибаются — ограничение не нужно;
- если ошибки регулярны и портят контроль или аналитику — появляется обоснованный кандидат на небольшую доработку.

## 6. Дополнительные Свойства

Добавляются только если реально нужны в поиске, контроле или аналитике.

Примеры:

- причина внешнего ожидания — `Выбор`;
- участок или другой небольшой стабильный перечень — `Выбор`;
- внутренний сотрудник — ссылка на **Сотрудников**;
- внешнее лицо или организация — ссылка на **Контакты**;
- оборудование — ссылка на **Обслуживание**, если модель подходит;
- другой локальный признак — только после проверки пользы.

Если Свойства начинают мешать массовому импорту, обязательности, связям или аналитике, тогда рассматриваются обычные поля или отдельная модель. Не раньше.

## 7. Этапы и Состояния

Рабочая Канбан-доска:

```text
Очередь | В работе | Внешнее ожидание
```

### `Очередь`

Задача принята, но не находится в активном исполнении.

### `В работе`

Задача находится в активном рабочем контуре Ответственного. Не требуется двигать карточку из-за каждого краткого переключения.

### `Внешнее ожидание`

Используется, когда продолжение зависит от внешнего ответа, документа, доступа, решения или события и нет отдельной внутренней блокирующей Задачи.

### Внутренняя зависимость

Если есть реальная блокирующая Задача, используется поле **Блокирующие задачи**. Odoo автоматически переводит зависимую Задачу в состояние `В ожидании` до закрытия блокировки и возвращает её в `В процессе`, когда блокировка снята.

Не нужно одновременно вручную держать такую Задачу во `Внешнем ожидании`.

### Закрытие

- результат получен → состояние `Готово`;
- результат больше не требуется → состояние `Отменено`.

Отдельный Этап `Готово` не создаётся, чтобы не требовать двух действий для одного завершения.

### Проверка результата

`Требуются изменения` и `Одобрено` не используются как обязательная лестница для всех Задач. Они включаются в рабочее правило только тех Процессов, где результат действительно должен проходить отдельную проверку.

## 8. Ответственные и общая очередь

Штатное поле `Ответственные` допускает нескольких пользователей.

Рабочее правило: у Задачи должен быть понятен основной владелец результата. Жёсткое ограничение на одного пользователя заранее не вводится.

Задачи без Ответственного на Этапе `Очередь` могут играть роль общей очереди.

При саморегистрации сотрудник назначает себя Ответственным. Если ручное самоназначение при реальном потоке Задач становится заметной лишней операцией, автоматическое назначение создателя — один из первых оправданных кандидатов на небольшую доработку.

## 9. Крайний срок и Приоритет

`Крайний срок` используется как срок конечного результата.

Активность используется как дата следующего действия.

Штатные уровни Приоритета:

- `Низкий` — обычный;
- `Средний` — выше обычной очереди;
- `Высокий` — заметный риск для срока, связанной работы или результата;
- `Срочно` — требуется немедленная реакция.

Не создавать отдельное поле `Критичность`.

Если команда фактически различает только обычную и срочную работу, можно использовать только крайние уровни. Главное — одинаковый смысл, а не заполнение всех четырёх вариантов.

## 10. Активности, история общения и почта

### Активность

Используется для конкретного следующего действия:

- повторно написать;
- позвонить;
- проверить ответ;
- вернуться к вопросу в дату;
- выполнить другой следующий шаг.

Активность не заменяет Задачу и не меняет её Крайний срок.

### История общения

Используется для:

- переписки;
- важных рабочих заметок;
- вложений;
- контекста передачи;
- истории изменений.

Не вести параллельный комментарий в отдельном реестре.

### Почтовый адрес Проекта

Можно проверить как ускоритель регистрации: сотрудник выборочно пересылает письмо на адрес Проекта, если письмо уже стало основанием самостоятельной Задачи.

Не направлять весь входящий поток автоматически в Задачи.

## 11. Личные этапы

Odoo 19 создаёт для пользователя персональные этапы вроде:

```text
Входящие | Сегодня | На этой неделе | В этом месяце | Позже | Готово | Отменено
```

Их стоит использовать как личный планировщик.

Это позволяет сотруднику решить:

- что делать сегодня;
- что оставить на неделю;
- что отложить;

при этом не меняя общий Этап Задачи.

Личные этапы не являются источником управленческого состояния и не должны использоваться в общей аналитике Процесса.

## 12. Подзадачи, зависимости и Вехи

### Подзадача

Для самостоятельной части общего результата со своим Ответственным, сроком или отдельным результатом.

Не использовать Подзадачи как чек-лист каждого технического действия.

### Внутренняя зависимость

Для реального порядка выполнения. Не использовать как простую ссылку между связанными темами.

### Веха

Для общей контрольной даты нескольких Задач: закрытие периода, пакет результатов, контрольная точка или ограниченная по времени инициатива.

Эти механизмы позволяют не дробить постоянную операционную работу на отдельные Проекты.

## 13. Повторяющиеся задачи

Повторяемость Odoo 19 подходит для **последовательной периодики**.

Штатное поведение:

- следующий экземпляр создаётся только после закрытия предыдущего состоянием `Готово` или `Отменено`;
- новый экземпляр попадает в первый Этап Проекта, поэтому первым Этапом должен быть `Очередь`;
- Приоритет нового экземпляра принудительно становится низким.

На стенде дополнительно проверить пользовательский результат копирования:

- Ответственных;
- Тегов;
- Свойств `Тип задачи`, `Процесс`, `Вид работы`;
- других реально используемых Свойств.

Если важный признак приходится восстанавливать каждый период вручную, это кандидат на небольшую доработку.

Если новая Задача должна появляться строго по календарю независимо от состояния предыдущей, нужна отдельная автоматизация; штатная повторяемость для этого сценария не используется.

## 14. Связанные объекты без своей разработки

### Контакты

Для внешних лиц и организаций.

### Сотрудники

Для внутреннего справочника сотрудников, если Задачу нужно связывать с человеком не в роли Ответственного.

### Обслуживание

Проверяется для физических объектов: оборудования, терминалов, рамок и других единиц, если карточка и логика обслуживания естественно соответствуют объекту.

Не использовать приложение только потому, что там уже есть похожие поля.

### Небольшие справочники

Для ограниченного стабильного набора вроде участков сначала использовать Свойство типа `Выбор`.

## 15. Импорт данных

Для штатных бизнес-объектов использовать импорт CSV/XLSX.

Если справочник обновляется повторно, задавать стабильный **Внешний ID**. Повторный импорт с тем же Внешним ID должен обновлять существующую запись, а не создавать дубль.

Для массовой загрузки значений Свойств задачи удобство импорта необходимо отдельно проверить на стенде до того, как строить на этом регулярный обмен данными.

## 16. Рабочие представления без кода

На пилоте настроить и сохранить как минимум:

- `Моя работа`;
- `Очередь`;
- `Внешнее ожидание`;
- `Внутренние блокировки`;
- `Просрочено`;
- `Без Ответственного`;
- `Запросы`;
- `Высокий и срочный Приоритет`;
- `Закрытые за период`;
- `Без Процесса`;
- `Без Вида работы`;
- `Аналитика`.

Использовать штатные фильтры и группировки Odoo по Ответственным, Этапам, Приоритету, срокам, открытым/закрытым Задачам, блокировкам, Активностям и Свойствам.

## 17. Аналитика в штатной Odoo

Без отдельного учёта Odoo даёт рабочие представления:

- Канбан;
- Список;
- Календарь;
- Сводную таблицу;
- График;
- Активности.

На их основе можно контролировать:

- количество Задач;
- Этап;
- Состояние;
- Ответственных;
- Приоритет;
- Крайний срок;
- даты создания и закрытия;
- Теги;
- Вехи;
- внутренние блокировки;
- Свойства задачи.

Штатный поиск поддерживает поиск и группировку по Свойствам. Поэтому Процесс и Вид работы можно использовать как аналитические признаки без отдельной модели.

### Что нельзя считать решённым до пилота

**Разрез `Процесс × Вид работы`.** Нужно проверить, насколько удобно получить два Свойства одновременно в Сводной таблице и Графике.

**Рабочее время до закрытия.** Odoo содержит такую штатную меру, но при нашей схеме завершения через состояние `Готово` её корректность необходимо проверить отдельно. До проверки она не является KPI.

**История длительности ожиданий, передач и возвратов.** Эти показатели не строятся заранее; только если появится реальное управленческое решение, для которого они нужны.

## 18. Что специально не строится заранее

Без фактической проблемы не добавлять:

- собственный модуль;
- отдельные модели Процессов и Видов работы;
- жёсткую обязательность Свойств;
- программную матрицу `Процесс × Вид работы`;
- ограничение ровно на одного Ответственного;
- автоназначение создателя;
- собственное вычисляемое состояние поверх Этапа и Состояния Odoo;
- отдельный журнал передачи;
- параллельный реестр Задач;
- отдельную оболочку интерфейса;
- табели времени для всех пользователей.

Каждый пункт может появиться позже, но только после подтверждённой проблемы.

## 19. Минимальный стенд

Для проверки модели достаточно одного рабочего Проекта и 30–50 обезличенных Задач, которые покрывают разные Процессы и Виды работы.

На стенде проверить:

1. создание и саморегистрацию Задачи;
2. `Работа / Запрос`;
3. `Очередь / В работе / Внешнее ожидание`;
4. `Готово / Отменено`;
5. `Требуются изменения / Одобрено` на одном сценарии, где проверка действительно нужна;
6. внутреннюю блокировку и автоматическое `В ожидании`;
7. Подзадачи;
8. Вехи;
9. Повторяющуюся задачу;
10. Личные этапы;
11. поиск и группировку по Процессу и Виду работы;
12. Сводную таблицу `Процесс × Вид работы`;
13. фильтры `Просрочено / Без Ответственного / Без Процесса`;
14. связи с Контактами, Сотрудниками и оборудованием;
15. импорт и повторное обновление справочника;
16. фактическое количество действий, которое пользователь делает для обычной Задачи.

Только после этого решается, нужна ли какая-либо доработка.
