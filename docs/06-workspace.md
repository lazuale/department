# Настройка Odoo 19 Community

[Главная](../README.md) · [00 Возможности Odoo](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [02 Сценарии](02-scripts.md) · [03 Контроль и аналитика](03-control.md) · [04 Шаблоны](04-templates.md) · [05 Процессы](05-processes.md) · **06 Настройка**

---

Этот документ описывает **click-only пилот Odoo 19 Community** для одного отдела.

Цель пилота — не включить максимум приложений. Цель — собрать минимальный, но методически правильный контур, в котором:

- обязательства ведутся в Project;
- сотрудники — в Employees;
- ТС — во Fleet, если они нужны;
- оборудование — в Maintenance, если оно нужно;
- внешние субъекты — в Contacts;
- обсуждения не подменяют задачи;
- контроль строится на Shared Views и штатной аналитике;
- код появляется только для подтверждённых разрывов модели.

## 1. Перед настройкой: не путать приложения и сущности

Базовая схема:

```text
Employees        → сотрудники
Contacts         → внешние люди/организации
Fleet            → транспортные средства
Maintenance      → оборудование и обслуживание
Project          → обязательства и результаты
Discuss/Chatter  → коммуникация
Calendar         → встречи
Activities       → следующее действие
Dashboards       → контроль существующих данных
```

Не создавать Project Property на данные, для которых уже есть штатная модель.

## 2. Что установить для пилота

### Обязательно

- `Project`;
- `Employees`;
- `Contacts`;
- `Dashboards` / My Dashboard — после настройки рабочих представлений.

`Discuss`, Chatter и Activities входят в платформенный контур через Mail и используются штатно.

### Установить, если реально участвует в работе отдела

- `Fleet` — если задачи и анализ связаны с ТС;
- `Maintenance` — если учитывается оборудование / внутреннее железо / заявки обслуживания;
- `Calendar` — если встречи нужно вести внутри Odoo;
- `Timesheets` — только если нужен факт трудозатрат;
- `Website` — только если нужен intake через форму.

### Не включать как зависимость методики

- Studio;
- Helpdesk;
- Approvals;
- Documents;
- Knowledge;
- Planning;
- другие Enterprise-функции.

### Не ставить просто «потому что есть»

- Timesheets;
- Customer Ratings;
- Website;
- сложные Automation Rules;
- дополнительные проекты;
- множество Activity Plans.

## 3. Настроить пользователей и Employees

### 3.1 Пользователи

В `Settings → Users` создать внутренних пользователей, которые реально будут работать в Odoo.

На пилоте не создавать сложную самодельную матрицу record rules.

Достаточно:

- выдать доступ только к нужным приложениям;
- Project users должны видеть операционный проект;
- административные настройки оставить ограниченному числу администраторов.

### 3.2 Employees

В `Employees` завести сотрудников, которые нужны как штатный справочник.

Минимум контролировать:

- ФИО;
- должность;
- подразделение;
- руководителя — если используется;
- рабочее местоположение — если нужно;
- связанного User для тех, кто работает в Odoo.

### 3.3 Массовая загрузка

Не вводить сотрудников по одному, если уже есть корректный CSV/XLSX.

Использовать стандартный Import:

1. открыть список Employees;
2. `Actions → Import records`;
3. загрузить CSV/XLSX;
4. сопоставить поля;
5. нажать `Test`;
6. исправить ошибки;
7. импортировать.

Для последующих массовых обновлений использовать стабильный External ID.

## 4. Contacts

Contacts использовать для внешних:

- организаций;
- подрядчиков;
- контактных лиц;
- заявителей.

Не создавать внешний субъект как Employee.

Не держать одну и ту же организацию одновременно:

- строкой в описании задачи;
- Property;
- отдельной Contact-карточкой.

Основной источник — Contact.

Для массового первоначального справочника также использовать Import.

## 5. Fleet: если ТС являются значимой сущностью

Если отдел регулярно работает с транспортными средствами, установить `Fleet` **до создания самодельного списка ТС в Project**.

Во Fleet заполнить/загрузить минимум:

- vehicle;
- license plate;
- model;
- driver — если требуется;
- остальные поля только если они реально поддерживаются и нужны процессу.

Дальше Fleet может самостоятельно хранить:

- services;
- odometer;
- contracts;
- costs;
- связанные отчёты.

### Критическое ограничение

Стандартный Project Task не имеет штатного поля Many2one на `fleet.vehicle`.

Поэтому **не делаем Property `ТС` на тысячи значений**.

В пилоте:

- Fleet используется как правильный master data реестр;
- необходимость строгой связи Task → Vehicle проверяется отдельно;
- если без неё невозможно управлять/анализировать значимый поток — это кандидат на минимальную доработку после пилота.

## 6. Maintenance: если учитывается оборудование

Установить `Maintenance`, если отдел должен вести:

- оборудование;
- терминалы;
- инструменты;
- внутреннее железо;
- corrective / preventive maintenance.

В Equipment хранить объект.

В Maintenance Request хранить ремонт/обслуживание.

Не создавать параллельно обычную Project Task на каждую maintenance request.

### Employees + Maintenance

При установленных Employees и Maintenance публичный Community-модуль `hr_maintenance` является штатным мостом между HR и оборудованием.

Это полезно для allocation tracking оборудования сотрудникам.

## 7. Создать основной операционный Project

Создать один основной проект, например:

```text
Операционная работа
```

Проект = общий контур обязательств одного отдела.

Не создавать заранее проекты:

```text
Табели
Топливо
Транспорт
Документы
Отчёты
Запросы
```

только потому, что это разные процессы.

Сначала процессы различаются классификацией и views.

## 8. Настроить Project visibility

Выбрать минимальную достаточную visibility-модель для внутренних пользователей.

Не включать portal/public sharing без реального внешнего сценария.

Если позже нужны external collaborators, Project штатно поддерживает режимы:

- Read;
- Edit with limited access;
- Edit.

До появления такого сценария внешний доступ не нужен.

## 9. Настроить Task Stages

Базовый набор:

```text
Входящие
Очередь
В работе
Ожидание внешнего
На проверке   ← только если нужна реальная независимая проверка
```

Не создавать `Готово` только для закрытия: закрытие выполняется State `Done` или `Canceled`.

### Что означает порядок

`Входящие` — зарегистрировано, не разобрано.

`Очередь` — готово к выполнению.

`В работе` — выполняется сейчас.

`Ожидание внешнего` — продолжение зависит от внешнего ответа/действия.

`На проверке` — результат действительно передан отдельному проверяющему.

## 10. Не настраивать Waiting как отдельный ручной Stage

При Task Dependencies Odoo вычисляет `Waiting` для blocked task.

Поэтому внутренняя зависимость:

```text
Blocked by = другая задача
```

а не:

```text
Stage = Ожидание
```

Внешнее ожидание и внутренняя блокировка остаются разными механизмами.

## 11. Properties

Через `Actions → Edit Properties` на задачах основного проекта создать только устойчивые небольшие признаки.

### `Вид работы`

Selection:

```text
Работа
Запрос
Улучшение
```

### `Процесс`

Добавлять только после того, как есть реальный список процессов и этот разрез будет использоваться в фильтрах/аналитике.

Не добавлять заранее:

- сотрудника;
- ТС;
- оборудование;
- организацию;
- длинные справочники.

## 12. Assignee

Технически Odoo допускает несколько Assignees.

Для операционной методики использовать одного владельца результата.

### Общая очередь

Неназначенная готовая работа:

```text
Stage = Очередь
Assignees = empty
```

Это и есть общий пул.

Не создавать пользователя:

```text
Общая очередь
Отдел
Смена
Группа
```

ради имитации группового исполнителя.

## 13. Deadline

Каждой задаче, где существует внешний или внутренний конечный срок, поставить Deadline.

Deadline = срок готовности результата.

Не использовать Deadline как дату:

- напоминания;
- звонка;
- проверки ответа.

Для этого Activity.

## 14. Allocated Time

Поле `Allocated Time` можно использовать для ожидаемой трудоёмкости.

На пилоте не делать обязательным.

Включать методически только если руководитель реально будет принимать решения по ожидаемой загрузке.

Не путать с Timesheets.

## 15. Priority

В модели Project Community доступны Low / Medium / High / Urgent.

На первом этапе не заставлять сотрудников тонко классифицировать каждую работу.

Рабочий минимум:

- обычная работа — базовый уровень;
- критичная — Urgent.

Medium/High вводить только после появления понятных критериев.

## 16. Tags

Tags использовать для лёгких поперечных меток, которые:

- не требуют отдельного master data;
- могут быть множественными;
- реально используются в фильтрах.

Не дублировать Tags и Properties с одинаковым смыслом.

## 17. Activities

Для типовых следующих действий использовать Activities.

Минимально полезные типы:

```text
Проверить
Напомнить
Позвонить
Встреча
```

Набор подбирается по фактической работе, а не ради полноты.

### Для внешнего ожидания

При переходе в `Ожидание внешнего` поставить Activity:

- кто делает follow-up;
- когда;
- что именно нужно проверить.

## 18. Activity Types: использовать chaining до Automation Rules

В настройке Activity Type при устойчивой последовательности можно использовать:

- `Suggest Next Activity`;
- `Trigger Next Activity`;
- Schedule после deadline предыдущей Activity;
- Schedule после completion date предыдущей Activity.

Пример:

```text
Проверить ответ
→ Trigger Next Activity через 2 дня
→ Напомнить
```

Если этого достаточно, Automation Rule не нужен.

## 19. Activity Plans

Создавать план только для повторяемого **набора нескольких контрольных действий вокруг одного результата**.

Пример:

```text
Запрос отправлен
→ проверить получение
→ проверить ответ
→ напомнить
→ эскалировать
```

Не использовать Activity Plan вместо нескольких самостоятельных результатов.

## 20. Task Dependencies

Включить `Task Dependencies` только если реально есть работы, где следующую нельзя начать до закрытия предыдущей.

В successor task заполнить `Blocked by`.

Не использовать dependency просто как тематическую связь.

## 21. Recurring Tasks

Включить для стабильной периодики одного результата.

Пример:

```text
Провести ежемесячную сверку X
```

Odoo создаёт следующую occurrence после Done/Canceled предыдущей.

Не создавать вручную 12 одинаковых задач на год.

Важно: Activities/Chatter/Subtasks не считаются автоматически переносимым шаблоном периодики. Структуру recurring task держать простой.

## 22. Subtasks

Создавать, когда часть результата имеет самостоятельное управление.

Не превращать каждый чек-лист в дерево из 20 subtasks.

Если нужен только список шагов одного исполнителя, использовать описание или Activities.

## 23. Rotting

После нескольких недель наблюдения определить, на каких Stages действительно полезен `Days to rot`.

Не задавать threshold вслепую.

Хороший кандидат:

- `Входящие`, если их должны разбирать быстро.

Сомнительный кандидат:

- `Ожидание внешнего`, если нормальный ответ может занимать долгое время.

После настройки создать Shared View `Залежавшиеся` по штатному Rotting filter.

## 24. Shared Favorites

Для каждого основного оперативного вопроса создать Saved Favorite.

Рекомендуемый набор:

### `Входящие`

```text
Project = Операционная работа
Stage = Входящие
Open
```

### `Очередь`

```text
Stage = Очередь
Open
```

### `Неназначенная очередь`

```text
Stage = Очередь
Unassigned
Open
```

### `В работе`

```text
Stage = В работе
Open
```

### `Просрочено`

```text
Deadline = Overdue
Open
```

### `Ожидание внешнего`

```text
Stage = Ожидание внешнего
Open
```

### `Блокировки`

Использовать штатные filters зависимостей / Waiting, когда Dependencies включены.

### `Критичные`

```text
Priority = Urgent
Open
```

### `Залежавшиеся`

```text
Rotting = true
Open
```

Shared Favorites должны быть доступны нужным пользователям, а не создаваться каждым заново.

## 25. Project Top Bar: общие кнопки рабочего места

Odoo 19 Project позволяет сохранить настроенное представление через `Save View` и сделать кнопку `Shared`.

После настройки filters/groupings создать верхние кнопки для наиболее частых views.

Рекомендуемый минимум:

```text
Входящие
Очередь
В работе
Просрочено
Ожидание
Критичные
```

Не нужно выносить в Top Bar каждый возможный фильтр.

## 26. List и Kanban использовать по разным задачам

### Kanban

Для визуального движения по Stages.

### List

Для контроля больших очередей, сортировки и массового просмотра полей.

Если задач много, ежедневный контроль руководителя чаще удобнее в List, а не в Kanban.

## 27. Task Analysis

После накопления реальных данных использовать `Project → Reporting → Tasks Analysis`.

Сначала ответить на простые вопросы:

- сколько создаётся;
- сколько закрывается;
- как меняется backlog;
- где просрочка;
- где Waiting;
- сколько времени до назначения;
- сколько времени до закрытия;
- в каких Stages копится хвост.

Не строить KPI, которых штатная модель не поддерживает надёжно.

## 28. My Dashboard

После стабилизации Shared Views установить/использовать Dashboards и собрать личный My Dashboard руководителя.

Добавлять Odoo views через Action → Dashboard.

Рекомендуемый состав первого экрана:

```text
Просрочено                  — List
Неназначенная очередь       — List
Критичные                   — List
Ожидание внешнего           — List
Открытые по Stage/Assignee  — Pivot
Закрытие по периодам        — Graph
```

My Dashboard не требует копирования данных в отдельный Excel.

## 29. Spreadsheet Dashboard

Не начинать с него.

Переходить к Spreadsheet Dashboard, когда:

- Shared Views уже работают;
- несколько периодов подряд используются одинаковые KPI;
- определены фильтры и меры;
- понятно, какое решение принимается по каждому показателю.

## 30. To-Do

To-Do оставить личным буфером.

Использовать для:

- мысли;
- личного напоминания;
- наблюдения;
- черновика будущей задачи.

Когда появляется обязательство отдела:

```text
To-Do → Convert to Task
```

Не вести общий backlog отдела в To-Do.

## 31. Discuss

Создать каналы только под реальную коммуникационную потребность.

Например:

```text
Рабочий канал отдела
Смена / оперативная координация
```

Но правило остаётся:

> если из сообщения следует обязательство, которое нельзя потерять — создать/обновить Project Task.

Не пытаться контролировать незавершённую работу чтением истории канала.

## 32. Calendar

Если Calendar установлен, использовать для:

- совещаний;
- встреч;
- событий с участниками;
- recurring meetings.

Не создавать Calendar Event вместо Activity или Task Deadline.

## 33. Email alias

Подключать только после стабилизации ручного входящего.

Настроить Project email alias и `Accept Emails From`.

Все новые email-задачи должны попадать в `Входящие`.

До включения письма определить:

- кто делает triage;
- что является дублем;
- какие письма вообще не должны становиться задачами;
- как обрабатывать автоответы/информационные письма.

## 34. Website Form

Если нужен простой intake и установлен Website:

1. создать/открыть страницу;
2. добавить Form block;
3. Action = `Create a Task`;
4. выбрать операционный Project;
5. настроить минимальный набор полей;
6. направлять созданные задачи во `Входящие`.

Не превращать форму в копию огромного Excel-реестра.

Если нужны сложные динамические справочники, validation и специализированная логика — это уже не простой website form.

## 35. Project sharing / portal

Не включать внешних пользователей без конкретного кейса.

Если внешний участник должен видеть проект, выбрать минимальный нужный Access Mode:

- Read;
- Edit with limited access;
- Edit.

Не давать Edit, если достаточно Read.

## 36. Timesheets

Включать только при конкретной цели:

```text
оценить фактическую трудоёмкость
сравнить план/факт
оценить стоимость
понять загрузку по типам работ
```

Перед включением:

- Employees должны быть корректно настроены;
- пользователи должны быть связаны с Employees;
- должны быть определены права Timesheets.

Не включать Timesheets только ради фиксации присутствия.

## 37. Automation Rules

Перейти к ним последними.

Порядок:

1. наблюдаем ручное действие;
2. убеждаемся, что правило всегда одинаково;
3. проверяем, не решается ли Activity chaining / Recurrence / Shared View;
4. включаем Developer Mode при необходимости;
5. `Settings → Technical → Automation → Automation Rules`;
6. создаём одно узкое правило;
7. проверяем на тестовых данных;
8. только потом расширяем.

Не создавать десятки автоматизаций одновременно.

## 38. Что импортировать, а что создавать руками

### Импортировать

Если уже есть качественный источник:

- Employees;
- Contacts;
- Fleet vehicles;
- Equipment — если формат и модель подходят;
- другие большие справочники штатных моделей.

### Создавать руками

- Stages;
- небольшие Tags;
- Properties;
- Activity Types;
- Activity Plans;
- Shared Views;
- Top Bar buttons;
- Automation Rules.

## 39. Правило External ID для справочников

Для массово обновляемого справочника хранить стабильный External ID.

Рабочий цикл:

```text
Export import-compatible
→ сохранить External ID
→ изменить нужные поля
→ Import
→ Test
→ Import
```

Не менять External ID между загрузками: иначе вместо обновления можно получить дубли.

## 40. Пилотные сценарии, которые нужно реально прогнать

Перед признанием методики рабочей выполнить в интерфейсе минимум:

1. ручное входящее → triage → очередь → работа → Done;
2. неназначенная задача → взятие исполнителем;
3. внешнее ожидание + Activity → ответ → Done;
4. внутренняя dependency → Waiting → разблокировка;
5. recurring task → закрытие → появление следующей occurrence;
6. task with subtask;
7. shared favorite другим пользователем;
8. shared Top Bar view другим пользователем;
9. overdue task в общем представлении;
10. Rotting task после тестового threshold;
11. To-Do → Convert to Task;
12. Task Analysis Pivot/Graph;
13. добавление view в My Dashboard;
14. Import небольшого справочника с `Test`;
15. повторный импорт по External ID без дубля;
16. Fleet vehicle + стандартный Fleet report, если Fleet в пилоте;
17. Maintenance Equipment + Request, если Maintenance в пилоте.

Опционально после стабилизации:

18. email alias → задача;
19. Website Form → задача;
20. Activity chaining;
21. Automation Rule;
22. Timesheet.

## 41. Критерии успешного пилота

Пилот считается успешным, если без Excel-реестра можно ответить:

- что сейчас не разобрано;
- что готово к выполнению;
- что реально выполняется;
- что просрочено;
- что критично;
- что ждёт внешнего;
- что заблокировано внутренней задачей;
- у кого находится работа;
- где копится хвост;
- что создано и закрыто за период;
- какие справочники являются источником истины;
- какие данные невозможно корректно связать без доработки.

## 42. Критерии для минимальной доработки

После пилота каждый разрыв записывается отдельно.

Пример:

```text
Проблема:
невозможно надёжно анализировать Project Tasks по ТС.

Есть штатно:
Fleet Vehicle + Project Task.

Нет штатно:
Many2one Task → Fleet Vehicle.

Ручной обход:
Property Selection на тысячи ТС — неприемлем.

Решение:
одно поле vehicle_id + отображение/фильтр/группировка.
```

Такой разрыв является нормальным основанием для минимального модуля.

Не является основанием:

```text
«хочется другой Kanban»
«хочется собственные комментарии»
«хочется собственные задачи»
```

если штатный механизм уже решает задачу.

## 43. Последовательность внедрения

```text
1. Users + Employees
2. Contacts
3. Fleet / Maintenance — только если нужны предметно
4. Project
5. Stages + Assignee + Deadline + Priority
6. минимальные Properties / Tags
7. Activities
8. Dependencies / Recurrence / Subtasks по потребности
9. Shared Favorites
10. Shared Top Bar Views
11. Task Analysis
12. Rotting после наблюдения
13. My Dashboard
14. Import/Export процедуры для справочников
15. Activity chaining / Activity Plans по факту
16. email / Website intake по факту
17. Timesheets по факту
18. Automation Rules по факту
19. список подтверждённых click-only gaps
20. минимальный custom module только на эти gaps
```

Не менять порядок так, чтобы Dashboard и Automation появились раньше достоверных исходных данных.
