# Настройка Odoo 19 Community

[Главная](../README.md) · [00 Возможности Odoo](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [02 Сценарии](02-scripts.md) · [03 Контроль и аналитика](03-control.md) · [04 Шаблоны](04-templates.md) · [05 Процессы](05-processes.md) · **06 Настройка**

---

Здесь фиксируется **минимальная конфигурация, которую можно собрать штатным интерфейсом Odoo 19 Community**.

Цель первого контура — не реализовать все возможные функции, а получить достоверную очередь, ответственность, сроки, ожидание и аналитику без собственного кода.

## 1. Что включить

Обязательная основа:

- `Проекты` (`Project`).

Штатные Chatter и Activities используются в задачах как часть платформы Odoo.

Не включать заранее только потому, что функция существует:

- Timesheets;
- дополнительные приложения;
- отдельные Dashboard;
- Milestones;
- email alias;
- лишние проекты.

Они подключаются ниже только при конкретной потребности.

## 2. Создать основной рабочий проект

Создать один проект, например:

```text
Операционная работа
```

Это основной контур регулярной работы подразделения.

На старте не создавать проекты на каждый процесс, сотрудника, участок или вид задачи.

В настройках проекта определить видимость, соответствующую реальному составу участников.

## 3. Создать этапы

В Kanban проекта создать колонки в таком порядке:

```text
Входящие
Очередь
В работе
Ожидание внешнего
```

На первом запуске **не создавать** отдельные этапы:

- `Готово`;
- `Отменено`;
- `Waiting`;
- `Просрочено`;
- `Срочно`.

Причины:

- `Done` и `Canceled` уже являются системными статусами закрытия;
- внутренний `Waiting` управляется зависимостями;
- просрочка определяется Deadline;
- срочность определяется Priority.

### `На проверке`

Добавить этот этап только если существует устойчивый процесс, где результат действительно должен проходить отдельную проверку.

Не добавлять его «на всякий случай».

## 4. Настроить свойства задач

Открыть любую задачу основного проекта и использовать:

```text
Действия → Изменить свойства / Edit Properties
```

### Свойство 1 — `Вид работы`

Тип: `Selection`.

Значения:

```text
Работа
Запрос
Улучшение
```

Это аналитический признак. Он не создаёт отдельный workflow.

### Свойство 2 — `Процесс`

Тип: `Selection`.

Добавить только устойчивые процессы, по которым действительно нужен фильтр или анализ.

Пример:

```text
Сверка данных
Корректировка данных
Учёт документов
Отчётность
```

Фактический список определяется при описании реальных процессов.

Если процессов много и справочник часто меняется, не пытаться бесконечно расширять Selection до проектирования нормального справочника. Это сигнал отдельно проверить модель данных.

### Другие свойства

Не добавлять на старте.

Новое Property допустимо, если одновременно понятно:

1. кто его заполняет;
2. зачем оно нужно;
3. по нему реально фильтруют/группируют/принимают решение;
4. штатный тип Property подходит без костыля.

Если нужен справочник существующих записей Odoo, Properties поддерживают ссылочные типы на модели. Это можно использовать отдельно после проверки конкретного справочника.

## 5. Приоритет

Использовать штатное поле Priority.

Базовое правило:

- обычная работа — минимальный штатный приоритет;
- критичная работа — `Urgent`.

Средние уровни не вводятся в методику, пока нет реальной потребности.

Не создавать отдельное Property `Критичность`: штатное поле уже решает эту задачу.

## 6. Исполнитель

Штатное поле Assignees технически допускает нескольких пользователей.

Правило рабочего контура:

- `Входящие` и общая `Очередь` могут быть без исполнителя;
- при фактическом взятии задачи назначается один ответственный за конечный результат;
- остальные участники не добавляются в Assignees просто для информирования.

Для участия использовать по смыслу:

- Followers;
- Chatter;
- Activity;
- подзадачу с собственным ответственным.

Не создавать искусственную сущность «групповой исполнитель».

## 7. Deadline и Activities

В каждой контролируемой задаче Deadline означает конечный срок результата.

Для промежуточных действий использовать Activities:

- проверить ответ;
- напомнить;
- позвонить;
- запросить уточнение;
- провести проверку результата.

Особенно важно: задача в `Ожидание внешнего` по умолчанию должна иметь следующую Activity, если follow-up нужен в определённую дату.

## 8. Включить Task Dependencies

В настройках проекта включить `Task Dependencies`, если в работе есть реальные внутренние блокировки.

Использование:

```text
Задача → Blocked by → добавить блокирующую задачу
```

После этого Odoo сам использует системный статус `Waiting` для зависимой задачи.

Не использовать зависимость для простой тематической связи.

Если внутренних блокировок фактически нет, функцию можно не включать на первом пилоте.

## 9. Включить Recurring Tasks

В настройках проекта включить `Recurring Tasks` для регулярных работ.

Настроить повторение на первой реальной периодической задаче.

Учитывать штатную механику:

- новый экземпляр создаётся после `Done` или `Canceled` предыдущего;
- следующий экземпляр попадает в первый этап проекта;
- Name, Description, Project, Assignees, Customer и Tags копируются;
- Deadline пересчитывается;
- Activities, Chatter, Milestones, Timesheets и Subtasks не копируются.

Поэтому первым этапом проекта является `Входящие`: новый повтор нужно увидеть и при необходимости проверить перед отправкой в очередь.

Не создавать параллельно ручной календарь будущих карточек.

## 10. Подзадачи

Использовать штатные Subtasks без отдельной кастомизации.

Подзадача создаётся только для самостоятельной части общего результата.

Если нужен лишь следующий шаг по той же задаче — Activity обычно проще и точнее.

## 11. Milestones

В основном операционном проекте не включать без потребности.

Milestones полезны для отдельной инициативы/проекта, где несколько задач должны привести к общей контрольной точке с датой.

Не использовать вехи как ещё один классификатор операционных задач.

## 12. Email alias — только после стабилизации входящих

Odoo умеет создавать задачи проекта из входящих писем через email alias.

Не включать это сразу, если:

- письма часто относятся к уже существующим задачам;
- нет правила дедупликации;
- в почтовом ящике много информационных писем без обязательства;
- неизвестно, кто разбирает автоматически созданные задачи.

Если alias включён, все новые письма попадают в первый этап `Входящие` и дальше проходят обычный разбор.

## 13. Создать сохранённые фильтры

Через строку поиска, `Filters`, `Group By` и `Favorites` создать рабочие представления.

Минимум:

### `Входящие`

```text
Open + Stage = Входящие
```

### `Общая очередь`

```text
Open + Stage = Очередь + Unassigned
```

### `Моя очередь`

```text
Open + Stage = Очередь + My Tasks
```

### `Моя работа`

```text
Open + Stage = В работе + My Tasks
```

### `Просрочено`

```text
Open + Deadline = Overdue
```

### `Ожидание внешнего`

```text
Open + Stage = Ожидание внешнего
```

### `Внутренние блокировки`

```text
Open + Status = Waiting
```

### `Критичные`

```text
Open + Priority = Urgent
```

Сохранить Favorites. Общие представления публиковать/делиться ими только там, где это упрощает работу команды.

## 14. Оперативная работа: Kanban и List выполняют разные задачи

### Kanban

Использовать для:

- визуального движения между этапами;
- быстрого понимания структуры потока;
- работы с Activities на карточках.

### List

Использовать для:

- большой очереди;
- сортировки и сравнения Deadline;
- массового просмотра ответственных, приоритетов и свойств;
- оперативного контроля исключений.

Не пытаться заставить одну Kanban-доску быть одновременно диспетчерским списком, отчётом и аналитической панелью.

## 15. Настроить базовую аналитику

После того как задачи начали вестись достоверно, открыть стандартный анализ задач и проверить Pivot/Graph.

Первый набор вопросов:

- сколько задач создаётся и закрывается;
- сколько остаётся открытыми;
- где концентрируется просрочка;
- где растёт внешнее ожидание;
- где есть внутренние блокировки;
- какие процессы создают основной хвост;
- где растёт время назначения/закрытия.

Группировки использовать по:

- Project;
- Stage;
- Assignee;
- Priority;
- свойствам `Процесс`/`Вид работы`, если они доступны в выбранном представлении;
- временному периоду.

Не создавать Dashboard раньше, чем эти вопросы стабилизировались.

## 16. Dashboard — второй этап

Когда набор управленческих показателей перестал меняться каждую неделю, можно собрать штатный Dashboard/Spreadsheet Dashboard.

На него выносятся только показатели, по которым есть регулярное решение.

Не делать отдельный график на каждый доступный показатель.

## 17. Timesheets — только при отдельной задаче управления

Включить учёт времени, если нужно:

- оценивать трудоёмкость процессов;
- понимать загрузку мощности;
- считать стоимость;
- сопоставлять план/факт времени.

Не включать Timesheets только ради контроля присутствия или рейтинга сотрудников.

## 18. Права и роли

Настроить штатные права доступа к приложению и видимость проекта в соответствии с реальными ролями.

Не закладывать в базовую конфигурацию несуществующую no-code матрицу вида:

```text
исполнитель может только X → Y,
старший только Y → Z,
руководитель единственный может закрыть.
```

Если такая техническая принудительность действительно обязательна, это отдельное требование к доработке/другому механизму, а не настройка базового Project.

Методические роли остаются:

- исполнитель;
- старший;
- руководитель.

Они определяют решения и ответственность, а не имитируют технический BPM.

## 19. Что проверить на пилоте

Перед расширением контура вручную пройти реальные сценарии:

- [ ] входящая задача без исполнителя;
- [ ] разбор и перевод в общую очередь;
- [ ] самоназначение/назначение старшим;
- [ ] фактическая работа;
- [ ] внешний запрос + Activity;
- [ ] внутренняя зависимость `Blocked by` и системный `Waiting`;
- [ ] просрочка без переноса Deadline;
- [ ] `Urgent`-задача;
- [ ] передача другому исполнителю;
- [ ] подзадача;
- [ ] повторяющаяся задача и создание следующего экземпляра;
- [ ] `Done`;
- [ ] `Canceled`;
- [ ] повторное открытие ошибочно закрытого результата;
- [ ] фильтры `Входящие`, `Общая очередь`, `Просрочено`, ожидания;
- [ ] Pivot/Graph по реальным данным.

## 20. Что не делать на первом запуске

- не писать собственный модуль;
- не ставить OCA-модули только ради красивой схемы;
- не создавать десятки Properties;
- не делать проект на каждый процесс;
- не создавать отдельные типы карточек кодом;
- не добавлять ручной `Waiting`;
- не дублировать `Done` этапом `Готово`;
- не создавать будущее периодики вручную;
- не вводить Timesheets без задачи;
- не строить Dashboard до стабилизации данных;
- не переносить Excel-реестр один в один в форму задачи.

После пилота фиксируются только реальные ограничения. Именно они определяют, нужна ли доработка Odoo и какая.
