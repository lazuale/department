# Настройка рабочего контура в OpenProject Community

## 1. Цель конфигурации

Конфигурация должна поддерживать методику без лишних сущностей и ручных действий.

Приоритет: простота, единообразие, читаемость очереди и управленческих представлений.

## 2. Иерархия проектов

Рекомендуемая структура:

```text
Рабочий контур
├── Операционная работа
├── Регламентные работы
├── Развитие и автоматизация
└── Проекты
    ├── Проект A
    └── Проект B
```

Отдельный Project не создаётся под отдельную Category или единичное поручение.

## 3. Work Package Types

Минимальный набор:

| Type | Назначение |
|---|---|
| `Работа` | любой обязательный самостоятельно контролируемый результат |
| `Запрос` | самостоятельный исходящий запрос |
| `Идея` | backlog развития и автоматизации |

Другие Types создаются только при отдельном lifecycle.

## 4. Статусы

Обязательный набор:

1. `Очередь` — open;
2. `В работе` — open;
3. `Ожидание` — open;
4. `Готово` — closed;
5. `Отменено` — closed.

Не добавлять промежуточные статусы без отдельного методического решения.

## 5. Workflow

### Исполнитель

Разрешённые переходы:

- `Очередь → В работе`;
- `Очередь → Отменено` — если роль имеет право отмены;
- `В работе → Ожидание`;
- `В работе → Готово`;
- `Ожидание → В работе`;
- `Ожидание → Очередь`;
- `Готово → В работе` — если исполнителю разрешён самостоятельный reopen.

### Руководящая роль

Дополнительно имеет право:

- менять владельца;
- корректировать приоритет;
- корректировать срок;
- отменять;
- переоткрывать;
- перераспределять работу.

## 6. Categories

Categories создаются внутри рабочих проектов как справочник устойчивых бизнес-процессов.

Правила:

- не кодировать статус;
- не кодировать срочность;
- не кодировать временный проект;
- не создавать категорию под каждый вид документа;
- не создавать категорию под конкретного исполнителя.

Список Categories должен быть коротким и стабильным.

## 7. Priority

Используются:

- `Обычный`;
- `Высокий`;
- `Критичный`.

Если стандартная конфигурация содержит дополнительные уровни, методика всё равно оперирует указанными тремя смысловыми уровнями.

## 8. Обязательные атрибуты операционной Work Package

При создании обязательной работы должны быть определены:

- Subject;
- Type;
- Category;
- Status;
- Assignee или групповая очередь;
- Finish date;
- Priority.

Description и attachments заполняются только в объёме, необходимом для выполнения и подтверждения основания.

## 9. Основная доска

Создаётся Status board:

```text
Очередь | В работе | Ожидание | Готово
```

`Отменено` в основную ежедневную доску не выводится.

Доска используется для визуального понимания потока, но не для контроля сроков вместо таблиц.

## 10. Сохранённые Work Package views

### Для исполнителя

`Моя работа`

Фильтры:

- открытые;
- Assignee = текущий пользователь или его рабочая группа.

Колонки:

- ID;
- Subject;
- Type;
- Category;
- Status;
- Priority;
- Finish date.

Сортировка:

1. Priority;
2. Finish date;
3. ID/дата создания.

### Для управления

Обязательные views:

- `Вся активная работа`;
- `Очередь`;
- `В работе`;
- `Ожидание`;
- `Просрочено`;
- `Без исполнителя`;
- `Критичные`;
- `По Category`;
- `По Assignee`;
- `Готово за период`.

## 11. Backlogs

Backlogs используются только в проекте `Развитие и автоматизация`.

Buckets:

1. `Inbox`;
2. `Наблюдаем`;
3. `Разобрать`;
4. `Кандидат`;
5. `Готово к реализации`.

Идеи не размещаются на операционной Status board.

## 12. Parent/child и relations

Использовать parent/child, когда одна крупная работа состоит из независимо контролируемых результатов.

Использовать relations для:

- связанных результатов;
- нового объёма после предыдущей работы;
- самостоятельного запроса, обслуживающего основную работу;
- связи идеи с подтверждающими её фактами;
- дубликатов.

Не создавать child Work Package на обычные технические шаги одного исполнителя.

## 13. Регламентные работы

Проект `Регламентные работы` содержит отдельные экземпляры каждого периода.

Рекомендуется заранее создавать/дублировать будущие экземпляры на утверждённый горизонт планирования.

Название обязательно содержит период.

## 14. Meetings

Meetings используются для управленческих решений и разбора исключений.

Повестка строится вокруг:

- просрочки;
- старых работ;
- ожиданий;
- конфликтов приоритетов;
- системных проблем;
- решений по backlog улучшений.

Meetings не используются для поочерёдного устного отчёта всех сотрудников о нормальной работе.

## 15. Права

Минимальная модель:

### Исполнитель

- просмотр рабочих проектов;
- создание Work Package в пределах разрешённого контура;
- редактирование доступных работ;
- изменение статуса по workflow;
- комментарии и вложения;
- назначение на себя при pull-модели.

### Руководящая роль

- все действия исполнителя;
- изменение владельцев и сроков;
- управление приоритетом;
- отмена и reopen;
- управление views/boards по принятой модели.

### Администратор

- Types;
- Statuses;
- Workflows;
- Roles;
- Projects;
- системная конфигурация.

Удаление рабочих Work Package не является обычным правом исполнителя.

## 16. Что не настраивается без необходимости

Не создавать заранее:

- большое число Types;
- десятки Categories;
- сложные иерархии проектов;
- отдельные проекты под каждую функцию;
- дополнительные статусы;
- дублирующие представления;
- обязательные поля, которые не используются для управления.

Конфигурация должна оставаться минимальным отражением принятой методики.
