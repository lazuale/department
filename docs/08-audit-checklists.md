# Аудит соблюдения методики

## 1. Цель

Аудит проверяет не формальное наличие карточек, а достоверность рабочего контура.

Главный вопрос: **можно ли по системе без дополнительных опросов понять фактическое состояние обязательной работы**.

---

# 2. Аудит входящего потока

Проверить выборку входящих сообщений и оснований.

- [ ] каждое обязательное действие породило Work Package либо добавлено к существующей;
- [ ] информационные сообщения не создают лишние Work Package;
- [ ] по одной теме не создаются необоснованные дубли;
- [ ] вложения и существенный контекст прикреплены к правильной работе;
- [ ] нет сообщений с состоянием `потом разберём` без фиксации;
- [ ] на конец рабочего периода вход разобран до установленного уровня.

Критический дефект: обязательная работа существует только во внешнем канале.

---

# 3. Аудит статусов

Для случайной выборки открытых Work Package задать фактический вопрос.

### Очередь

- [ ] работу прямо сейчас никто не выполняет;
- [ ] она действительно обязательна;
- [ ] срок актуален;
- [ ] владелец/группа определены либо карточка находится в контролируемом view `Без исполнителя`.

### В работе

- [ ] исполнитель реально выполняет работу сейчас;
- [ ] это не просто назначенная на будущее работа;
- [ ] Assignee соответствует фактическому владельцу.

### Ожидание

- [ ] существует реальная внешняя блокировка;
- [ ] Assignee сохранён;
- [ ] в Activity понятно, что ожидается;
- [ ] Finish date не потерял смысл;
- [ ] карточка не забыта после перевода в ожидание.

### Готово

- [ ] достигнут DoD;
- [ ] нет обязательного действия, оставшегося только в почте/чате;
- [ ] работа не закрыта только потому, что отправлен запрос.

Критический дефект: статус систематически не соответствует факту.

---

# 4. Аудит WIP

- [ ] `В работе` не используется как склад назначенных задач;
- [ ] у сотрудников нет необъяснимо большого активного WIP;
- [ ] работы, которые фактически остановлены, переведены в `Очередь` или `Ожидание`;
- [ ] при передаче владельца Assignee обновляется.

Сигнал деградации: большая часть открытых работ находится `В работе`.

---

# 5. Аудит сроков

- [ ] обязательные работы имеют Finish date;
- [ ] внешний срок не подменён датой напоминания;
- [ ] перенос срока объясним по Activity;
- [ ] просроченные работы попадают в управленческий обзор;
- [ ] срок не меняется только для сокрытия просрочки.

Критический дефект: сроки массово переносятся без изменения условий.

---

# 6. Аудит гранулярности

### Признаки слишком мелких Work Package

- [ ] отдельные карточки создаются на письма;
- [ ] отдельные карточки создаются на звонки;
- [ ] отдельные карточки создаются на обычные шаги одного исполнителя;
- [ ] один реальный результат искусственно дробится для увеличения количества закрытий.

### Признаки слишком крупных Work Package

- [ ] в одной карточке несколько независимых исполнителей;
- [ ] разные части имеют разные сроки;
- [ ] одна часть может быть завершена, пока другая заблокирована;
- [ ] невозможно однозначно определить готовность всей работы.

---

# 7. Аудит Category

- [ ] каждая Category обозначает устойчивый бизнес-процесс;
- [ ] нет категорий, кодирующих срочность;
- [ ] нет категорий, созданных под конкретного сотрудника;
- [ ] нет временных одноразовых категорий;
- [ ] нет нескольких почти одинаковых категорий;
- [ ] новые Category создавались через контрольный шаблон.

Сигнал деградации: число Category растёт быстрее числа устойчивых процессов.

---

# 8. Аудит запросов

- [ ] отдельный Type `Запрос` используется только для самостоятельного результата;
- [ ] обычные уточнения внутри работы не создают дополнительные карточки;
- [ ] отправленный запрос переводится в `Ожидание`, если активных действий больше нет;
- [ ] полученный ответ возвращает запрос в фактическое состояние;
- [ ] самостоятельные запросы не теряются после отправки.

---

# 9. Аудит регламентных работ

- [ ] каждый период имеет отдельную Work Package;
- [ ] будущие периоды созданы на утверждённый горизонт;
- [ ] Subject содержит период;
- [ ] срок периода задан корректно;
- [ ] одна карточка не используется бесконечно для разных периодов;
- [ ] пропуск создания очередного периода обнаруживается до дедлайна.

---

# 10. Аудит передачи работы

- [ ] отсутствующий исполнитель не остаётся владельцем фактически продолжаемой работы;
- [ ] остановленная работа не остаётся `В работе`;
- [ ] при ожидании сохранён контекст;
- [ ] следующая сторона видит активный поток без отдельного полного реестра передачи;
- [ ] в комментариях передаётся только дополнительный контекст, а не копия всей карточки.

---

# 11. Аудит завершения и reopen

- [ ] DoD определён для основных Category;
- [ ] новый дополнительный объём не оформляется reopen;
- [ ] ошибка первоначального результата оформляется reopen;
- [ ] причина возврата фиксируется;
- [ ] reopen анализируется как сигнал качества.

---

# 12. Аудит контроля качества

- [ ] обычный поток не требует обязательной проверки перед закрытием;
- [ ] существует выборочная проверка обычных завершённых работ;
- [ ] риск-контроль не смешивается со случайной выборкой;
- [ ] ошибка возвращает исходную Work Package в работу;
- [ ] результаты контроля не используются без контекста как рейтинг сотрудников.

---

# 13. Аудит управленческих представлений

Должны быть рабочими и используемыми:

- [ ] Моя работа;
- [ ] Вся активная работа;
- [ ] Очередь;
- [ ] В работе;
- [ ] Ожидание;
- [ ] Просрочено;
- [ ] Без исполнителя;
- [ ] Критичные;
- [ ] По Category;
- [ ] По Assignee;
- [ ] Готово за период.

Неиспользуемые и дублирующие views удаляются.

---

# 14. Аудит управленческого поведения

- [ ] руководство разбирает исключения, а не просматривает каждую работу;
- [ ] количество закрытых Work Package не превращено в прямой KPI человека;
- [ ] сотрудники не мотивированы дробить работу ради статистики;
- [ ] срочность не используется для обхода нормальной очереди без причины;
- [ ] backlog идей не смешан с обязательной работой;
- [ ] проекты не создаются под каждое поручение.

---

# 15. Аудит backlog улучшений

- [ ] каждая идея содержит проблему/наблюдение;
- [ ] дубли объединяются;
- [ ] неактуальные идеи закрываются;
- [ ] `Готово к реализации` содержит только реально подготовленные инициативы;
- [ ] крупные идеи связаны с фактами из операционного потока;
- [ ] после внедрения проверяется эффект.

---

# 16. Красные флаги системы

Немедленного разбора требуют следующие признаки:

1. большинство открытых Work Package находятся `В работе`;
2. `Ожидание` стабильно растёт и почти не уменьшается;
3. Finish date массово отсутствует;
4. просрочка исчезает за счёт переноса сроков;
5. Category постоянно плодятся;
6. сотрудники ведут параллельный Excel/чат-реестр обязательной работы;
7. обычные работы требуют обязательного согласования старшим;
8. одна Work Package живёт месяцами за счёт новых объёмов;
9. backlog развития содержит десятки `готовых к реализации` инициатив без ресурса;
10. Dashboard выглядит хорошо, но во внешних каналах остаётся незарегистрированная работа.

---

# 17. Формат результата аудита

Для каждого дефекта фиксируется:

```text
Нарушение:
<что именно не соответствует методике>

Риск:
<какой управленческий эффект возникает>

Пример:
<ID/обезличенный случай>

Корневая причина:
<почему правило не работает>

Корректирующее действие:
<что меняем в процессе/настройке/обучении>

Владелец:
<роль>

Срок проверки:
<дата>
```

Цель аудита — исправить систему работы, а не накопить список формальных нарушений.
