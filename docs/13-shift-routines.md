# Сменная работа и регламентные циклы в Odoo 19 Community

[Главная](../README.md) · [00 Возможности](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [06 Настройка](06-workspace.md) · **13 Смены и регламентные циклы**

---

Этот документ проверяет, насколько штатный Odoo 19 Community подходит для сменной операционной работы без Enterprise Planning.

## 1. Resource Calendar — рабочий календарь, не сменный диспетчер

Public Community `resource` поддерживает рабочие календари с:

- днями недели;
- интервалами рабочего времени;
- fixed/flexible schedule;
- timezone;
- leaves;
- двухнедельным режимом.

В `resource.calendar.attendance` подтверждено:

```text
dayofweek = Monday ... Sunday
week_type = First / Second
two_weeks_calendar = True/False
```

Источник: [`resource_calendar_attendance.py`](https://github.com/odoo/odoo/blob/19.0/addons/resource/models/resource_calendar_attendance.py).

## 2. Двухнедельный режим не является произвольным циклом

Two-week calendar повторяет:

```text
First week
Second week
First week
Second week
...
```

Это цикл 14 календарных дней.

Чистый график `2 рабочих / 2 выходных` имеет цикл 4 дня.

Поскольку 14 не кратно 4, обычный repeating two-week calendar не представляет бесконечный 2/2 без сдвига/исключений корректно.

### Методический вывод

Не заявлять:

> Resource Calendar штатно закрывает любой 2/2 график.

Корректно:

> Resource Calendar можно использовать для нормативных working schedules, но произвольный rotating shift cycle требует отдельной проверки/обхода и не является эквивалентом Enterprise Planning.

## 3. Attendances не решает планирование смен

Attendances фиксирует фактический:

```text
Check In
Check Out
```

и связанные overtime/attendance rules.

Он отвечает на вопрос:

> Когда человек фактически отметился как присутствующий?

а не:

> Кто должен быть назначен на следующую смену?

Не использовать Attendances как планировщик состава смены.

## 4. Work Entries также не являются Planning

Work Entries — HR-интервалы рабочего времени/типов работ, связанные с resource calendars.

Это расчётно-кадровый слой, а не Kanban распределения дежурств.

## 5. Recurring Task не умеет интервал в часах

Public `project.task.recurrence` поддерживает:

```text
Days
Weeks
Months
Years
```

Поля:

```python
repeat_interval
repeat_unit = day / week / month / year
```

Источник: [`project_task_recurrence.py`](https://github.com/odoo/odoo/blob/19.0/addons/project/models/project_task_recurrence.py).

Следовательно, штатно нельзя настроить:

```text
Repeat every 12 hours
```

через обычный Recurring Task UI/model.

## 6. Но дневную и ночную передачу можно представить двумя независимыми daily chains

Если нужен отдельный контролируемый артефакт **каждой дневной и каждой ночной передачи**, возможен click-only вариант:

```text
Recurring Task A
Передать дневную смену
Deadline time = <время окончания дневной>
Repeat every 1 day

Recurring Task B
Передать ночную смену
Deadline time = <время окончания ночной>
Repeat every 1 day
```

`date_deadline` — Datetime, а source recurrence добавляет `relativedelta(days=1)`, поэтому время суток сохраняется.

### Ограничение

Следующая occurrence создаётся только после `Done`/`Canceled` предыдущей.

Если предыдущая передача не закрыта, новая автоматически не появится.

Это может быть как полезным контролем дисциплины, так и нежелательной блокировкой цепочки. Нужно испытать на пилоте.

## 7. Не фиксировать конкретного сменного исполнителя в recurrence без проверки

Официальная документация говорит, что Assignees копируются в следующую recurring Task.

Если исполнители меняются по графику 2/2, постоянный Assignee в recurring chain может быть неправильным.

Практический stock-вариант:

```text
recurring handover Task
→ Assignee empty
→ Stage = первый Stage / затем triage
→ фактический старший смены берёт Task
```

или заранее назначать только если roster поддерживается другим надёжным механизмом.

Не создавать fake-users `Дневная смена` / `Ночная смена` ради назначения.

## 8. Task Template полезен для содержания передачи смены

Если каждая смена должна проверить одинаковый набор смысловых пунктов, Task Template может задавать устойчивую структуру:

```text
Название:
Передать смену

Описание:
1. Незакрытые критичные работы
2. Просрочки / риски
3. Внешние ожидания, требующие реакции следующей смены
4. Технические/системные отклонения
5. Что обязательно сделать в следующей смене
```

Но Task Template и Recurrence — разные механизмы.

Для автоматической daily chain основой остаётся Recurring Task; template полезен для ручного создания/восстановления или иных однотипных сменных records.

## 9. Не переносить весь backlog в «журнал смены»

Главная опасность отдельной handover Task — дублирование существующих Tasks.

В передаче не нужно переписывать:

- все открытые работы;
- их Deadline;
- Assignees;
- Properties;
- полную историю.

Эти данные уже находятся в Odoo.

Handover фиксирует только **исключения и контекст, которого нельзя понять из самой очереди**.

## 10. Лучший baseline передачи смены — Shared Views + короткий handover record

Перед передачей следующая смена уже должна видеть:

```text
Urgent
Overdue
В работе
Ожидание внешнего
Waiting
Неназначенная очередь
Late Activities
```

через Shared Views.

Отдельная handover Task нужна только для неструктурированного контекста, например:

```text
«Внешняя система нестабильна, не запускать повторную загрузку до подтверждения»
```

или:

```text
«По Task X созвонились, обещали ответ в 09:00; при отсутствии — звонить Y»
```

Если эта информация относится к конкретной Task, предпочтительно оставить её в Chatter/Activity той Task, а не дублировать в журнале.

## 11. Discuss channel может помогать оперативной координации, но не быть журналом обязательств

Для смены допустим общий Discuss channel:

```text
Оперативная координация
```

Он полезен для быстрых сообщений.

Но сообщение, которое должно пережить смену и требует результата, превращается в Project Task или обновляет существующую.

История чата не является системой контроля незавершённой работы.

## 12. Scheduled message не заменяет handover

Scheduled email/message подходит, когда заранее известно, **что именно** должно отправиться в конкретное время.

Передача смены обычно требует фактического обзора текущих исключений, поэтому полностью автоматический scheduled message не заменяет её.

Можно автоматизировать напоминание о необходимости передачи, но не сам содержательный handover без надёжной модели данных.

## 13. Automation Rules: можно помочь, но не построить полноценный roster

Community Automation Rules умеют time-based triggers и использование Resource Calendar для рабочих дней.

Это позволяет автоматизировать конкретные действия вокруг существующих records.

Но `base_automation` не является полноценным roster engine для произвольного 2/2 состава смен.

Не строить сложную систему расписания из десятков Automation Rules, если реальная потребность — Planning/roster.

## 14. Расхождение документации и source по Recurring Subtasks

Официальная документация Odoo 19 говорит:

> Subtasks не копируются в следующую recurring Task.

Однако текущий public source `project_task_recurrence.py` в `_create_next_occurrences_values()` явно рекурсивно создаёт:

```python
'child_ids': [Command.create(vals) for vals in ...]
```

### Методический вывод

Это расхождение source ↔ documentation нельзя разрешать догадкой.

Перед использованием recurring subtasks в критичном регламенте обязательно выполнить runtime-тест на конкретной установленной версии Odoo 19.

До этого не строить процесс, зависящий от автоматического копирования Subtasks.

## 15. Аналогично проверить Properties в recurrence

`task_properties` имеет `copy=True`, а recurrence использует `copy_data()`.

Это указывает, что Properties могут переноситься в следующий экземпляр.

Но официальная документация не перечисляет Properties среди гарантированно копируемых полей.

Поэтому на стенде отдельно проверить:

- Selection Properties;
- Many2one Properties;
- Many2many Properties;
- изменение Property между occurrences.

Особенно важно не переносить конкретный Vehicle/Employee автоматически там, где объект должен меняться каждую смену/период.

## 16. Priority recurrence source сбрасывает

Текущий public source при создании следующей occurrence явно задаёт:

```python
'priority': '0'
```

То есть текущий код сбрасывает Priority нового экземпляра на базовый уровень.

Не рассчитывать, что `Urgent` автоматически сохранится в recurring chain.

Это тоже нужно подтвердить runtime-тестом, если Priority периодической Task имеет значение.

## 17. Что действительно является gap для сменной работы

После аудита можно отделить:

### Штатно закрывается

- общая очередь;
- текущие Assignees;
- Deadline;
- handover через Task/Chatter;
- daily recurring chain;
- Shared Views;
- Activities;
- Attendances как факт присутствия;
- Working Schedules как HR-календарь.

### Не подтверждено как полноценная click-only функция

- произвольный rotating roster 2/2;
- автоматическое назначение сменного состава по 4-дневному циклу;
- recurrence каждые 12 часов;
- capacity planning смен;
- автоматическое распределение Tasks по фактическому roster.

## 18. Минимальный пилот сменного сценария

На тестовом стенде прогнать:

1. две daily recurring Tasks — дневная/ночная передача;
2. оставить их unassigned;
3. фактический старший смены берёт Task;
4. проверить создание следующей occurrence после Done;
5. проверить поведение при незакрытой предыдущей;
6. проверить копирование Description;
7. проверить relational Properties;
8. проверить Subtasks;
9. проверить Priority reset;
10. проверить Shared Views для следующей смены.

Только после этого решать, нужен ли вообще отдельный «Журнал смены» как сущность или stock Project уже достаточно.
