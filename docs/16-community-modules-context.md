# Карта модулей Odoo 19 Community для методики

[Главная](../README.md) · [00 Возможности](00-odoo19-community.md) · [01 Модель](01-methodology.md) · [06 Настройка](06-workspace.md)

---

Этот файл — **контекстный реестр**, а не инструкция по установке.

Он фиксирует, какие официальные бесплатные модули Odoo 19 Community рассматриваются для реальных процессов отдела и с каким текущим решением:

- **Используем** — входит в базовый контур или является необходимой штатной инфраструктурой;
- **Возможно** — есть реальный сценарий применения, но модуль включается только после подтверждения потребности;
- **Вероятно нет** — для известных процессов модуль не нужен либо дублирует предметную систему;
- **Автоматический bridge** — служебный Community-модуль, который связывает установленные предметные приложения.

Статус — **методическое решение текущего проекта**, а не характеристика качества самого модуля.

## 1. Граница перечня

Источник технической доступности — публичная ветка `odoo/odoo:19.0`.

В реестр включаются:

1. пользовательские приложения Community, которые могут быть предметно значимы для работы отдела;
2. бесплатные функциональные модули без отдельной иконки приложения, если они влияют на архитектуру методики;
3. штатные bridge-модули между используемыми приложениями.

В этот файл **не перечисляются поштучно** сотни технических зависимостей, локализаций, EDI/payment-provider модулей, тем, website-коннекторов и других add-ons, которые не образуют самостоятельного предметного решения для наших процессов.

Также сюда не входят OCA и другие сторонние модули: сначала строится baseline на официальном Odoo Community.

## 2. Принцип выбора

Модуль устанавливается не потому, что он бесплатный, а только если можно ответить на вопрос:

> **Какой реальный объект или процесс отдела этот модуль естественно представляет?**

Если ответа нет — модуль не включается в рабочий контур.

Базовая логика выбора:

```text
реальный процесс / объект
        ↓
есть естественная штатная модель Odoo?
        │
      да ───→ использовать её
        │
       нет
        ↓
нужна самостоятельная управляемая работа?
        │
      да ───→ Project Task
        │
       нет
        ↓
не создавать искусственную сущность
```

Если на существующей записи требуется только следующее действие / follow-up, сначала рассматривается `Activity`, а не новая Task.

## 3. Базовый контур — используем

| Приложение / модуль | Technical name | Роль в нашем контуре | Решение |
|---|---|---|---|
| **Project / Проекты** | `project` | Самостоятельная управляемая работа: Tasks, Stages, Statuses, Assignees, Deadline, Dependencies, Subtasks, Templates, Recurrence, Project-level управление | **Используем** |
| **Discuss / Обсуждения** | `mail` | Chatter, Activities, входящая/исходящая коммуникация, email gateway, история обсуждения и follow-up | **Используем** |
| **Employees / Сотрудники** | `hr` | Нативный справочник сотрудников как предметных записей; не равен `res.users` | **Используем** |
| **Contacts / Контакты** | `contacts` | Внешние лица, организации, контрагенты, отправители и участники взаимодействия | **Используем** |
| **Fleet / Автопарк** | `fleet` | Нативный справочник ТС; источник предметной ссылки для работ по транспорту | **Используем** |
| **Dashboards / Панели** | `board` | My Dashboard и пользовательские контрольные экраны на базе штатных views | **Используем** |
| **API Documentation** | `api_doc` | Динамическая `/doc`, фактические models/fields/methods базы, playground для интеграций | **Используем как техническую инфраструктуру** |

### Почему именно это ядро

Оно покрывает без собственной предметной системы:

```text
работа               → Project Task
следующее действие   → Activity
коммуникация         → Chatter / Discuss
сотрудник            → Employees
внешний субъект      → Contacts
ТС                    → Fleet
контроль              → Views / Task Analysis / My Dashboard
интеграция            → JSON-2 / API Documentation
```

## 4. Возможно — включаем только по реальному процессу

| Приложение / модуль | Technical name | Возможный сценарий | Почему не включаем заранее |
|---|---|---|---|
| **Calendar / Календарь** | `calendar` | Встречи и календарные события, которые действительно являются частью процесса | Встреча не должна становиться обязательной сущностью для любой Task |
| **To-Do** | `project_todo` | Личный буфер заметок / персональных дел с возможностью дальнейшей работы через Project | Не должен превратиться во второй скрытый backlog отдела |
| **Maintenance / Обслуживание** | `maintenance` | Карточки Equipment и Maintenance Requests для оборудования, если этот предметный контур реально переносится в Odoo | Работа «про оборудование» не автоматически является Maintenance Request |
| **Inventory / Склад** | `stock` | Serial/lot, location, физические движения и складская модель оборудования/терминалов | Не нужен, если требуется только справочная ссылка на оборудование |
| **Website / Сайт** | `website` | Внешний/внутренний web-вход в процессы | Не нужен для первого внутреннего контура |
| **Online Task Submission** | `website_project` | Website + Project → web form → Project Task | Включать только при реальной необходимости принимать заявки формой |
| **Survey / Опросы** | `survey` | Структурированный сбор данных / опросы / анкеты | Не является универсальной формой любого процесса |
| **Automation Rules** | `base_automation` | Механические реакции на изменения, time-based actions, webhooks | Автоматизацию нельзя использовать вместо нормальной модели процесса |
| **Purchase / Закупки** | `purchase` | Если отдельный процесс закупок действительно будет вестись в Odoo | Пока предметный закупочный workflow не относится к базовому контуру |

## 5. Вероятно нет для текущего контура

| Приложение / модуль | Technical name | Почему сейчас не используем |
|---|---|---|
| **Accounting / Бухгалтерия** | `account` | Не создаём вторую учётную систему вместо действующего предметного контура |
| **Timesheets / Task Logs** | `hr_timesheet` | Учитывает время сотрудников на Project Tasks; это не наши табели 1С/Мстрой |
| **Work Entries** | `hr_work_entry` | HR-интервалы рабочего времени; не является системой наших табельных сверок |
| **Attendances / Посещаемость** | `hr_attendance` | Check-in/check-out; не нужен для контроля операционных Tasks и не заменяет табель |
| **Time Off / Отпуска** | `hr_holidays` | HR-процесс отсутствий не входит в текущую задачу |
| **Expenses / Расходы** | `hr_expense` | Не относится к известным рабочим процессам отдела |
| **Skills / Навыки** | `hr_skills` | Не влияет на текущую модель операционной работы |
| **Recruitment / Подбор** | `hr_recruitment` | Подбор персонала не относится к текущему контуру |
| **CRM** | `crm` | Наши входящие обязательства не являются Leads/Opportunities |
| **Sales / Продажи** | `sale_management` | Не относится к процессам отдела |
| **Manufacturing / Производство** | `mrp` | Не заменяет действующие производственные информационные системы |
| **Repair / Ремонт** | `repair` | Для внутреннего оборудования при необходимости сначала рассматривается Maintenance; отдельный repair workflow не заявлен |
| **Point of Sale** | `point_of_sale` | Не относится к процессам отдела |
| **Restaurant POS** | `pos_restaurant` | Не относится к процессам отдела |
| **Lunch / Питание** | `lunch` | Модуль предназначен для корпоративного заказа питания; не решает задачу сверки фактических табелей питания |
| **Email Marketing** | `mass_mailing` | Маркетинговые рассылки не нужны для операционного управления |
| **SMS Marketing** | `mass_mailing_sms` | Не относится к текущим процессам |
| **Marketing Card** | `marketing_card` | Не относится к текущим процессам |
| **Live Chat** | `im_livechat` | Для внутренней коммуникации достаточно Discuss; публичный web-chat не требуется |
| **eCommerce** | `website_sale` | Не относится к процессам отдела |
| **Events** | `event` / website event modules | Управление мероприятиями и регистрациями не относится к текущему контуру |
| **eLearning** | `website_slides` | Может быть отдельным будущим контуром обучения, но не нужен для управления текущей работой |
| **Online Recruitment** | `website_hr_recruitment` | Не относится к текущему контуру |

`Вероятно нет` не означает запрет навсегда. При появлении нового реального процесса модуль оценивается повторно по тому же правилу: **есть ли естественное совпадение предмета процесса и модели Odoo**.

## 6. Автоматические и полезные bridge-модули

Эти модули не являются самостоятельным бизнес-приложением. Они связывают уже выбранные предметные приложения.

| Bridge | Technical name | Связка | Решение |
|---|---|---|---|
| **Fleet History** | `hr_fleet` | Employees ↔ Fleet | **Используем автоматически**, если установлены `hr` + `fleet` |
| **Maintenance – HR** | `hr_maintenance` | Employees ↔ Maintenance Equipment | **Возможно автоматически**, если включаем Maintenance |
| **Stock – Maintenance** | `stock_maintenance` | Inventory serial/lot/location ↔ Maintenance Equipment | **Возможно автоматически**, если включаем Inventory + Maintenance |
| **Project – Purchase** | `project_purchase` | Project ↔ Purchase | **Возможно**, только при реальном закупочном процессе |
| **Project – Stock** | `project_stock` | Project ↔ Stock Pickings | **Возможно**, если складской процесс должен быть связан с Project |
| **Project – Accounting** | `project_account` | Project ↔ accounting/profitability layer | **Вероятно нет** для текущего контура |
| **Project – Expenses** | `project_hr_expense` | Project ↔ employee expenses / analytic layer | **Вероятно нет** для текущего контура |

Правило:

> наличие bridge-модуля подтверждает штатную связь моделей, но не означает автоматически, что нам нужен соответствующий предметный процесс или что существует готовый отчёт под наш вопрос.

## 7. Что сознательно не считаем частью baseline

Даже если в общей документации Odoo функция существует, она не включается в Community-baseline без подтверждения публичной веткой и реальным workflow.

Не строим обязательную архитектуру на:

- Studio;
- Helpdesk;
- Approvals;
- Documents;
- Knowledge;
- Planning;
- Project Gantt;
- Sign;
- Appointments;
- Enterprise Data Cleaning/Data Merge;
- полном Enterprise Quality;
- Enterprise-only capacity/planning features;
- собственном Spreadsheet Dashboard без отдельной runtime/edition-проверки.

## 8. Важные предметные границы для наших процессов

### Транспорт / путевые листы

```text
ТС                         → Fleet
исходные/учётные данные    → действующая предметная система
исправление / проверка     → Project Task, если это самостоятельная работа
следующий follow-up        → Activity
```

Fleet не превращается в систему путевых листов только потому, что работа относится к ТС.

### Табели / Мстрой / 1С

```text
сотрудник                  → Employees
табельные данные           → предметная система
сверка / исправление       → Task при самостоятельном результате
```

Не использовать `hr_timesheet`, `hr_attendance` или `hr_work_entry` как искусственную замену действующим табельным системам.

### Сверки

```text
набор исходных строк       → SQL / 1С / Мстрой / портал / BI / файл
цикл сверки                → Task, если его нужно отдельно управлять
отдельное исключение       → новая Task только если есть самостоятельный результат / исполнитель / срок / решение
```

Не создавать Task на каждую строку расхождения.

### Топливные карты

Транзакции, литры и расхождения являются предметными данными, а Odoo управляет работой по сверке, запросу, исправлению и контролю результата.

### Оборудование

```text
карточка оборудования      → Maintenance, если модель подходит
serial / lot / location    → Inventory, если нужен физический учёт
самостоятельная работа     → Project Task
```

Не превращать любую работу с оборудованием в Maintenance Request.

### Входящие

```text
email / web form
      ↓
существующая работа? → Chatter
новая самостоятельная работа? → Task
```

Website и `website_project` включаются только когда web-вход действительно требуется.

```text

Employees

```

Автоматически / технически рядом:

```text

```

Следующий кандидат на расширение:

```text
Maintenance

hr_maintenance
stock_maintenance
```

только если подтверждена потребность вести оборудование, серийники, location и движения именно в Odoo.

## 10. Критерий пересмотра статуса модуля

Любой модуль переводится между `Используем / Возможно / Вероятно нет` только после ответа на пять вопросов:

1. Какой реальный процесс или объект он представляет?
2. Где сейчас находится источник истины?
3. Не создаёт ли установка второй конкурирующий реестр?
4. Повышает ли модуль удобство ежедневной работы или контроль без дополнительной бюрократии?
5. Нужна ли его собственная предметная модель, или достаточно Task / Activity / Property / существующей записи?

Если модуль не даёт явной ценности по этим вопросам — не устанавливать его «на будущее».

## 12. Статус документа
