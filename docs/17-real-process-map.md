# Карта реальных процессов → Odoo 19 Community

[Главная](../README.md) · [16 Реестр модулей](16-community-modules-context.md) · [05 Процессы](05-processes.md) · [06 Настройка](06-workspace.md) · [Master data: люди](17-master-data-people.md)

---

Этот документ переводит **реальные рабочие процессы** в естественные сущности Odoo 19 Community.

Он является промежуточным инженерным слоем между:

```text
реальная работа
→ технические возможности Odoo
→ будущая нативная методика
```

Техническая граница определяется [опорным реестром Community-модулей](16-community-modules-context.md). Если этот документ требует функцию, которой нет в подтверждённом Community baseline, это должно быть явно отмечено как `gap` или `runtime check`.

Для людей действует уже согласованное решение [Master data: люди](17-master-data-people.md): человек / сотрудник компании → `res.partner`, доступ в Odoo → связанный `res.users`. Employees / HR не является baseline только ради справочника людей.

## 1. Как читать карту

Для каждого процесса фиксируется одна и та же цепочка:

```text
реальный процесс
→ источник истины
→ предметные сущности
→ естественные Odoo models
→ Task / Activity / профильная запись / внешняя система
→ результат
→ контроль
→ аналитические разрезы
→ кандидат Project
→ кандидат Stage
→ Properties
→ открытые вопросы
→ возможные gaps
```

Три типа утверждений не смешиваются:

- **Факт процесса** — известная часть реальной работы;
- **Odoo mapping** — штатный механизм Odoo, который естественно представляет этот элемент;
- **Кандидат** — решение, которое ещё должно быть подтверждено walkthrough процесса или пилотом.

`Кандидат` не является правилом методики.

## 2. Общие правила mapping

### 2.1. Источник истины не переносится в Odoo автоматически

Если предметные данные уже живут в 1С, Мстрой, топливном портале, SQL/BI или другом профильном источнике, Odoo не должен создавать второй конкурирующий реестр только ради контроля работы.

```text
предметные данные
→ остаются в source of truth

управляемая работа над ними
→ Odoo
```

### 2.2. Сначала профильная запись, затем Task

```text
есть естественная Odoo model?
→ использовать её как предметную запись

нужно только следующее действие по записи?
→ Activity

нужен отдельный контролируемый результат?
→ Project Task
```

### 2.3. Строка данных не равна Task

Строка расхождения, транзакция, строка табеля, путевой лист или запись отчёта не становятся Task автоматически.

Task создаётся только когда появляется самостоятельный результат, для которого имеет смысл отдельно управлять выполнением, ответственностью, сроком или решением.

### 2.4. Odoo-анализ и предметная аналитика разделяются

Odoo отвечает на вопросы о работе:

```text
что открыто
что просрочено
что требует действия
кто выполняет
где зависла работа
какой процесс создаёт backlog
```

Профильные системы / SQL / BI отвечают на предметные вопросы:

```text
литры
рейсы
ПЛ
табельные часы
транзакции
объёмы
суммы
строки расхождений
```

Не рассчитывать предметные KPI из количества Tasks, если Tasks не являются исходными предметными данными.

| Разовые аналитические запросы | открыто / срок / Assignee / ожидание данных | тип запроса, заявитель/источник, срок | кандидат общего операционного Project | определяется реальным циклом аналитического запроса | заявитель при необходимости; источник данных только если используется аналитически |

Ни один `Кандидат Project`, `Кандидат Stage` или `Property` в таблице не считается утверждённым до проверки реального процесса.

## 5. Процесс: входящие основания / СЗ / письма

### Факт процесса

В работу поступает основание: письмо, документ, сообщение или иной рабочий вход. Оно может либо породить новую самостоятельную работу, либо относиться к уже существующей.

### Источник истины

Источник самого основания — исходный канал и оригинальный документ/письмо.

Odoo может хранить рабочий контекст и копию/attachment, но не должен автоматически становиться юридическим реестром всех оснований без такого требования.

### Естественные Odoo models

```text
заявитель / отправитель → res.partner
существующая работа     → project.task + Chatter
следующий follow-up     → mail.activity
новая самостоятельная работа → project.task
```

### Правило Task

```text
входящее требует отдельного результата
→ Task

входящее относится к существующей Task
→ Chatter / attachment

нужно только вернуться к вопросу позже
→ Activity
```

### Результат

Не универсальное `письмо обработано`, а конкретный результат, который требуется содержанием основания.

### Контроль

Odoo должен позволять увидеть только те входящие, которые превратились в управляемую работу:

- открытые Tasks;
- просроченные Tasks;
- Tasks без требуемого Assignee, если это правило процесса;
- просроченные Activities;
- Tasks, по которым ожидается следующее действие.

### Открытые вопросы

1. Нужен ли самостоятельный реестр оснований независимо от Tasks?
2. Требуются ли номер, дата, тип и заявитель как обязательные структурные поля?
3. Может ли одно основание порождать несколько независимых Tasks?
4. Должен ли отдельный email alias автоматически создавать Tasks, или вход сначала проходит другой triage?

### Возможный gap

Если основание должно иметь собственную уникальность, lifecycle, отдельный реестр, права, поиск и связь many-to-many с Tasks, attachment/Property недостаточны — это кандидат на минимальную custom model.

## 6. Процесс: исправления ПЛ / транспортных данных

### Источник истины

Путевые листы и учётные транспортные данные остаются в действующей профильной системе.

### Предметные сущности

```text
ТС
ПЛ / внешний идентификатор
период
основание
требуемое изменение
```

### Естественные Odoo models

```text
ТС          → fleet.vehicle
работа      → project.task
follow-up   → mail.activity
контекст    → Chatter / attachment
```

Fleet представляет ТС, а не копию путевого листа.

### Единица Task

Task создаётся на самостоятельное исправление/проверку, если им нужно отдельно управлять.

Не создавать Task на каждую строку транспортной выгрузки или каждый ПЛ автоматически.

### Результат

Требуемое изменение выполнено в source of truth. Дополнительная проверка считается частью процесса только если она реально требуется.

### Контроль

- открытые работы по ТС;
- просроченные работы;
- работы за период;
- Tasks с просроченным follow-up;
- отдельные блокирующие зависимости, если они существуют.

### Аналитика

Odoo анализирует количество и состояние работ. Поездки, километры, объёмы и другие транспортные показатели остаются в профильной аналитике.

### Кандидат Properties

```text
ТС      → Many2one(fleet.vehicle)
Период  → только если реально используется для поиска/анализа
Ссылка/номер основания → только если нужен системный поиск
```

### Открытые вопросы

1. Что является минимальной единицей исправления: один ПЛ, пакет ПЛ, ТС-период или иной результат?
2. Есть ли отдельное внешнее ожидание после внесения изменения?
3. Нужна ли подтверждающая проверка результата?
4. Нужен ли идентификатор ПЛ как структурное поле или достаточно текста/ссылки/attachment?

## 7. Процесс: табели / Мстрой / 1С

### Источник истины

Табельные данные остаются в Мстрой / 1С или другом действующем профильном источнике.

### Предметные сущности

```text
сотрудник
период
табельные данные
основание
расхождение / требуемое исправление
```

### Естественные Odoo models

```text
сотрудник → res.partner
работа    → project.task
follow-up → mail.activity
```

HR-приложения не используются как искусственная копия внешнего табеля или как обязательный справочник людей.

### Единица Task

Task представляет самостоятельную сверку или исправление, а не строку табеля.

### Результат

Требуемое исправление или сверка завершены в source of truth.

### Контроль

- открытые работы по сотруднику;
- период;
- срок;
- просроченные Activities;
- состояние самостоятельной корректировки.

### Кандидат Properties

```text
Сотрудник → Many2one(res.partner)
Период
Source system — только если по нему реально нужен разрез
```

### Открытые вопросы

1. Как группируются реальные исправления: по сотруднику, документу, периоду или пакету?
2. Требуется ли связать одну Task с несколькими сотрудниками?
3. Какие данные действительно нужны в Odoo для поиска, а какие должны оставаться только во внешней системе?

## 8. Процесс: сверки топлива

### Источник истины

```text
1С
топливные порталы
SQL / BI / рабочие выгрузки
```

Каждый источник остаётся источником своих фактических данных.

### Предметные сущности

```text
период сверки
ТС
операции
объёмы
источники данных
расхождения / исключения
```

### Odoo mapping

```text
цикл сверки как самостоятельный результат → project.task
конкретное ТС при отдельной работе         → fleet.vehicle relation
следующее действие                         → mail.activity
исходные строки и расчёты                  → вне Odoo
```

### Единица Task

Нормальный масштаб:

```text
сверка за период
или
отдельное исключение, если у него есть самостоятельный исполнитель/срок/решение
```

Ненормальный масштаб:

```text
каждая строка расхождения → Task
```

### Результат

Сверка завершена, исключения классифицированы, а самостоятельные действия по ним закрыты.

### Контроль

Odoo должен отвечать на вопросы о ходе работы, но не пересчитывать исходную сверку:

- какая сверка открыта;
- какой срок;
- кто выполняет;
- какие самостоятельные исключения не закрыты;
- какие follow-up просрочены.

### Аналитика

Литры, транзакции, количества операций и расхождения считаются из предметных данных. Odoo показывает workload и управленческое состояние.

### Открытые вопросы

1. Что считается одной самостоятельной сверкой?
2. Когда исключение становится отдельной Task?
3. Нужна ли связь одной Task с несколькими ТС?
4. Нужен ли отдельный Project для сверок или достаточно общего операционного Project + классификации?

## 9. Процесс: топливные карты

### Источник истины

Карты, операции и фактические объёмы остаются в 1С / топливных порталах / рабочей аналитической модели.

### Предметные сущности

```text
карта
владелец
ТС
транзакция
период
исключение
```

### Естественные Odoo models

У Community baseline нет подтверждённой отдельной предметной модели `fuel.card`.

Используем только естественные связи, когда они действительно соответствуют предмету:

```text
сотрудник-владелец → res.partner
ТС                  → fleet.vehicle
работа              → project.task
```

### Единица Task

Task возможна для:

- цикла сверки;
- запроса уточнения;
- внесения отдельной корректировки;
- исключения, которое требует самостоятельного решения.

Карта и транзакция сами по себе Task не являются.

### Кандидат Properties

Идентификатор карты допустим как Property/text только если по нему реально ищут Tasks. Это не превращает Property в полноценный реестр карт.

### Открытые вопросы

1. Нужен ли в Odoo самостоятельный реестр топливных карт?
2. Должна ли карта иметь уникальность, владельца, историю выдачи/возврата и связи с несколькими ТС?
3. Или для Odoo достаточно ссылки/идентификатора карты внутри работы, а master data остаётся во внешней системе?

### Возможный gap

Если карта должна стать самостоятельным Odoo-record с lifecycle, уникальностью, историей и отношениями, потребуется отдельная предметная model; использовать Task как карточку карты нельзя.

## 10. Процесс: оборудование / терминалы

### Источник истины

Этот процесс требует отдельного решения о source of truth.

До решения возможны два режима:

```text
A. текущий внешний реестр остаётся source of truth
B. предметный учёт переносится в Odoo
```

### Естественные Odoo models

При режиме B сначала оцениваются:

```text
Equipment             → maintenance.equipment
serial / lot           → Inventory
location               → Inventory
movement               → Inventory
обслуживание / ремонт  → Maintenance Request, если это действительно обслуживание
отдельная работа       → project.task
```

### Правило Task

Task не является карточкой терминала.

Task нужна, например, если появляется самостоятельный результат:

```text
провести проверку
разобрать расхождение
подготовить документ
выполнить отдельное действие по объекту
```

### Контроль

Предметное состояние оборудования контролируется профильной моделью. Project контролирует только самостоятельные работы вокруг объекта.

### Аналитика

Если Odoo становится source of truth для оборудования, serial/location/movement анализируются из Inventory/Maintenance, а не из Tasks.

### Открытые вопросы

1. Переносим ли реестр оборудования в Odoo вообще?
2. Что именно является оборудованием, а что складской единицей/serial?
3. Нужен ли физический movement workflow?
4. Нужна ли история актов как самостоятельный реестр или достаточно attachments/документов движения?
5. Какие права нужны на изменение master data оборудования?

### Runtime checks

Перед принятием решения проверить связку:

```text
Maintenance
Inventory
stock_maintenance
```

и реальный UX serial/location/movement на пилотных данных.

## 11. Процесс: регулярная отчётность

### Источник истины

Исходные данные остаются в соответствующих предметных системах, SQL/BI или рабочих файлах.

### Odoo mapping

Если каждый выпуск отчёта является самостоятельным результатом:

```text
Recurring Task
→ очередной выпуск
→ Deadline / Assignee при необходимости
→ attachment / link / Chatter
→ Done
```

Если требуется только напоминание без самостоятельного управленческого результата, достаточно Activity.

### Результат

Конкретный выпуск отчёта подготовлен и передан/размещён там, где это требует процесс.

### Контроль

- очередной выпуск создан;
- Deadline не нарушен;
- Task закрыта;
- follow-up выполнен при наличии.

### Кандидат Properties

Стабильные данные лучше задавать Template/Recurrence. Property добавляется только если по нему нужен поиск/фильтрация/аналитика.

### Открытые вопросы

1. Какие отчёты действительно являются отдельными контролируемыми результатами?
2. Какая периодичность у каждого?
3. Нужен ли Deadline и как он определяется?
4. Где хранится сам результат: attachment, ссылка, внешний ресурс?

## 12. Процесс: разовые аналитические запросы

### Источник истины

SQL / BI / файлы / профильные системы.

### Odoo mapping

```text
самостоятельный аналитический результат → project.task
следующий запрос данных / напоминание   → mail.activity
исходные наборы данных                  → внешние системы / attachment / link
```

### Результат

Подготовлена конкретная выгрузка, анализ, заключение или иной запрошенный результат.

### Контроль

- что запрошено;
- кто выполняет;
- срок;
- ожидание исходных данных;
- завершение результата.

### Открытые вопросы

1. Нужен ли единый тип/классификатор аналитических запросов?
2. Нужно ли системно фиксировать заявителя?
3. Нужно ли разделять разовые аналитические запросы и регулярную отчётность разными Projects или достаточно разных представлений?

## 13. Процесс: прочие корректировки в предметных системах

Это fallback-категория, а не отдельный универсальный workflow.

Для каждого нового вида корректировки сначала выполняется тот же выбор:

```text
что изменяем?
→ где source of truth?
→ есть ли естественная Odoo model объекта?
→ нужен только follow-up?
→ нужен отдельный контролируемый результат?
```

Новый вид работы не получает отдельный Project/Stage/Property только потому, что появился новый термин процесса.

Если новый процесс начинает устойчиво отличаться по workflow, visibility, Properties или управленческому контуру, он выводится из fallback и описывается отдельной карточкой.

## 14. Кандидат архитектуры Projects

На текущем уровне данных **нельзя честно зафиксировать окончательное количество Projects**.

Рабочая гипотеза для пилота:

```text
общий Project операционной работы
```

может быть удобен для task-based процессов, если одновременно выполняются условия:

- совместимый доступ;
- совместимый базовый workflow;
- Properties не превращаются в гигантскую общую форму;
- общие Views дают нормальное рабочее место;
- не требуется самостоятельное project-level управление.

Разделять Projects нужно при доказанном различии:

```text
visibility
workflow
property schema
project-level управление
lifecycle
```

Предметные приложения `Fleet`, `Contacts`, `Maintenance`, `Inventory` не превращаются в Projects.

## 15. Кандидат архитектуры Stages

Окончательный набор Stages сейчас **не определён**.

Он должен быть выведен после walkthrough реальных Tasks каждого процесса.

Для любого кандидата Stage задаются три вопроса:

1. Есть ли реальная рабочая позиция, в которой Task может находиться заметное время?
2. Нужно ли руководителю/исполнителю видеть именно эту позицию отдельно?
3. Нельзя ли выразить то же самое штатным Status, Activity или Dependency без дополнительной колонки?

Если хотя бы на один процесс Stage нужен только «для красоты», он не включается в общий workflow.

## 16. Кандидат минимальной схемы Properties

Properties не проектируются как анкета «на все случаи».

Общий кандидатный пул:

| Property | Тип | Где может понадобиться | Условие включения |
|---|---|---|---|
| ТС | Many2one → `fleet.vehicle` | транспорт, топливо, отдельные исключения | только для Tasks, где одна/несколько конкретных ТС действительно являются предметом работы |
| Сотрудник | Many2one → `res.partner` | табели, отдельные корректировки | если по сотруднику ищут/фильтруют Tasks |
| Заявитель / отправитель | Many2one → `res.partner` | входящие / запросы | если нужна системная связь с человеком |
| Оборудование | relation → Maintenance Equipment | работы по оборудованию | если Maintenance включён и объект ведётся там |
| Период | Date/text/selection — выбрать после UX-теста | сверки, табели, отчёты | если период нужен как рабочий или аналитический разрез |
| Внешний идентификатор / основание | text | исправления / входящие | если нужен системный поиск и нет отдельной предметной model |
| Тип процесса | selection/tag/property | только если несколько процессов живут в одном Project | если реально нужен для Views/аналитики |

Правило:

> Property добавляется только если оно нужно для выполнения, поиска, фильтрации, группировки, контроля или принятия решения.

Если свойство необходимо как жёстко обязательное, уникальное или аудируемое поле, сначала проверить ограничения Properties; при недостаточности фиксировать gap.

## 17. Сквозные открытые вопросы

До превращения этой карты в нормативную методику нужно подтвердить:

1. точную единицу Task для каждого процесса;
2. какие реальные действия являются просто Activity, а какие отдельной Task;
3. нужен ли самостоятельный реестр оснований;
4. нужен ли самостоятельный реестр топливных карт;
5. переносится ли оборудование/терминалы в Maintenance/Inventory;
6. какие процессы действительно имеют разные workflows;
7. где реально нужен отдельный Stage ожидания;
8. где существует обязательная проверка результата;
9. какие deadlines являются реальными бизнес-сроками;
10. какие Properties реально используются ежедневно;
11. какой доступ требуется к `fleet.vehicle`, `res.partner`, Maintenance и Inventory;
12. нужен ли один общий Project или несколько рабочих контуров.

Не выводить ответы из организационных предположений, должностей или ранее использованной методики.

## 18. Сквозные runtime-проверки

На пилоте проверить:

- relational Properties к `fleet.vehicle`, `res.partner`, `maintenance.equipment`;
- UX этих Properties в List/Kanban/Form и Shared Views;
- группировку/фильтрацию по Properties на реальном объёме;
- права пользователей на target records;
- email alias / Chatter для входящих;
- Recurring Task для реальной регулярной отчётности;
- Task Templates для повторяемых разовых работ;
- Activity как личный/операционный follow-up;
- зависимость `Blocked by` только для реальных внутренних зависимостей;
- массовую работу в List;
- My Dashboard / Task Analysis для управленческих вопросов;
- Maintenance + Inventory на пилотном наборе оборудования, если этот контур подтверждён.

## 19. Возможные gaps, которые уже можно отслеживать

Это **кандидаты**, а не решение о разработке.

| Потенциальный gap | Когда становится реальным |
|---|---|
| Самостоятельный реестр оснований | если основанию нужны собственная уникальность, lifecycle, права, поиск и связи с несколькими Tasks |
| Самостоятельный реестр топливных карт | если карта должна жить в Odoo независимо от Tasks и иметь lifecycle/историю/relations |
| Жёсткие обязательные/уникальные поля вместо Properties | если процесс нельзя безопасно вести без database-level/ORM constraints |
| Гарантированный аудит изменений динамических Properties | если требуется формальный audit trail именно этих значений |
| Сложные переходы по ролям | если подтверждена матрица, которую нельзя надёжно выразить Groups/ACL/Record Rules/Automation |
| Предметная аналитика внутри Odoo | если возникает требование считать в Odoo литры, табельные часы, транзакции и другие показатели, которых нет в Odoo source of truth |

Любой gap сначала подтверждается пилотом, затем выбирается минимальная доработка.
