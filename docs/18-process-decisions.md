# Решения по реальным процессам Odoo 19 Community

[Главная](../README.md) · [16 Реестр модулей](16-community-modules-context.md) · [17 Карта процессов](17-real-process-map.md) · [05 Процессы](05-processes.md)

---

Этот документ фиксирует **подтверждённые и пилотные решения по конкретным реальным процессам**.

Он не является каталогом идей. Для каждого решения явно указывается его статус:

- **Факт процесса** — известно из реальной работы;
- **Решение пилота** — конкретная схема, которую проверяем в Odoo;
- **Runtime check** — технически подтверждено документацией/source, но UX/права/поведение надо проверить на нашем стенде;
- **Открытое правило** — организационное решение ещё не подтверждено и не должно додумываться.

Техническая граница модулей определяется [docs/16](16-community-modules-context.md), а общая карта процессов — [docs/17](17-real-process-map.md).

# 1. Исправления ПЛ / транспортных данных

## 1.1. Цель процесса

Обеспечить управляемое выполнение исправления транспортных данных в профильной системе так, чтобы было понятно:

- что именно требуется исправить;
- по какому основанию;
- к каким ТС / данным относится работа;
- кто фактически отвечает за выполнение;
- есть ли срок результата;
- что сейчас происходит с работой;
- когда результат действительно можно закрыть.

Odoo управляет **работой по исправлению**, но не становится второй системой путевых листов.

## 1.2. Источник истины

**Факт процесса**:

```text
путевой лист / транспортные учётные данные
→ профильная транспортная / учётная система

ТС как справочный объект для связи работы
→ Odoo Fleet

управляемая работа по исправлению
→ Odoo Project Task
```

Сам ПЛ не копируется в `fleet.vehicle` и не моделируется как Fleet Service.

Если в дальнейшем появится требование вести самостоятельный реестр ПЛ внутри Odoo, это будет отдельный предметный gap и отдельное архитектурное решение.

## 1.3. Единица Task

**Решение пилота**:

> **Одна Task = один независимо управляемый пакет исправлений, который можно целиком принять как один результат и закрыть одной операцией.**

Это не означает «один ПЛ = одна Task».

### Одна Task подходит, если

- несколько исправлений выполняются как один пакет;
- у них общий контекст/основание;
- работа не требует независимого распределения между разными исполнителями;
- нет отдельных сроков завершения;
- весь пакет можно закрыть одним результатом.

### Нужно разделять Tasks, если

- части работы имеют независимых ответственных;
- разные части могут завершаться независимо;
- отличаются реальные сроки;
- требуется отдельный контроль результата;
- одна часть блокирует другую как самостоятельную работу.

### Не создавать Task на

- каждую строку выгрузки;
- каждое автоматически найденное расхождение;
- каждую техническую операцию в 1С;
- каждое сообщение по уже существующей работе;
- каждый ПЛ только ради реестра.

Если внутри одного пакета нужно перечислить десятки строк данных, это остаётся в исходном файле/выгрузке/вложении либо в предметной системе. Subtask используется только когда появляется **отдельная управляемая работа**, а не как контейнер строки данных.

## 1.4. Предметные связи

**Решение пилота**:

```text
Task
├── ТС → relation на fleet.vehicle
├── внешний идентификатор / номер ПЛ
├── период данных
├── основание
├── Assignee(s)
├── Deadline — только если существует срок результата
├── Stage / Status
├── Activities — следующий шаг
└── Chatter / attachments — рабочий контекст и исходные материалы
```

`fleet.vehicle` используется как master record ТС. Путевые данные и сам факт исправления остаются в профильной системе.

## 1.5. Пилотный Project

**Решение пилота**:

Для проверки процесса создать отдельный пилотный Project:

```text
Транспортные корректировки — пилот
```

Это **не решение о финальной архитектуре Projects**.

Причина отдельного Project на пилоте:

- изолировать schema Properties;
- проверить workflow без влияния других процессов;
- проверить Shared Views и аналитику;
- проверить права к `fleet.vehicle`;
- затем сравнить с табелями / топливом и решить, можно ли объединять контуры.

После разбора нескольких процессов Project либо останется самостоятельным, либо будет объединён с общим операционным Project, если совпадут workflow, visibility, property schema и управленческий контур.

## 1.6. Конкретный workflow пилота

Odoo Project не задаёт стандартные Task Stages; Stage должен отражать реальную позицию Task в процессе. Поэтому для первого пилота используется минимальная схема:

```text
К выполнению
    ↓
В работе
    ↕
Ожидание

закрытие → Status = Done
отмена   → Status = Canceled
```

### Stage `К выполнению`

Task зарегистрирована как самостоятельная работа, но активное выполнение ещё не начато.

Это **первая Stage Project**.

Она нужна для отделения зарегистрированной работы от фактически начатой.

### Stage `В работе`

По Task выполняется действие, которое продвигает её к результату:

- анализ основания;
- проверка данных;
- внесение исправления;
- проверка того, что изменение действительно применено в source of truth.

### Stage `Ожидание`

Используется только когда продолжение работы реально зависит от внешнего ответа/документа/уточнения, а не от другой Odoo Task.

Примеры:

```text
запрошено основание
ожидается уточнение
ожидается ответ из внешнего контура
```

При переходе в `Ожидание` должен быть создан Activity с датой следующего follow-up, если известно, когда нужно проверить ответ.

Когда ответ получен:

```text
Activity → выполнена
Task → обратно в В работе
```

### Что не является отдельной Stage

В пилоте **не создаются**:

```text
Запрос отправлен
Требуется уточнение
На проверке
Проверено
Возвращено
Готово
Закрыто
```

без отдельного доказанного смысла.

`Запрос отправлен` фиксируется Chatter/Activity.

`Done` и `Canceled` являются Task Status и не требуют колонок Kanban.

Отдельная стадия проверки появится только если подтверждено, что независимая проверка — обязательный реальный этап процесса.

## 1.7. Использование Task Status

**Технический факт Odoo 19**: Task Status и Task Stage — разные механизмы.

Для пилота:

| Status | Использование |
|---|---|
| `In Progress` | обычное открытое состояние Task внутри `К выполнению`, `В работе` или внешнего `Ожидание` |
| `Changes Requested` | **не использовать как обязательное правило**; кандидат только если появится реальный цикл проверки/возврата |
| `Approved` | **не использовать как обязательное правило**; кандидат только если появится реальный этап принятия результата |
| `Done` | результат исправления реально достигнут в source of truth |
| `Canceled` | работа больше не должна выполняться и закрывается как отменённая |

`Changes Requested` и `Approved` не считаются долговременной классификацией: Odoo сбрасывает их в `In Progress` при переходе Task в другую Stage.

## 1.8. Внешнее ожидание и внутренняя dependency — разные вещи

### Внешнее ожидание

```text
Task → Stage Ожидание
     → Activity на следующий follow-up
```

### Внутренняя зависимость от другой Odoo Task

```text
Task B Blocked by Task A
→ системный Waiting
```

Не использовать `Blocked by` для ожидания письма, СЗ или ответа внешнего участника.

Не создавать одновременно локальную dependency и Stage `Ожидание` для одного и того же внутреннего блокирования без отдельной причины.

## 1.9. Минимальная карточка Task

### Стандартные поля Odoo

Используются:

- **Task Title**;
- **Project**;
- **Assignees**;
- **Deadline** — если есть реальный срок результата;
- **Stage**;
- **Status**;
- **Priority** — только если позже будет определено реальное последствие этого признака;
- **Chatter**;
- **Activities**.

### Properties пилота

| Property | Тип | Назначение | Статус |
|---|---|---|---|
| **ТС** | `Many2many → fleet.vehicle` | поиск работы по одному или нескольким ТС | **Runtime check**: проверить UX, поиск и группировку |
| **Период с** | Date | начало периода данных | **Используем в пилоте** |
| **Период по** | Date | конец периода данных | **Используем в пилоте** |
| **Номер ПЛ / внешний ID** | Text | быстрый поиск по внешнему идентификатору; может содержать один или небольшой набор ID | **Используем в пилоте** |
| **Основание** | Text | номер/краткий идентификатор документа-основания | **Используем в пилоте** |

Для одного дня `Период с = Период по`.

Properties **не являются** реестром путевых листов и не заменяют предметную систему.

### Что пока не добавляем

- участок;
- тип корректировки;
- система;
- причина ошибки;
- инициатор;
- отдельный статус документа;
- «проверено кем»;
- десятки служебных признаков.

Они добавляются только после доказанной потребности в выполнении, поиске, фильтрации, группировке или принятии решения.

## 1.10. Название Task

Автонейминг на первом пилоте не нужен.

Рекомендуемый ручной шаблон:

### Одиночная работа

```text
Исправить ПЛ <номер> — <госномер>
```

### Пакет

```text
Исправить транспортные данные — <основание / краткий предмет>
```

Название должно позволять понять результат без открытия карточки, но не обязано дублировать все Properties.

## 1.11. Assignee

**Техническое решение**:

Assignee означает пользователя Odoo, который фактически отвечает за выполнение Task в данный момент.

**Открытое организационное правило**:

- кто назначает Task;
- можно ли создавать неназначенную Task;
- требуется один или несколько Assignees;
- допускается ли самостоятельное взятие работы;
- кто передаёт работу другому пользователю.

До подтверждения этих правил методика не вводит роли и маршрутизацию.

Для пилота достаточно проверять, что рабочие Views позволяют видеть как назначенные, так и неназначенные Tasks.

## 1.12. Deadline и Activity Due Date

```text
Deadline
= когда должен быть получен конечный результат исправления

Activity Due Date
= когда нужно выполнить следующий шаг / проверить ответ
```

Если для Task нет реального срока результата, искусственный Deadline не создаётся только ради заполнения поля.

Но если Task находится в `Ожидание`, Activity позволяет не потерять следующий follow-up даже без Deadline конечного результата.

## 1.13. Поступление работы

### Baseline пилота

Первый пилот использует **ручное создание Task** из подтверждённого входящего основания или обнаруженной самостоятельной работы.

Причина: сначала нужно проверить правильную единицу Task и качество карточки, а уже затем автоматизировать intake.

### Email alias — второй шаг

Odoo Project умеет создавать Task из email alias. При этом письмо автоматически превращается в новую Task.

Поэтому alias подключается только для канала, где правило действительно звучит:

```text
одно входящее письмо
→ новая самостоятельная Task
```

Не подключать весь общий/личный входящий поток к alias, если часть писем должна попадать в Chatter существующих Tasks или вообще не создавать работу.

## 1.14. Chatter и attachments

Chatter используется как **контекст работы**, а не как замена структурным полям.

В нём естественно хранить:

- исходное письмо/сообщение;
- вложение-основание;
- уточнения;
- сообщения по ходу работы;
- факт получения внешнего ответа.

Не требовать отдельный «закрывающий комментарий» только ради бюрократии, если сам факт завершения однозначно подтверждается source of truth и Task Status `Done`.

Если конкретному процессу требуется обязательное доказательство результата, это фиксируется отдельно и только тогда становится условием закрытия.

## 1.15. Когда Task считается Done

**Решение пилота**:

Task переводится в `Done`, когда **требуемое исправление фактически выполнено в source of truth** и дополнительных действий по этому пакету не требуется.

Не закрывать Task только потому, что:

- запрос отправлен;
- файл передан другому сотруднику;
- получено обещание исправить;
- данные подготовлены, но изменение ещё не внесено;
- карточка «больше не мешает» в Kanban.

Если работа отменена как не требующая выполнения, используется `Canceled`, а не `Done`.

## 1.16. Рабочие Views пилота

Shared Views должны отвечать на реальные вопросы, а не дублировать весь Kanban.

Минимальный набор для проверки:

### `Мои открытые`

Открытые Tasks, где текущий пользователь — Assignee.

### `К выполнению`

Tasks в первой Stage.

### `Ожидание`

Tasks во внешнем ожидании с видимой следующей Activity.

### `Просроченные`

Открытые Tasks с прошедшим Deadline.

### `Просрочен следующий шаг`

Tasks с просроченными Activities.

### `Без исполнителя`

Открытые Tasks без Assignee — если такие Tasks допускаются реальным правилом распределения.

### `По ТС`

Поиск/фильтрация по relation `fleet.vehicle`.

### Поиск по основанию / номеру ПЛ

Проверить, насколько Properties дают достаточный ежедневный поиск без отдельного реестра.

## 1.17. Контроль процесса

Odoo должен позволять без параллельного Excel-реестра ответить минимум на вопросы:

```text
какие транспортные корректировки открыты?
что фактически в работе?
что ждёт внешнего ответа?
у какой ожидающей работы просрочен follow-up?
что просрочено по конечному сроку?
кто отвечает за конкретную Task?
что относится к конкретному ТС?
что относится к конкретному ПЛ / основанию?
что уже закрыто?
```

Это управленческая аналитика работы.

Количество ПЛ, ездок, километры, объёмы, литры и другие предметные показатели считаются из профильных данных, а не из количества Tasks.

## 1.18. Права

Перед production-настройкой требуется runtime-проверка доступа.

Минимальный принцип:

- пользователь, работающий с транспортной Task, должен иметь возможность **прочитать** нужную `fleet.vehicle` для relation Property;
- право изменять карточку Fleet не должно выдаваться только ради выбора ТС в Task;
- видимость Tasks определяется Project visibility + Groups/ACL/Record Rules;
- доступ к attachments/Chatter должен следовать доступу к самой Task.

**Открытое правило**: кто может изменять Fleet master data и кто видит весь транспортный контур.

## 1.19. Что специально не используем

Для этого процесса baseline **не строится** на:

- Fleet Service как карточке исправления ПЛ;
- Timesheets;
- Attendances;
- Work Entries;
- Inventory;
- Maintenance;
- отдельном custom-модуле ПЛ;
- Automation Rules как основании workflow;
- Task на каждую строку расхождения.

Эти механизмы могут появиться только при отдельной реальной потребности.

## 1.20. Runtime walkthrough

Перед переносом решения в нормативную методику провести на стенде минимум следующие сценарии.

### Сценарий A — одиночное исправление

```text
создать Task
→ выбрать ТС
→ указать номер ПЛ
→ указать период
→ приложить основание
→ В работе
→ исправить source of truth
→ Done
```

Проверить: скорость заполнения, поиск по ТС/ПЛ, история.

### Сценарий B — требуется внешнее основание

```text
Task
→ В работе
→ отправлен запрос
→ Stage Ожидание
→ Activity на follow-up
→ получен ответ
→ Activity done
→ В работе
→ исправление
→ Done
```

Проверить: не теряется ли Task и видит ли руководитель просроченный follow-up.

### Сценарий C — пакет исправлений

```text
одно основание
→ несколько ПЛ / ТС
→ одна Task, если это единый результат
→ выполнить пакет
→ Done
```

Проверить: достаточно ли `Many2many → fleet.vehicle` и Text external ID без собственного реестра строк.

### Сценарий D — пакет распадается на независимые работы

```text
один вход
→ разные ответственные / сроки / независимое закрытие
→ отдельные Tasks или Subtasks
```

Проверить: какой вариант удобнее и не создаёт лишнюю иерархию.

### Сценарий E — внутренняя зависимость

```text
Task B зависит от отдельной Task A
→ Blocked by
→ системный Waiting
→ A Done/Approved/Canceled
→ B доступна для продолжения
```

Проверить: не нужен ли локальный Stage `Ожидание` для этого сценария. Базовое ожидание внешнего ответа и dependency должны оставаться разными механизмами.

### Сценарий F — поиск исторической работы

Найти закрытую Task:

- по ТС;
- по номеру ПЛ;
- по основанию;
- по периоду.

Если это неудобно или ненадёжно на реальном объёме, зафиксировать конкретный gap.

## 1.21. Критерии прохождения пилота

Процесс считается пригодным для штатной реализации без custom-модуля, если реальный пользователь может:

1. быстро создать Task без избыточного заполнения;
2. однозначно связать работу с нужным ТС/периодом/основанием;
3. видеть собственную текущую работу;
4. не терять внешнее ожидание;
5. контролировать Deadline и follow-up;
6. найти историческую работу по предметным признакам;
7. закрыть результат без параллельного ручного реестра Tasks;
8. получить управленческие срезы без копирования предметных данных в Odoo;
9. работать с нужными `fleet.vehicle`, не получая лишних прав на master data.

Если один из этих пунктов не выполняется, фиксируется точный технический или UX gap.

## 1.22. Потенциальные gaps

Пока это **кандидаты**, а не основания для разработки.

| Gap | Когда он становится реальным |
|---|---|
| Самостоятельный реестр ПЛ | если ПЛ должен иметь собственный lifecycle, права, уникальность и отношения внутри Odoo |
| Самостоятельный реестр оснований | если одно основание системно связывается с множеством Tasks и должно иметь свой поиск/lifecycle/права |
| Таблица строк исправления внутри Task | если attachment/внешний набор данных недостаточен, а строки нужно структурно хранить и анализировать в Odoo |
| Properties недостаточны | если нужны жёсткие required/unique constraints, гарантированный audit trail или стабильные schema fields |
| Many2many ТС неудобен | если фильтрация/группировка/поиск по нескольким ТС не подходит реальной ежедневной работе |
| Строгие правила переходов | если реально требуется запретить `Done` без конкретных полей/проверки либо переход в `В работе` без назначения |
| Intake по email | если объём входящих требует автоматического создания, но правило `одно письмо = одна Task` не выполняется |

До подтверждения gap не писать custom-модуль.

## 1.23. Что уже можно считать решённым

| Вопрос | Решение |
|---|---|
| ПЛ является записью Fleet? | **Нет** |
| Task на каждый ПЛ обязательна? | **Нет** |
| Единица Task | **независимо управляемый пакет исправлений** |
| Master data ТС | **Fleet (`fleet.vehicle`)** |
| Работа по исправлению | **Project Task** |
| Внешний follow-up | **Activity** |
| Внешнее ожидание | **Stage `Ожидание` + Activity** |
| Внутренняя Task-зависимость | **Blocked by / системный Waiting** |
| Завершение | **Status `Done` после фактического результата в source of truth** |
| Отмена | **Status `Canceled`** |
| Отдельный Stage `Done` | **Не нужен** |
| Отдельный Stage `Проверка` | **Не вводится без подтверждения реального этапа** |
| Финальное количество Projects | **Пока не решено; отдельный Project только для изолированного пилота** |
| Роли/кто назначает/кто закрывает | **Открытое организационное правило** |
