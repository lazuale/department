# Master data — реестр решений

Этот документ фиксирует **только согласованные решения по master data**.

Технические исследования, кандидаты и возможные модели не становятся архитектурой системы до отдельного согласования.

## 1. Правило принятия решения

Каждый master-data объект рассматривается отдельно:

```text
семантика объекта
→ источник истины
→ есть ли подходящая штатная модель Odoo
→ качество поиска и аналитики
→ стабильность и права
→ импорт / интеграции
→ только затем решение
```

Выбирается не вариант с минимальным количеством кода, а наиболее чистый вариант с точки зрения:

- семантики;
- аналитики;
- стабильности;
- функциональности;
- сопровождения.

При наличии подходящей штатной модели Odoo она используется как предметный master record. `project.task` хранит работу, а не копию справочника.

## 2. Согласовано: люди

**Статус: зафиксировано.**

Полная модель: [24 — Master data: люди](24-master-data-people.md).

```text
человек / сотрудник компании
→ res.partner

доступ в Odoo при необходимости
→ res.users, связанный с тем же res.partner
```

Следствия:

- все сотрудники компании используют единый master record `res.partner`;
- человек без доступа не требует `res.users`;
- сотрудник департамента, руководитель, администратор или будущий portal user остаётся тем же `res.partner`, меняется только учётная запись и права;
- заявитель и другие предметные ссылки на людей используют `res.partner`;
- штатные Assignees Project остаются `res.users`;
- Fleet может использовать тот же справочник людей для водителей;
- Employees / `hr.employee` не входит в baseline только ради справочника сотрудников.

## 3. Согласовано: путевая техника

**Статус: зафиксировано.**

Самосвалы, строительная техника и малая механизация образуют один предметный контур, потому что:

- в действующей учётной системе они ведутся одним списком;
- на эти единицы выписываются путевые листы;
- для операционной работы нужна единая ссылка на конкретную единицу техники независимо от её класса.

```text
самосвалы
строительная техника
малая механизация
        ↓
   fleet.vehicle
```

`fleet.vehicle` является master record конкретной единицы путевой техники.

Разделять этот единый реестр между Fleet и Maintenance только по физическому типу объекта не требуется.

Источник и правила загрузки реквизитов из действующей учётной системы, а также окончательная классификация техники внутри Fleet фиксируются отдельно после разбора исходного справочника.

## 4. Согласовано: сканирующие рамки объёма

**Статус: зафиксировано.**

Единица учёта — конкретная рамка с собственным инвентарным номером.

Рамка может:

- находиться на конкретном участке;
- перемещаться между участками;
- передаваться в ремонт;
- возвращаться в эксплуатацию.

```text
сканирующая рамка
→ maintenance.equipment
```

`maintenance.equipment` является master record конкретной рамки.

Инвентарный номер является её главным бизнес-идентификатором. Конкретная реализация местонахождения и истории перемещений будет определена отдельно вместе с общей моделью участков / мест хранения; ремонтный lifecycle должен использовать штатный контур Maintenance там, где он соответствует процессу.

## 5. Согласовано: терминалы Nobilis и их комплектующие

**Статус: зафиксировано. Используется нативный Inventory / Stock.**

Терминал в предметной модели — **комплект отдельных физических частей**, а не основной блок.

Номер терминала идентифицирует комплект. Основной блок является одной из частей комплекта и имеет собственный серийный номер, как и остальные серийные компоненты.

```text
терминал / комплект
→ stock.package

тип комплектующей
→ product.product

конкретная физическая часть с серийным номером
→ stock.lot

текущее складское местонахождение
→ stock.location / stock.quant

история перемещений и изменения состава
→ stock.move / stock.move.line
```

Правила:

- номер терминала хранится как идентификатор `stock.package`;
- серийный номер основного блока не является номером терминала;
- каждая физическая комплектующая учитывается отдельно по своему `stock.lot` / Serial Number;
- замена части означает изменение содержимого Package штатными складскими операциями, а не перезапись серийника в карточке терминала;
- часть может переходить между терминалами, храниться отдельно или возвращаться производителю с сохранением штатной traceability;
- целый терминал может перемещаться как Package;
- собственная модель терминала для текущего контура не вводится.

Подробная карта согласованных материальных сущностей: [25 — Master data: техника и оборудование](25-master-data-assets.md).

## 6. Согласовано: связь `project.task` с master data

**Статус: зафиксировано для пилота.**

Task хранит работу и контролируемый результат. Master data остаются в своих предметных моделях и не копируются в Task.

Исполнители остаются штатной связью:

```text
project.task.user_ids
→ res.users
```

Для предметных связей в нативном click-only пилоте используются relational Properties:

```text
Заявитель       → Many2one(res.partner)
Связанные люди  → Many2many(res.partner)
Техника         → Many2one / Many2many(fleet.vehicle)
Рамка           → Many2one(maintenance.equipment)
Терминал        → Many2one(stock.package)
Комплектующие   → Many2many(stock.lot)
```

`project.task.partner_id` не переиспользуется как универсальный «Заявитель», потому что штатная семантика этого поля в Project — Customer.

Properties определяются на уровне Project. Поэтому они принимаются как базовый нативный механизм пилота, но перед окончательным production-решением проверяются поиск, аналитика, импорт, API, работа при нескольких Projects и права на target records.

Обычные ORM-поля в `project.task` рассматриваются только при доказанном gap. Само отсутствие schema field не является основанием для custom module.

Полное решение: [26 — Связь Task с master data](26-task-master-data-relations.md).

## 7. Что пока не зафиксировано

До отдельного обсуждения **не считать согласованной архитектурой** модели следующих объектов:

```text
участки / площадки как единый корпоративный master data
виды работ
топливные карты
основания / документы
прочие справочники
```

Важно: использование `stock.location` внутри Inventory для физического местонахождения Nobilis **не означает**, что `stock.location` автоматически принят как универсальная сущность «Участок» для Tasks, Fleet, Maintenance и всей системы.

## 8. Статус технических исследований

Документы `20–23` и другие технические материалы PR могут содержать альтернативные варианты использования Inventory, Maintenance, HR, собственных моделей и связей.

Они остаются **исследовательскими материалами**, если соответствующее решение не перенесено в этот реестр после согласования.

При противоречии между исследовательским документом и этим реестром действует текущее решение из этого реестра и связанного нормативного документа.

## 9. Текущий реестр

| Master data / связь | Odoo model / механизм | Статус |
|---|---|---|
| Люди / сотрудники компании | `res.partner`; доступ через связанный `res.users` | **Согласовано** |
| Самосвалы, строительная техника, малая механизация | `fleet.vehicle` | **Согласовано** |
| Сканирующие рамки объёма | `maintenance.equipment` | **Согласовано** |
| Терминал Nobilis как комплект | `stock.package` | **Согласовано** |
| Тип комплектующей Nobilis | `product.product` | **Согласовано** |
| Конкретная комплектующая Nobilis / Serial Number | `stock.lot` | **Согласовано** |
| Местонахождение и движение Nobilis | `stock.location`, `stock.quant`, `stock.move`, `stock.move.line` | **Согласовано в контуре Inventory** |
| Исполнители Task | `project.task.user_ids → res.users` | **Согласовано** |
| Task → предметные master data | relational `task_properties` | **Согласовано для пилота** |
| Участки / площадки как общий master data | не зафиксировано | **На рассмотрении** |
| Виды работ | не зафиксировано | **На рассмотрении** |
| Топливные карты | не зафиксировано | **На рассмотрении** |
| Основания / документы | не зафиксировано | **На рассмотрении** |
