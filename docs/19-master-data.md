# Справочники и master data для Odoo 19 Community

[Главная](../README.md) · [16 Реестр модулей](16-community-modules-context.md) · [17 Карта процессов](17-real-process-map.md) · [18 Решения по процессам](18-process-decisions.md)

---

Этот документ фиксирует **предметный слой справочников и master data**, на который дальше должны ссылаться процессы, Tasks, Activities, оборудование и аналитика.

Порядок проектирования теперь такой:

```text
master data / справочники
→ предметные связи
→ Tasks / Activities / профильные записи
→ workflow
→ Views / аналитика
```

Процесс не должен заново определять, что такое ТС, сотрудник, участок или оборудование. Он должен ссылаться на уже определённую предметную запись.

## 1. Что считаем master data

Master data — самостоятельная предметная запись, которая:

- существует независимо от конкретной Task;
- имеет устойчивую идентичность;
- используется в нескольких процессах;
- нужна для поиска, фильтрации, группировки или анализа;
- может иметь собственный жизненный цикл;
- не должна копироваться текстом в каждую Task.

Для нашего контура подтверждены следующие семейства master data:

```text
ТС
люди / сотрудники
участки / площадки
терминалы Nobilis
комплектующие терминалов с серийными номерами
рамки измерения объёма
внешние люди / организации — при необходимости
```

Отдельно от master data существуют **исторические регистры событий**:

```text
перемещение оборудования
установка / снятие комплектующего
ремонт / обслуживание
```

Их нельзя заменять текущим значением поля, если нужна история.

## 2. Главное правило идентичности

Каждый предметный объект хранится **один раз в своей естественной модели**.

```text
ТС          → fleet.vehicle
сотрудник   → hr.employee
участок     → отдельная сквозная model участка
оборудование→ maintenance.equipment, если смысл совпадает
```

Task хранит relation на объект, а не его копию.

Плохо:

```text
Task.ТС = "А123АА"
Task.Сотрудник = "Иванов Иван"
Task.Участок = "Участок 1"
```

Правильно:

```text
Task → fleet.vehicle
Task → hr.employee
Task → участок
Task → maintenance.equipment
```

Текстовое значение допустимо только как внешний идентификатор, примечание или временный импортный атрибут, но не как замена master record.

## 3. Не создаём универсальную таблицу «Субъект» на старте

Термин **«субъект работы»** используется методически: это предмет, к которому относится работа.

Но сейчас не создаётся единая искусственная таблица вида:

```text
subject
├── ТС
├── сотрудник
├── участок
├── терминал
└── рамка
```

Такой слой дублировал бы штатные модели Odoo и создавал вторые идентификаторы.

На первом этапе используются **типизированные relations**:

```text
ТС          → fleet.vehicle
Сотрудник   → hr.employee
Участок     → department.site (рабочее имя модели)
Оборудование→ maintenance.equipment
```

Если позднее подтвердится жёсткое требование к единому polymorphic `subject_id` во всех процессах и отчётах, это рассматривается как отдельный технический gap. До этого типизированные связи безопаснее и прозрачнее.

## 4. Сводная модель справочников

| Справочник / объект | Source of truth в Odoo | Решение | Что хранит | История |
|---|---|---|---|---|
| **ТС** | `fleet.vehicle` | **Используем штатно** | идентичность ТС, госномер, VIN/SN, модель и другие нужные атрибуты | отдельная история предметных изменений только если реально нужна |
| **Сотрудники** | `hr.employee` | **Используем штатно** | идентичность сотрудника и необходимые рабочие атрибуты | кадровую историю не моделируем сверх реальной потребности |
| **Внешние люди / организации** | `res.partner` | **Используем при необходимости** | контрагенты, отправители, внешние участники | штатный Chatter/изменения по потребности |
| **Участки / площадки** | отдельная сквозная model | **Минимальная custom model оправдана** | устойчивый код/наименование участка как общий аналитический субъект | архивирование; переименование не должно ломать ссылки |
| **Терминал Nobilis** | `maintenance.equipment` | **Используем как предметную карточку оборудования** | терминал как самостоятельный серийный объект | перемещения и состав — отдельными историческими записями |
| **Комплектующая терминала** | `maintenance.equipment` | **Используем для серийных долговечных компонентов** | отдельный компонент с уникальным serial | установка/снятие из терминала — отдельная история |
| **Рамка измерения объёма** | `maintenance.equipment` | **Используем** | самостоятельная единица оборудования | перемещения между участками + Maintenance Requests для ремонта |
| **Inventory / stock** | `stock.*` | **Не baseline для этих объектов пока** | включать только если потребуется реальный складской учёт, остатки, складские операции или stock traceability | stock moves / serial traceability при таком решении |

## 5. ТС

### 5.1. Естественная model

```text
fleet.vehicle
```

Это основной master record транспортного средства.

Проверенный Odoo 19 source содержит, в частности:

```text
license_plate
vin_sn
model_id
brand_id
state_id
location (text)
tag_ids
vehicle_properties
```

`fleet.vehicle` поддерживает Chatter/Activities и предназначен для самостоятельных записей ТС.

### 5.2. Что считаем ключом

Для интеграций нужен устойчивый внешний ключ.

Кандидаты:

```text
внешний ID из source system — предпочтительно
VIN/SN — если заполнен и действительно уникален в исходных данных
госномер — рабочий поисковый ключ, но не считать вечной идентичностью ТС
```

Госномер может меняться, поэтому нельзя строить всю интеграционную идентичность только на `license_plate`, если внешний источник предоставляет более стабильный ID.

### 5.3. Участок ТС

Если у ТС есть текущая принадлежность к участку, её можно хранить отдельной relation на master участка.

Но историческая аналитика Tasks **не должна зависеть только от текущего участка ТС**.

Иначе:

```text
ТС было на участке A
→ Task закрыта
→ ТС перевели на участок B
→ старый отчёт неожиданно начинает выглядеть как работа участка B
```

Поэтому Task/событие, где участок является контекстом работы, должно хранить собственную relation `Участок` на значение в момент работы.

## 6. Сотрудники / люди

### 6.1. Внутренний сотрудник

```text
hr.employee
```

Используется как master record внутреннего сотрудника.

Не создавать отдельный CSV-справочник ФИО внутри Task Properties.

### 6.2. Внешний человек

Если человек не является сотрудником организации и нужен как самостоятельный участник процесса:

```text
res.partner
```

### 6.3. Идентичность сотрудника

Для импорта нужен устойчивый внешний ID / табельный номер, если он есть в source system.

ФИО не является безопасным уникальным ключом:

- возможны однофамильцы;
- ФИО может измениться;
- возможны разные варианты написания.

### 6.4. Участок сотрудника

Если требуется текущая привязка сотрудника к участку, используем relation на единый справочник участков, а не создаём второй список участков специально внутри HR.

При необходимости анализа исторической работы по участку Task хранит участок как собственный контекст события.

## 7. Участки / площадки

### 7.1. Что это за сущность

Участок — **сквозной предметный и аналитический субъект**, который должен использоваться одновременно для:

```text
Tasks
ТС
сотрудников
терминалов
рамок
других предметных записей
аналитики
```

Поэтому участок не является только:

- рабочим местом сотрудника;
- складской полкой/ячейкой;
- текстовым тегом Task.

### 7.2. Почему не `hr.work.location`

HR Work Location семантически относится к рабочим местам/локациям сотрудников.

Наш участок должен жить независимо от Employees и быть общим master record для транспорта, оборудования и Tasks.

### 7.3. Почему не `stock.location`

Официальная модель Inventory Location описывает физическое место хранения внутри складской логистики: warehouse/room/aisle/shelf и т. п.

Наш участок является более широким операционным субъектом. Использовать `stock.location` как универсальный участок означало бы подчинить всю предметную архитектуру складской модели.

### 7.4. Решение

Минимальная custom model участка **уже имеет доказанный предметный смысл**.

Рабочее техническое имя:

```text
department.site
```

Имя пока проектное; окончательное имя модели определяется при разработке минимального модуля.

### 7.5. Минимальные поля участка

```text
name        — наименование
code        — устойчивый код
active      — активен / архивирован
external_id — внешний идентификатор, если есть
note        — примечание, только при необходимости
```

Базовые требования:

- `code` должен быть уникальным;
- удаление используемого участка не должно быть штатным способом закрытия — использовать архивирование;
- rename не должен ломать связи;
- CSV import/update должен выполняться по устойчивому ключу.

Не добавлять адрес, координаты, юрлицо, тип участка и другие поля без реальной потребности.

## 8. Терминалы Nobilis

### 8.1. Предметная модель

Терминал — самостоятельный физический объект:

- существует независимо от Tasks;
- имеет серийный номер;
- находится на конкретном участке;
- перемещается между участками;
- имеет состав из комплектующих;
- комплектующие периодически заменяются.

Это master data + история состава и движений, а не Task.

### 8.2. Карточка терминала

Базовый кандидат:

```text
maintenance.equipment
category = Терминал Nobilis
```

Штатный Odoo 19 `maintenance.equipment` уже содержит:

```text
name
category_id
model
serial_no
partner/vendor
warranty_date
active
Properties
Chatter / Activities
Maintenance Requests
```

В Community source на `serial_no` есть database constraint `unique(serial_no)`.

Это делает Equipment подходящей базой для индивидуально идентифицируемых терминалов и серийных комплектующих.

### 8.3. Текущий участок терминала

Нужна relation:

```text
maintenance.equipment → department.site
```

с tracking текущего значения.

Но одного Chatter недостаточно для полноценной истории перемещений, если нужны:

- дата перемещения;
- откуда;
- куда;
- основание / акт;
- поиск и анализ истории.

Поэтому перемещение должно иметь отдельную структурированную запись.

## 9. Комплектующие терминалов

### 9.1. Что считаем комплектующей

Если комплектующая:

- имеет собственный серийный номер;
- может быть снята с одного терминала;
- установлена в другой;
- должна сохранять историю;

то она является самостоятельным master record, а не строкой в текстовом поле терминала.

Базовый кандидат:

```text
maintenance.equipment
category = <тип комплектующей>
```

### 9.2. Почему не Properties на терминале

Плохо:

```text
Модем = SN123
Блок = SN456
Датчик = SN789
```

Если просто перезаписывать Property, теряется структурированная история:

```text
какой компонент стоял раньше
когда снят
куда потом установлен
сколько раз менялся
на каких терминалах использовался
```

### 9.3. Нужна история установки / снятия

Для этого нужен отдельный исторический register, например концептуально:

```text
equipment.component.assignment
```

Минимальный состав:

```text
terminal_id       → maintenance.equipment
component_id      → maintenance.equipment
installed_at
removed_at
install_basis     → при необходимости
remove_basis      → при необходимости
active/current
```

Окончательное имя модели и поля определяются при минимальной разработке.

Ключевое правило:

> текущий состав терминала вычисляется из активных assignment-записей; история не уничтожается заменой текущего значения.

## 10. Рамки измерения объёма

### 10.1. Предметная модель

Рамка — самостоятельное оборудование:

```text
maintenance.equipment
category = Рамка измерения объёма
```

Рамка:

- имеет устойчивую идентичность;
- находится на определённом участке;
- перемещается между участками;
- иногда ремонтируется.

### 10.2. Ремонт

Для реального ремонта естественная штатная запись:

```text
maintenance.request
```

Odoo Maintenance Request поддерживает оборудование, стадии, тип corrective/preventive, даты, ответственного техника и историю выполнения.

Task поверх Maintenance Request не создаётся автоматически.

Project Task нужна только если вокруг ремонта возникает отдельный управленческий результат, который не закрывается самой Maintenance Request.

## 11. Общий register перемещений оборудования

Для терминалов и рамок подтверждена потребность в истории перемещений между участками.

Текущее поле `site_id` отвечает только на вопрос:

> где объект находится сейчас?

Оно не отвечает надёжно на вопрос:

> где объект был раньше и на каком основании его переместили?

Поэтому нужен структурированный register перемещения.

Концептуальная model:

```text
equipment.movement
```

Минимальные поля:

```text
equipment_id   → maintenance.equipment
from_site_id   → department.site
to_site_id     → department.site
movement_date
document_date  → если реально используется
document_no    → если реально используется
note           → необязательно
```

При фиксации нового подтверждённого movement текущее поле `equipment.site_id` должно соответствовать последнему движению.

Способ синхронизации определяется при разработке:

```text
movement record
→ update current site
```

Это может быть минимальная ORM-логика; не строить скрытый BPM.

## 12. Почему Inventory пока не делаем обязательным

Inventory отлично подходит, когда реально нужны:

- складские остатки;
- receipts / deliveries / internal transfers;
- складские locations;
- lot/serial traceability;
- движение stock items как складских единиц.

Официальная документация Odoo 19 подтверждает, что serial/lot records дают traceability stock moves и историю местонахождения продукта.

Но текущая подтверждённая потребность другая:

```text
терминал / рамка = эксплуатируемое оборудование
участок = операционный субъект
перемещение = история между участками
комплектующая = серийный долговечный компонент терминала
ремонт = Maintenance
```

Это не автоматически означает складской процесс.

Кроме того, штатный `stock_maintenance` в Odoo 19:

- добавляет `stock.location` в Equipment;
- ищет `stock.lot` по совпадающему серийному номеру;
- не создаёт полноценную структурированную модель состава терминала и истории замен комплектующих.

Поэтому решение:

> **Inventory оставить в категории `Возможно`, а не делать baseline master-data слоя.**

Включать его только если появится реальная потребность вести складские остатки, складские операции или использовать Stock как источник истины движения оборудования/компонентов.

## 13. Связь master data с Tasks

После определения master data Task может ссылаться на предмет работы типизированными relations.

Кандидатный набор:

```text
Task.ТС            → fleet.vehicle
Task.Сотрудник     → hr.employee
Task.Участок       → department.site
Task.Оборудование  → maintenance.equipment
```

Не обязательно показывать все четыре поля во всех Projects.

Для каждого процесса показываются только реально применимые relations.

Пример:

```text
транспортная корректировка
→ ТС
→ Участок

табельная корректировка
→ Сотрудник
→ Участок

работа по терминалу
→ Оборудование
→ Участок
```

## 14. Аналитика по субъекту

Цель master data слоя — позволить отвечать на вопросы без текстового поиска:

```text
все работы по конкретному ТС
все работы по конкретному сотруднику
все работы по конкретному участку
вся история конкретного терминала
все перемещения терминала
какие комплектующие стояли на терминале
где сейчас находится рамка
какие ремонты были у рамки
```

Важно различать:

### Аналитика работы

```text
Task / Activities
→ открыто / закрыто / сроки / backlog / исполнитель
```

### Аналитика master data

```text
Fleet / Employees / Equipment / Site
→ сам объект и его текущие атрибуты
```

### Аналитика истории оборудования

```text
Movement / Component Assignment / Maintenance Request
→ перемещения / состав / ремонт
```

Не пытаться получить историю состава терминала из количества Tasks.

## 15. Исторический контекст и текущие значения

Критическое правило:

> текущая принадлежность объекта не должна переписывать смысл старых событий.

Например:

```text
2026-01: терминал на участке A
2026-03: Task по терминалу на участке A
2026-06: терминал перемещён на участок B
```

Task марта должна сохранять relation на участок A, если участок был частью контекста работы.

Нельзя строить исторический отчёт только через:

```text
Task → Equipment → Current Site
```

иначе вся старая история «переедет» на новый участок.

## 16. Импорт и обновление справочников

Для каждого master-data семейства нужен устойчивый ключ обновления.

| Справочник | Предпочтительный ключ |
|---|---|
| ТС | внешний ID source system; VIN/SN при гарантированной уникальности; госномер только как рабочий идентификатор |
| Сотрудник | внешний ID / табельный номер |
| Участок | уникальный `code` |
| Терминал | `serial_no` + при необходимости внешний ID |
| Комплектующая | `serial_no` + тип/категория при необходимости |
| Рамка | уникальный серийный/инвентарный номер |

CSV import должен обновлять существующие records по ключу, а не создавать дубликаты при каждом импорте.

Архивированные объекты не удаляются из истории.

## 17. Минимальные права

Права проектируются отдельно от должностей.

Нужны как минимум разные действия:

```text
читать master data
создавать master data
изменять master data
архивировать master data
фиксировать movement
фиксировать component assignment
создавать Maintenance Request
```

Исполнитель Task не должен автоматически получать право изменять госномер ТС, ФИО сотрудника, serial оборудования или справочник участков.

## 18. Что уже считается доказанным gap

### 18.1. Сквозной справочник участков

Штатные HR/Stock location-модели не совпадают с нашей сущностью участка как общего аналитического субъекта.

**Статус: минимальная custom model оправдана.**

### 18.2. История перемещений оборудования между участками

Текущее поле местонахождения не даёт структурированную историю движения с `from/to/date/basis`.

**Статус: нужен минимальный исторический register.**

### 18.3. История состава терминала

Штатный Equipment не имеет нативной parent/component history, а `stock_maintenance` не решает этот вопрос.

**Статус: нужен минимальный register установки/снятия серийных компонентов либо другой подтверждённый runtime-механизм.**

Это уже конкретные предметные gaps, а не абстрактные причины «написать свой модуль».

## 19. Что пока не считаем gap

Не считаются доказанными gaps:

- собственный реестр ТС — есть Fleet;
- собственный реестр сотрудников — есть Employees;
- собственный реестр оборудования — есть Maintenance Equipment;
- собственный workflow ремонта — есть Maintenance Requests;
- отдельный справочник каждого типа комплектующих — категории Equipment могут быть достаточны;
- Inventory — наличие серийников само по себе ещё не требует склада;
- универсальный `subject_id` — пока достаточно типизированных relations.

## 20. Минимальный кандидат собственного модуля

Если runtime-проверка подтверждает выбранную архитектуру, custom-разработка должна быть **минимальным расширением штатных моделей**, а не новой системой учёта.

Концептуально модуль должен добавить только недостающий слой:

```text
department.site

fleet.vehicle
└── site_id → department.site   [если требуется текущее закрепление]

hr.employee
└── site_id → department.site   [если требуется текущее закрепление]

maintenance.equipment
├── site_id → department.site
└── штатные serial/category/maintenance

equipment.movement
├── equipment_id
├── from_site_id
├── to_site_id
└── date / basis

equipment.component.assignment
├── terminal_id
├── component_id
├── installed_at
└── removed_at
```

Task relations добавляются только там, где Properties не дают достаточного UX/обязательности/аналитики.

То есть собственный модуль **не заменяет**:

```text
Fleet
Employees
Maintenance
Project
```

Он только связывает их общей предметной моделью участка и добавляет отсутствующую структурированную историю оборудования.

## 21. Runtime-проверки перед реализацией

До кода проверить на пилотном Odoo 19 Community:

1. импорт реального набора `fleet.vehicle`;
2. импорт реального набора `hr.employee`;
3. Equipment category + Equipment для терминала;
4. Equipment для серийной комплектующей;
5. Equipment для рамки;
6. уникальность `maintenance.equipment.serial_no`;
7. Maintenance Request по рамке;
8. UX relational Properties Task → Fleet/Employee/Equipment;
9. нужно ли текущее `site_id` непосредственно на Fleet/Employee или достаточно site-context в Tasks;
10. насколько удобно анализировать Equipment по category/serial/site;
11. есть ли реальный повод включать Inventory после walkthrough движения терминала/компонента.

Только после этих проверок фиксировать окончательную ORM-схему собственного модуля.

## 22. Следующий шаг

После согласования master-data архитектуры:

```text
1. подготовить минимальные CSV-схемы импорта
2. загрузить пилотные справочники
3. создать участки
4. загрузить ТС и сотрудников
5. завести небольшой набор терминалов / комплектующих / рамок
6. проверить relations и историю
7. только затем вернуться к docs/18 и проектированию процессов
```

Именно master data становится первым техническим слоем пилота.

## 23. Источники технической проверки

Проверенный Community snapshot определён в [docs/16](16-community-modules-context.md).

Ключевые source-файлы Odoo 19:

```text
addons/fleet/models/fleet_vehicle.py
addons/maintenance/models/maintenance.py
addons/stock_maintenance/models/maintenance.py
```

Официальная документация Odoo 19 дополнительно подтверждает:

- Equipment предназначен для индивидуальных единиц оборудования с serial/warranty/maintenance history;
- Inventory Lots/Serial Numbers предназначены для traceability складских продуктов и stock moves;
- Inventory Locations являются физическими складскими locations, а не универсальным справочником операционных участков.
