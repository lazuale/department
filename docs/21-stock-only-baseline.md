# Штатный baseline Odoo 19 Community

[Главная](../README.md) · [16 Реестр модулей](16-community-modules-context.md) · [20 Аудит досье субъекта](20-subject-dossier-stock-audit.md) · [19 Master data](19-master-data.md)

---

Этот документ фиксирует **текущее принятое ограничение проекта**:

> На данном этапе используем только штатные возможности официального Odoo 19 Community.

Цель этапа — собрать максимально рабочий контур на стандартных моделях, официальных Community-модулях и штатной конфигурации, а затем уже оценивать фактические компромиссы.

## 1. Приоритет этого решения

Это решение имеет приоритет над более ранними гипотезами о custom-моделях и собственном связующем модуле.

В частности, идеи из `docs/19-master-data.md` вида:

```text
department.site
equipment.movement
equipment.component.assignment
custom relations / smart buttons
```

**не являются принятыми решениями** текущего этапа.

Они сохраняются только как возможные будущие варианты, если штатный пилот покажет неприемлемый gap.

## 2. Что считается штатным вариантом

Допускаются:

- официальные модули из публичной ветки `odoo/odoo:19.0`, подтверждённые в `docs/16-community-modules-context.md`;
- стандартные Odoo models и их штатные relations;
- стандартные Properties, включая relational Properties;
- Tags;
- стандартные поля и настройки приложений;
- стандартные List / Kanban / Form / Search / Pivot / Graph / Activity views;
- фильтры, группировки, Favorites / Shared Views, если доступны штатно;
- Chatter и Activities;
- Task Templates, Recurring Tasks, Dependencies и другие штатные механизмы Project;
- стандартный CSV/XLSX import/export;
- штатные Groups / Access Rights / Record Rules / Project visibility;
- официальные Community bridge-модули;
- Automation Rules только как штатный механизм и только после отдельной проверки конкретного сценария.

## 3. Что сейчас не принимается

На текущем этапе не используем как решение:

- собственные Odoo-модули;
- собственные Python models;
- собственные ORM fields;
- собственные XML views / smart buttons;
- OCA и иные сторонние модули;
- прямую доработку core Odoo;
- прямую запись в PostgreSQL;
- Server Action / Automation с произвольным Python-кодом как способ достроить предметную модель;
- попытку имитировать отсутствующую модель скрытым кодом.

Если требование штатно не закрывается, оно фиксируется как **gap**, а не автоматически превращается в разработку.

## 4. Правило выбора решения

Для каждого требования используем последовательность:

```text
1. Есть штатная Odoo model?
   ↓
2. Есть штатный модуль / bridge?
   ↓
3. Можно ли закрыть задачу стандартным полем / Property / Tag / Activity / View?
   ↓
4. Можно ли получить приемлемый UX через стандартный поиск / фильтр / переход?
   ↓
5. Если да — принимаем штатный компромисс.
   ↓
6. Если нет — фиксируем gap и продолжаем пилот без самодельного обхода.
```

## 5. Текущий baseline по субъектам

### ТС

```text
fleet.vehicle
```

Используем штатную карточку Fleet.

Связь Task с ТС на текущем этапе проверяется только штатными relational Properties.

Если из карточки ТС нет обратной кнопки на все Project Tasks, это принимается как штатное ограничение пилота; доступ к работам проверяется через Project search/filter.

### Сотрудник

```text
hr.employee
```

Используем штатную карточку Employees.

Штатные связи с Equipment через `hr_maintenance` допускаются.

Операционные Tasks, где сотрудник является **предметом работы**, не подменяются Assignee. Для предметной привязки проверяется relational Property на `hr.employee`.

### Терминал Nobilis

Первый штатный кандидат:

```text
maintenance.equipment
```

Проверяем штатно:

- карточку Equipment;
- serial number;
- Properties;
- Chatter / Activities;
- Maintenance Requests;
- назначение сотруднику/подразделению через `hr_maintenance`;
- текущую location-семантику;
- возможный Inventory-контур для serial/location/movement.

Собственная модель терминала сейчас не рассматривается.

### Рамка измерения объёма

Первый штатный кандидат:

```text
maintenance.equipment
```

Ремонты проверяются через `maintenance.request`.

Перемещения проверяются только штатными способами Maintenance / Inventory. Отдельный register movement сейчас не создаётся.

### Участок / площадка

Собственная `department.site` сейчас **не принимается**.

Проверяются только штатные кандидаты:

```text
hr.work.location
stock.location
```

а также возможность использовать участок как Property / Tag там, где самостоятельная карточка участка не обязательна.

Если ни один штатный вариант не даст приемлемой привязки и аналитики, это будет зафиксировано как gap пилота.

## 6. Требование «все чихи по субъекту»

На текущем этапе требование трактуется прагматично:

```text
можно ли без кода найти все существенные записи по субъекту?
```

Не требуется заранее, чтобы всё обязательно открывалось одной smart button из карточки субъекта.

Принимаемый штатный путь может выглядеть так:

```text
карточка субъекта
+ штатная история профильного приложения
+ Project search/filter по relational Property
+ Maintenance / Inventory history
+ Chatter / Activities
```

Критерий пилота:

- данные находятся однозначно;
- поиск не требует ручного сопоставления текстовых названий;
- пользователь может повторить сценарий без технических знаний;
- аналитика по субъекту воспроизводима;
- неудобство не разрушает ежедневную работу.

Если это выполняется, отсутствие единой кнопки `Все работы` считается допустимым компромиссом.

## 7. Как фиксируем gaps

Gap описывается только в форме:

```text
Требование
→ какой штатный путь проверен
→ где именно возникает ограничение
→ сколько действий требуется пользователю
→ что невозможно получить
→ насколько это влияет на работу / контроль / аналитику
```

Не писать `нужен custom module`, пока отдельно не принято решение выйти за пределы штатного baseline.

## 8. Следующий этап

Продолжение работы строится только от штатного пилота:

```text
справочники и субъектные карточки
→ штатные связи
→ штатный поиск/фильтры
→ реальные Tasks
→ workflow
→ контроль
→ список фактических gaps
```

До отдельного решения об изменении baseline вся методика должна исходить из принципа:

> **Сначала адаптируем процессы к штатному Odoo 19 Community настолько, насколько это не ломает необходимый контроль и достоверность данных.**
