# Нативная модель Task и привязки к субъектам

[Главная](../README.md) · [21 Штатный baseline](21-stock-only-baseline.md) · [22 Справочники и субъекты](22-stock-master-data-model.md)

---

Этот документ фиксирует **текущее решение следующего слоя** после master data:

> как в штатном Odoo 19 Community создавать операционные Project Tasks, привязывать их к ТС, сотруднику, участку, оборудованию и серийному объекту, а затем воспроизводимо находить всю работу по субъекту.

Граница решения прежняя: только официальный Odoo 19 Community, без custom fields/models/views, OCA и собственного кода.

## 1. Почему начинаем с одного операционного Project

В Odoo 19 Task Properties определяются не глобально для всех Tasks, а на уровне Project:

```text
project.project.task_properties_definition
        ↓
project.task.task_properties
```

То есть Property, созданная для Tasks одного Project, не становится автоматически общей схемой для Tasks другого Project.

Поэтому текущий baseline:

```text
Project: Операционная работа
```

В нём ведутся те работы департамента, которые действительно являются Project Tasks.

Это не означает, что вся Odoo-система сводится к одному Project:

```text
ремонт оборудования        → Maintenance Request
физическое перемещение     → Inventory Transfer
Fleet-события              → Fleet
операционная работа        → Project Task
```

Новый Project создаётся только если позже подтвердится реальная отдельная граница:

- права/видимость;
- materially different workflow;
- отдельный lifecycle;
- отдельное project-level управление;
- необходимость независимой схемы Task Properties.

Не создаём Project просто потому, что появился новый вид работы.

## 2. Штатная Task остаётся карточкой работы, а не карточкой субъекта

Основные штатные поля Task используем по их прямому назначению:

| Поле Odoo | Использование |
|---|---|
| **Task Title** | кратко описывает контролируемый результат |
| **Project** | `Операционная работа` |
| **Assignees** | кто выполняет работу |
| **Deadline** | реальный срок результата, если он есть |
| **Stage** | положение работы в текущем workflow |
| **Task Status** | системный статус Odoo: In Progress / Changes Requested / Approved / Done / Canceled |
| **Priority** | только когда приоритет реально влияет на порядок работы |
| **Tags** | дополнительная лёгкая классификация, не замена справочникам |
| **Description** | рабочее описание / условия результата |
| **Chatter** | коммуникация и история по самой Task |
| **Activities** | следующее действие / follow-up |
| **Dependencies** | только реальная зависимость от другой Task |
| **Subtasks** | отдельные части работы, которые требуют собственного контроля |

Task не дублирует Fleet, Employee, Equipment, Serial или Inventory Location.

## 3. Единый набор субъектных Properties

На Project `Операционная работа` создаём штатные relational Properties.

### 3.1. ТС

```text
Property: ТС
Type: Many2one
Model: fleet.vehicle
```

Используется, когда работа относится к конкретному транспортному средству.

Если реальный процесс требует одной Task сразу по нескольким ТС, только для такого процесса рассматриваем `Many2many`; базово сохраняем `Many2one`, чтобы не размывать единицу работы.

### 3.2. Сотрудник

```text
Property: Сотрудник
Type: Many2one
Model: hr.employee
```

Это **предмет работы**, а не исполнитель.

```text
Assignees = кто делает
Сотрудник = по кому выполняется работа
```

### 3.3. Участок

```text
Property: Участок
Type: Many2one
Model: stock.location
```

Используется как операционный контекст работы.

Для обычной Task достаточно одного `Участок`.

`Откуда` / `Куда` не добавляем в универсальную карточку Task: физическое перемещение ведётся штатным Inventory Transfer. Если Project Task управляет организацией перемещения, она может ссылаться на участок результата, а фактический маршрут остаётся в Inventory.

### 3.4. Оборудование

```text
Property: Оборудование
Type: Many2one
Model: maintenance.equipment
```

Используется для терминалов Nobilis, рамок и других Equipment records, когда Task относится именно к эксплуатационному объекту.

Не используется вместо `maintenance.request` для самого ремонта.

### 3.5. Серийный объект / комплектующая

```text
Property: Серийный объект
Type: Many2one
Model: stock.lot
```

Используется, когда работа относится к конкретному physical serial: комплектующей, терминалу/рамке в Inventory-контуре или другому tracked item.

Не копируем serial текстом, если соответствующий `stock.lot` уже существует.

## 4. Контекстные Properties Task

Помимо субъектов в Project допускается небольшой общий набор контекстных Properties.

### Вид работы

```text
Property: Вид работы
Type: Selection
```

Нужен для общей очереди и аналитики одного Project.

Список значений утверждается только после прохода по реальным процессам. До этого не создаём искусственный большой классификатор.

### Внешний номер / основание

```text
Property: Внешний номер / основание
Type: Text
```

Используем только для номера ПЛ, СЗ, обращения, реестрового ID или другой внешней ссылки, которая нужна для поиска.

Сам документ/файл остаётся вложением, ссылкой или записью профильной системы; текстовое поле не превращается в отдельный реестр документов.

### Период с / Период по

```text
Период с  → Date
Период по → Date
```

Добавляем только если период регулярно нужен для выполнения и поиска работ. Для единичной даты используется одно из полей по согласованному правилу процесса.

## 5. Что не добавляем в универсальную Task

Не создаём без доказанной потребности:

```text
Откуда
Куда
Снятая комплектующая
Установленная комплектующая
Номер ремонта
Номер transfer
Тип топлива
номер топливной карты
табельный участок
юрлицо
смена
старший
проверяющий
```

Если атрибут относится только к одному процессу, сначала проверяем, не существует ли он уже в профильной записи Odoo или source system.

Причина: Properties принадлежат Project. Любое лишнее универсальное поле засоряет карточку всех Tasks этого Project.

## 6. Правило заполнения субъектов

Properties в штатном Odoo являются pseudo-fields. Текущий baseline не рассчитывает на custom required constraints.

Поэтому используется простое методическое правило:

> Заполняем только те субъектные Properties, которые реально относятся к данной Task, но если без субъекта невозможно однозначно понять предмет работы, соответствующая Property должна быть заполнена до начала исполнения.

Примеры:

```text
Исправить данные ПЛ по конкретной машине
→ ТС обязательно по смыслу

Разобрать ошибку по конкретному человеку
→ Сотрудник обязательно по смыслу

Проверить терминал TN-001
→ Оборудование обязательно по смыслу

Сверить общий отчёт по периоду
→ субъект может отсутствовать
```

Не заполняем пустые/фиктивные значения только ради одинаковой карточки.

## 7. «Все чихи по субъекту» в штатном baseline

Штатная модель не обещает универсальный reverse smart button из каждой карточки субъекта в Project Tasks.

Текущий принятый путь:

```text
Project → Tasks
→ фильтр по Property нужного субъекта
→ вся открытая и закрытая операционная работа по нему
```

Одновременно профильные события остаются в своих приложениях:

```text
ТС
→ Fleet history
→ Project Tasks по Property ТС

Сотрудник
→ Employees
→ Project Tasks по Property Сотрудник

Терминал / рамка
→ Maintenance Requests
→ Inventory traceability
→ Project Tasks по Property Оборудование / Серийный объект

Участок
→ Inventory location / movements
→ Project Tasks по Property Участок
```

То есть «досье» в штатном baseline является **составным**, но все части используют структурированные records, а не ручное совпадение текста.

## 8. Штатные поиски и Favorites

Для Project Tasks создаём и сохраняем стандартными средствами Odoo рабочие поиски:

```text
Открытые работы
Просроченные
Без исполнителя
По ТС
По сотруднику
По участку
По оборудованию
По серийному объекту
По виду работы
Мои работы
```

Для конкретного субъекта пользователь применяет значение relational Property.

Нужные поиски сохраняются через Favorites; общие Favorites можно расшаривать штатными средствами Odoo пользователям.

До runtime-проверки не утверждаем конкретную раскладку Search view, но сам механизм Filters / Group By / Favorites является штатным.

## 9. Stage и Status пока не смешиваем с субъектной моделью

Субъектные Properties не определяют workflow.

```text
субъект = о чём работа
Stage   = где работа находится в процессе
Status  = системное состояние Task
Activity= что нужно сделать следующим
```

Поэтому после утверждения этой модели следующий шаг — пройти реальные процессы и определить, какой минимальный общий workflow действительно подходит для одного операционного Project и где есть исключения.

## 10. Проверенные технические основания Odoo 19

В официальном Community source:

```text
project.project.task_properties_definition
    = PropertiesDefinition('Task Properties')

project.task.task_properties
    = Properties(... definition='project_id.task_properties_definition')
```

Следствие: схема Properties Task является Project-scoped.

Официальная документация Odoo 19 подтверждает:

- Properties являются pseudo-fields и для Tasks зависят от родительского Project;
- Properties поддерживают relational типы;
- Project Task штатно содержит Assignees, Tags, Deadline и другие стандартные поля;
- Task Stages project-specific по умолчанию и могут быть shared между несколькими Projects;
- Filters / Group By / Favorites являются стандартным механизмом поиска и сохранения представлений.

## 11. Текущее решение

```text
один операционный Project
        ↓
единая Project-scoped схема Properties
        ↓
ТС / Сотрудник / Участок / Оборудование / Serial
        ↓
Project Tasks как управляемая работа
        ↓
профильные факты остаются во Fleet / Inventory / Maintenance
```

Это считается текущим нативным baseline до появления доказанного требования, которое он не закрывает.
