## Статус решения

Для текущего контура Odoo 19 Community зафиксирована единая модель людей без обязательной установки Employees / HR.

Это решение относится только к master data **людей**. Остальные master data рассматриваются отдельно.

## 1. Единая запись человека

Все сотрудники компании ведутся как записи:

```text
res.partner
```

Одна запись человека переиспользуется во всех рабочих ролях, где Odoo или наша модель ожидает контакт / человека.

Не создаются отдельные карточки одного человека только потому, что он в разных случаях является заявителем, связанным сотрудником, водителем или пользователем системы.

## 2. Доступ в Odoo — отдельный слой

`res.partner` отвечает за запись человека.

`res.users` создаётся только тем людям, которым нужен вход в Odoo, и связывается с той же записью `res.partner`.

```text
сотрудник без доступа
→ res.partner

сотрудник с доступом
→ res.partner
  └── res.users
```

Уровень доступа определяется правами `res.users`, а не созданием другой карточки человека.

Поэтому сотрудник департамента, руководитель, администратор и будущий portal user остаются теми же людьми в master data; меняется только наличие и права учётной записи.

## 3. Использование в Project

Для задач различаются две роли:

```text
Заявитель / связанный человек
→ res.partner

Исполнитель Task
→ штатный Assignees / res.users
```

Исполнитель должен быть пользователем системы, потому что Odoo назначает Task на `res.users`.

Заявитель или человек, которого касается работа, не обязан иметь учётную запись Odoo.

## 4. Использование в других штатных моделях

Если штатная модель Odoo уже ссылается на `res.partner`, используется тот же справочник людей.

В частности, Fleet использует `res.partner` для водителя, поэтому отдельный справочник водителей не создаётся.

## 5. Employees / HR не входит в базовый контур

Модуль `hr` не устанавливается только ради справочника сотрудников.

```text
Contacts / res.partner
→ единый рабочий справочник людей

Users / res.users
→ только доступ в систему
```

Employees / `hr.employee` возвращается на рассмотрение только если появится реальная потребность в HR-функциональности, для которой `res.partner` недостаточен.

Наличие HR-модуля в Odoo Community само по себе не является причиной включать его в рабочий контур.

## 6. Граница данных

`res.partner` в этом проекте используется как **операционный справочник людей**, а не как кадровая система.

В него входят только данные, необходимые рабочим процессам и идентификации человека. Состав конкретных полей справочника будет определён отдельным решением по master data.

Кадровые данные и HR-процессы этим решением не моделируются.

## 7. Базовая схема

```text
ВСЕ ЛЮДИ КОМПАНИИ
        │
        ▼
    res.partner
        │
        ├── заявитель Task
        ├── связанный человек Task
        ├── водитель Fleet
        └── другие роли, где модель использует partner
        │
        └── если нужен вход
                ▼
             res.users
                ├── internal user
                ├── administrator
                └── portal user при будущем внешнем доступе
```

## 8. Правила модели

1. Один человек — одна master record `res.partner`.
2. Не создавать `hr.employee` только ради выбора сотрудника в Task.
3. Не использовать `res.users` как общий справочник сотрудников компании.
4. Не дублировать человека при выдаче ему доступа в Odoo.
5. Assignees остаются штатными `res.users`.
6. Предметные ссылки на людей используют `res.partner`, если специализированная модель не доказана отдельной потребностью.
7. HR добавляется только при появлении реального HR-контура.

## 9. Следующий шаг

После фиксации модели людей остальные master data рассматриваются по одному и по тому же критерию:

```text
семантика
→ источник истины
→ штатная модель Odoo
→ аналитика
→ стабильность
→ права
→ необходимость минимальной доработки
```

До отдельного согласования этот документ не определяет модель участков, видов работ, документов, оборудования, карт и других справочников.
