# Master data — техника и оборудование

[Главная](../README.md) · [19 Реестр master data](19-master-data.md) · [24 Люди](24-master-data-people.md)

---

Этот документ фиксирует **согласованные предметные модели техники и оборудования** для текущего контура Odoo 19 Community.

Цель — не создать универсальный реестр «всего железа», а использовать штатную Odoo model там, где её предметный смысл совпадает с реальным объектом учёта.

## 1. Общая карта

```text
ПУТЕВАЯ ТЕХНИКА
├── самосвалы
├── строительная техника
└── малая механизация
        ↓
   fleet.vehicle

СКАНИРУЮЩИЕ РАМКИ ОБЪЁМА
        ↓
maintenance.equipment

NOBILIS
├── терминал как комплект      → stock.package
├── тип части                  → product.product
├── физическая часть / Serial  → stock.lot
├── текущее положение          → stock.location / stock.quant
└── движение / смена состава   → stock.move / stock.move.line
```

Эти три контура не объединяются искусственно в одну собственную модель `asset`.

## 2. Путевая техника — `fleet.vehicle`

В один реестр входят:

- самосвалы;
- строительная техника;
- малая механизация.

Основание решения — не внешний вид техники, а единый предметный контур:

```text
единый список в действующей учётной системе
+
на объект выписывается путевой лист
+
нужна единая операционная ссылка на конкретную единицу
        ↓
fleet.vehicle
```

Поэтому экскаватор, бульдозер или единица малой механизации не переводятся в `maintenance.equipment` только потому, что они не являются обычным автомобилем.

`fleet.vehicle` — единая master-запись конкретной путевой единицы.

Окончательный состав полей, внешние идентификаторы и классификаторы должны быть определены по фактическому справочнику источника данных. Эти детали не меняют выбранную корневую модель.

## 3. Сканирующие рамки объёма — `maintenance.equipment`

Единица учёта — **конкретная рамка**.

```text
рамка
├── собственный инвентарный номер
├── текущее состояние
├── местонахождение
└── история обслуживания
        ↓
maintenance.equipment
```

Инвентарный номер является главным бизнес-идентификатором рамки.

Рамка может перемещаться между участками, уходить в ремонт и возвращаться в эксплуатацию. Поэтому она является самостоятельной единицей оборудования, а не атрибутом Task и не строкой общего справочника техники Fleet.

Универсальная модель участков / площадок пока не согласована. Поэтому способ связи рамки с участком не фиксируется в этом документе раньше времени.

## 4. Nobilis — нативный Inventory / Stock

### 4.1. Что считается терминалом

Терминал — **комплект отдельных физических частей**.

```text
Терминал T-001
│
├── основной блок  SN-BASE-001
├── компонент A    SN-A-105
└── компонент B    SN-B-211
```

Номер `T-001` идентифицирует комплект.

Основной блок не является самим терминалом. Он является одной из физических частей комплекта и имеет собственный Serial Number.

### 4.2. Корень комплекта — `stock.package`

```text
терминал / комплект
→ stock.package
```

`stock.package.name` используется как номер терминала / Package Reference.

Package хранит текущее содержимое и участвует в штатных складских перемещениях.

Собственная `terminal` model не вводится.

### 4.3. Тип комплектующей — `product.product`

```text
«Основной блок Nobilis»
«Модем Nobilis»
«Датчик Nobilis»
        ↓
product.product
```

`product.product` описывает **что это за тип части**, а не конкретный физический экземпляр.

### 4.4. Конкретная комплектующая — `stock.lot`

Каждая физическая часть, которая имеет собственный серийный номер, учитывается как Serial Number:

```text
product.product: Модем Nobilis
        ↓
stock.lot: SN-MDM-000456
```

Следствия:

- серийный экземпляр не теряет идентичность при замене;
- одна и та же часть может последовательно находиться в разных терминалах;
- часть может храниться отдельно от терминала;
- часть может быть возвращена производителю;
- история не должна сводиться к перезаписи текстового поля в карточке комплекта.

### 4.5. Текущее положение — `stock.location` и `stock.quant`

Внутри Inventory фактическое текущее состояние запасов определяется штатными stock records:

```text
где находится
→ stock.location

какой product / serial / package находится в location
→ stock.quant
```

Это решение относится именно к Inventory-контексту Nobilis.

`stock.location` пока **не считается универсальным master data «Участок»** для всех остальных приложений Odoo.

### 4.6. Перемещения и изменение состава

История физических операций остаётся штатной:

```text
stock.move
stock.move.line
```

На уровне конкретной операции `stock.move.line` связывает продукт, Serial Number, исходное и конечное местонахождение, а также Package.

Поэтому реальные события моделируются складскими операциями:

```text
переместить весь терминал
→ переместить Package

снять часть из T-001
→ serial выходит из Package T-001

поставить новую часть
→ serial входит в Package T-001

переставить часть T-001 → T-007
→ stock operation между Package

вернуть часть производителю
→ stock operation конкретного Serial

вернуть комплект производителю
→ stock operation Package
```

Отдельный регистр `terminal_component_history` для текущего решения не нужен: состав и traceability должны опираться на штатный Stock.

## 5. Граница между выбранными моделями

```text
fleet.vehicle
= единица путевой техники

maintenance.equipment
= самостоятельная эксплуатируемая рамка

stock.package
= терминал Nobilis как комплект

product.product
= тип комплектующей

stock.lot
= конкретная серийная комплектующая
```

Один и тот же термин не должен использоваться для разных смыслов только ради унификации интерфейса.

## 6. Что этим решением не определяется

Пока отдельно не согласованы:

- универсальная сущность участка / площадки;
- структура классификатора путевой техники;
- точный набор полей синхронизации с внешней учётной системой;
- виды работ;
- топливные карты;
- основания / документы;
- правила связи этих master records с `project.task` в конкретных процессах.

Эти вопросы принимаются следующими отдельными решениями и затем добавляются в [19 — Реестр master data](19-master-data.md).
