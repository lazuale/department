# Связь Task с master data

[Главная](../README.md) · [19 Реестр master data](19-master-data.md) · [24 Люди](24-master-data-people.md) · [25 Техника и оборудование](25-master-data-assets.md)

---

Этот документ фиксирует **согласованный способ связывать `project.task` с предметными master data** в текущем контуре Odoo 19 Community.

## 1. Базовый принцип

`project.task` хранит **работу и контролируемый результат**, а не копию карточки предметного объекта.

```text
master record
    ↑
    │ relation
project.task
```

Данные предметного объекта остаются в своей штатной модели Odoo.

Примеры:

```text
человек        → res.partner
путевая техника → fleet.vehicle
рамка          → maintenance.equipment
терминал       → stock.package
комплектующая  → stock.lot
```

Task не должен дублировать ФИО, госномер, VIN, инвентарный номер, серийный номер, состав терминала или иные поля master record только ради отображения контекста работы.

## 2. Штатные связи Task

Исполнители остаются штатным полем Project:

```text
project.task.user_ids
→ res.users
```

Это пользователи Odoo, отвечающие за выполнение Task.

`project.task.partner_id` в штатной модели Project имеет семантику **Customer**. Для текущего контура он не переименовывается и не используется как универсальный «Заявитель» только ради отсутствия отдельного поля.

## 3. Нативный click-only способ — relational Properties

Для предметных связей в пилоте используется штатный `project.task.task_properties`.

Определение Properties задаётся на уровне Project через `project_id.task_properties_definition`.

Базовый набор:

```text
Заявитель
→ Many2one(res.partner)

Связанные люди
→ Many2many(res.partner)

Техника
→ Many2one / Many2many(fleet.vehicle)

Рамка
→ Many2one(maintenance.equipment)

Терминал
→ Many2one(stock.package)

Комплектующие
→ Many2many(stock.lot)
```

Конкретная Property заполняется только тогда, когда соответствующий объект действительно относится к работе.

## 4. Разные роли людей не смешиваются

```text
Исполнитель Task
→ res.users

Заявитель
→ res.partner

Человек, являющийся предметом работы
→ res.partner
```

Например, аналитик может быть исполнителем Task, а другой сотрудник — человеком, по которому выполняется сверка или исправление.

Один и тот же `res.partner` не дублируется только из-за разных ролей в процессе.

## 5. Связь с путевой техникой

```text
Task
└── Техника → fleet.vehicle
```

В Task не копируются госномер, VIN, модель или другие реквизиты техники.

Если одна работа действительно относится к нескольким единицам техники, используется Many2many. Не следует выбирать Many2many по умолчанию только «на всякий случай».

## 6. Связь с рамкой

```text
Task
└── Рамка → maintenance.equipment
```

Инвентарный номер, состояние и остальные реквизиты рамки остаются в Equipment.

Task фиксирует работу с рамкой, например проверку, перемещение, ремонтный вопрос или разбор расхождения, если такая Task действительно нужна процессу.

## 7. Связь с Nobilis

Если работа относится ко всему терминалу как комплекту:

```text
Task
└── Терминал → stock.package
```

Если работа относится к конкретной серийной части:

```text
Task
├── Терминал      → stock.package   # если контекст терминала нужен
└── Комплектующая → stock.lot
```

Текущий состав Package не копируется в Task. Источником истины по составу, местонахождению и движениям остаётся Inventory / Stock.

Если состав терминала после создания Task изменился, это не должно переписывать исторический смысл самой работы. Когда для результата критично зафиксировать конкретную часть, Task связывается непосредственно с соответствующим `stock.lot`.

## 8. Properties принадлежат Project

`task_properties` определяются через текущий Project.

Следствие:

```text
Project A → своё определение Properties
Project B → своё определение Properties
```

Поэтому Properties принимаются как основной **нативный click-only механизм пилота**, но не объявляются автоматически окончательной schema-моделью для любой будущей архитектуры с множеством Projects.

## 9. Когда возможны обычные ORM-поля

Отсутствие Python-поля само по себе **не является gap**.

Переход от Properties к обычным relational fields рассматривается только если пилот докажет проблему в одном из значимых сценариев:

```text
сквозной поиск по нескольким Projects
группировка / аналитика
массовый импорт
API / интеграции
BI / SQL
производительность
ограничения / обязательность
аудит изменений
```

Тогда допускается минимальное расширение `project.task`, например:

```text
requester_partner_id → res.partner
vehicle_ids          → fleet.vehicle
frame_id             → maintenance.equipment
package_id           → stock.package
lot_ids              → stock.lot
```

Это не означает создание собственной системы задач или копирование master data.

## 10. Что должно быть проверено на пилоте

До окончательного решения по schema fields проверяются:

1. поиск по relational Properties;
2. группировка и Task Analysis;
3. импорт и массовое заполнение;
4. API-представление;
5. работа при нескольких Projects;
6. права пользователя на target master records;
7. удобство карточки Task при реальном потоке работы.

## 11. Итоговая граница

```text
MASTER DATA                     WORK
───────────                     ────
res.partner          ←────┐
fleet.vehicle        ←────┤
maintenance.equipment←────┤── project.task
stock.package        ←────┤
stock.lot            ←────┘

связь пилота → relational Properties
исполнители  → штатный user_ids
```

Источник истины по предметному объекту всегда остаётся в его master model.
