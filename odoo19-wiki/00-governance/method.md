# Метод изучения Odoo 19

## Область курса

Курс изучает **Odoo 19.0 Community в самостоятельном развёртывании (self-hosted)** как платформу и ERP-систему: архитектуру, ORM, данные, безопасность, пользовательский интерфейс, механизмы расширения, работу сервера, а затем штатные бизнес-модели и сквозные процессы.

В базовый контур не включаются автоматически:

- функции, подтверждённые только для Enterprise;
- особенности Odoo Online;
- особенности Odoo.sh;
- ветки `saas-19.x`, если утверждение должно описывать именно Odoo 19.0.

Официальные примеры собственных модулей допустимы как учебный инструмент для понимания платформы. Они **не означают**, что собственные дополнения входят в штатный набор Odoo Community.

## Язык курса

Основной язык wiki — **русский**.

Английский сохраняется только там, где он нужен для точности:

- точные имена классов Odoo и Python: `Model`, `Field`, `Environment`, `Many2one`;
- имена методов, полей и атрибутов: `search()`, `readonly`, `_name`, `company_id`;
- технические идентификаторы и фрагменты кода;
- устойчивый термин при первом вводе, если без оригинала сложно сопоставить объяснение с документацией.

Правильная подача:

```text
модель (`Model`)
поле (`Field`)
запись (`record`)
набор записей (`recordset`)
окружение (`Environment`)
```

После первого ввода в обычном тексте используется русский термин, если это не создаёт неоднозначности.

Запрещена бессмысленная смесь языков вида:

```text
field semantics
runtime behavior
canonical owner
business model decision
```

внутри русского объяснения, если смысл нормально передаётся по-русски.

Код, имена API и ссылки на официальную документацию не переводятся.

## Три типа утверждений

- **[ODOO]** — утверждение непосредственно следует из официальной документации Odoo 19.0;
- **[ВЫВОД]** — наше логическое следствие документированных механизмов;
- **[ERP-КЛАССИФИКАЦИЯ]** — внешний термин для анализа бизнес-смысла, а не внутренний тип, класс или модель Odoo.

Если сама Odoo использует термин в другом значении, контекст всегда уточняется. Например, **master data модуля Odoo** и **ERP master data** — разные понятия.

## Владение понятиями

У каждого фундаментального понятия есть **один канонический владелец** — урок, где понятие впервые определяется полноценно.

Другие уроки могут владеть только явно указанным **аспектом** понятия.

Пример:

```text
базовая семантика Environment → ORM-01
аспект безопасности           → SEC-01
аспект компании               → EXT-04
кэш и предзагрузка             → RUN-01
```

Разрешены три режима использования:

- **предварительное упоминание** — краткое обозначение до канонического урока;
- **использование** — применение уже определённого понятия;
- **аспект** — подробное развитие только назначенной стороны понятия.

Запрещено давать второе независимое каноническое определение. Карта хранится в [concept-ownership.md](concept-ownership.md).

## Полнота покрытия

Карта владельцев защищает от дублей, но не от пропусков. Поэтому разделы официальной документации сопоставляются с курсом в [coverage-map.md](coverage-map.md).

Допустимые статусы закрыты:

- `covered` — покрыто;
- `in progress` — в работе;
- `planned` — запланировано;
- `intentionally deferred` — сознательно отложено;
- `out of scope` — вне области курса.

Если нужно указать частичное покрытие или отдельный аспект, это записывается в колонке владельца/области, а не превращается в новый статус.

Крупный раздел курса нельзя считать завершённым, пока соответствующая часть карты покрытия не сверена с актуальным индексом документации Odoo 19.0.

## Трассировка источников

Каждое утверждение **[ODOO] обязано** иметь хотя бы один локальный ID источника:

```text
[ODOO][S1]
```

Правило:

```text
1 ID источника = 1 страница официальной документации
```

Если утверждение подтверждается несколькими страницами:

```text
[ODOO][S1][S2]
```

Внизу урока:

```text
S1 — ORM API — <официальный URL>
S2 — Server Framework 101 — <официальный URL>
```

Одна страница может подтверждать много утверждений, но один `S#` не должен объединять разные страницы.

Для `[ВЫВОД]` ID источника в самой метке не обязателен, но исходные факты `[ODOO]` должны быть прослеживаемы.

Полная политика — в [source-policy.md](source-policy.md).

## Community / Enterprise

Наличие страницы в общей документации **не доказывает** доступность функции в Community. Доказательства по редакциям хранятся отдельно в [edition-ledger.md](edition-ledger.md).

### Ограничение режима «только документация»

При текущих правилах официальная документация является единственным источником фактов.

Это позволяет глубоко изучать документированную семантику платформы, но **не гарантирует исчерпывающий технический список всех модулей Community**, поскольку общая документация не является полной матрицей CE/EE.

Если когда-либо потребуется доказать полный состав модулей Community, использование официального исходного кода и manifest-файлов должно быть отдельно разрешено изменением правил курса.

### Почему ORM-03 выделен отдельно

Справочник ORM содержит не только поля, но и технические метаданные модели, параметры хранения и объявления схемы. Они не должны бесконтрольно смешиваться с уроком о полях.

Поэтому:

```text
ORM-03 → метаданные модели / SQL-хранение / объявления схемы
ORM-04 → типы полей / параметры полей / хранение значений
ORM-05 → поля-связи
ORM-06 → вычисляемые и связанные поля / Python-ограничения
```

### Почему ARCH-03 не владеет реестром ORM

Цепочку Python-импортов можно понять до ORM. Но экземпляр модели, итоговый класс модели и набор моделей конкретной базы требуют уже определённых понятий `Model` и `recordset`. Поэтому эта тема находится в `ORM-02`.

### Почему ARCH-04 расположен рано

Публичные методы, документированное поведение транзакций RPC и `@api.onchange` зависят от границы клиент/сервер. Поэтому базовая модель вызова вводится заранее, а HTTP-контроллеры и frontend разбираются позже.

### Почему `@api.onchange` идёт после представлений

`@api.onchange` — механизм формы и клиентского взаимодействия с псевдозаписью. Его нельзя полноценно изучать до формы и границы запроса.

### Почему транзакции идут до продвинутой ORM

Raw SQL, `flush`, сброс кэша и часть поведения ORM требуют понимания транзакционного контекста, которым управляет framework.

## Принцип data-driven

Архитектурный фундамент сохраняет официальный принцип: Odoo в значительной степени управляется данными. Представления, действия, меню, элементы безопасности и другие части системы во многих случаях представлены записями базы данных. Их полное устройство принадлежит отдельным урокам.

## Не учим Odoo через меню

Курс не делает вывод:

```text
есть меню → существует независимая предметная система
```

Правильное направление анализа:

```text
граф модулей
    ↓
модели / записи / данные
    ↓
безопасность + действия + представления
    ↓
пользовательский интерфейс
```

## Не подгоняем Odoo под заранее выбранный процесс

До предметной части сначала устанавливается штатный смысл платформы и её моделей. Только после этого оценивается применимость к бизнес-процессам.

## Заморозка baseline

После финального аудита базовая архитектура курса зафиксирована в [baseline.md](baseline.md).

После заморозки структура курса меняется только если:

- новое официальное доказательство противоречит текущей модели;
- обнаружено фактическое внутреннее противоречие;
- аудит покрытия выявил фундаментальную зависимость, которую невозможно корректно встроить существующим механизмом владельцев;
- изменён согласованный scope или политика источников.

Литературная редактура, перевод терминов, добавление новых уроков и расширение уже предусмотренных аспектов **не являются основанием** для перестройки baseline.

## Правило остановки

Новый урок не добавляется, если предыдущий материал:

- использует предпосылку, отсутствующую в каноническом графе курса;
- имеет двух канонических владельцев одного понятия;
- содержит неподтверждённое утверждение о редакции;
- смешивает внутреннюю терминологию Odoo с ERP-классификацией;
- выдаёт особенность реализации за архитектурный фундамент;
- оставляет релевантный раздел официальной документации без допустимого статуса в карте покрытия;
- содержит утверждение `[ODOO]` без однозначной трассировки к источнику;
- без необходимости смешивает русский текст с английской объяснительной лексикой.
