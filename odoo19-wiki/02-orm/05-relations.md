# ORM-05. Связи между моделями

> ID урока: `ORM-05`  
> Версия: Odoo 19.0  
> Проверено: 2026-08-13  
> Предпосылки: `ORM-04`  
> Канонический владелец: `Many2one`; `One2many`; `Many2many`; `Command`; базовые переходы `domain` по связям  
> Владельцы аспектов: безопасность переходов и `bypass_search_access` / `any!` → `SEC-01`; `check_company` → `EXT-04`; наследование через `delegate` / `_inherits` → `EXT-01`; производительность выборок по связям → `RUN-01`  
> Предварительное упоминание: `related`  
> Отложено: вычисляемые и связанные поля; `_inherits`; полная семантика multi-company; правила записей (`record rules`); кэш и предзагрузка (`prefetch`); SQL-планирование запросов  
> Область редакции: семантика ORM-платформы; доступность конкретных приложений здесь не определяется  
> Источники: `S1`, `S2`, `S3`

## Цель

Понять, как Odoo связывает записи разных моделей и почему связь в ORM — это не просто «поле с чужим ID».

После `ORM-04` мы уже знаем, что поле (`Field`) задаёт тип и правила работы значения. Теперь добавляем связи:

```text
ПОЛЕ ORM
   │
   ├── несвязное поле               → ORM-04
   │
   └── связное поле                 → ORM-05
         ├── Many2one
         ├── One2many
         └── Many2many
```

Ключевая идея этого урока:

> при чтении связного поля Odoo возвращает набор записей (`recordset`), а не «сырой внешний ключ» как основной рабочий интерфейс.

---

## 1. Связи соединяют записи моделей

**[ODOO][S2]** Официальный учебник определяет связные поля как поля, которые связывают записи одной модели с записями той же или другой модели.

Например:

```text
Заказ
 ├── клиент                 → одна запись клиента
 ├── строки заказа          → несколько строк
 └── метки                  → несколько меток
```

В ORM эти случаи выражаются разными типами полей.

**[ВЫВОД]** Связь — часть модели данных, а не только средство сделать выпадающий список в форме.

---

## 2. Все связные поля при чтении возвращают `recordset`

**[ODOO][S1]** Обращение к `Many2one`, `One2many` или `Many2many` всегда возвращает `recordset`. Если связь пуста, возвращается пустой набор записей.

```python
record.partner_id
record.line_ids
record.tag_ids
```

Это связывает `ORM-05` с `ORM-01`:

```text
связное поле
     ↓
recordset связанной модели
     ↓
можно читать поля и вызывать методы связанной модели
```

Например:

```python
record.partner_id.name
```

**[ВЫВОД]** Основная рабочая абстракция связи в Python ORM — связанный `recordset`, а не отдельный объект «foreign key».

---

# Часть I. `Many2one`

## 3. `Many2one`: много записей могут ссылаться на одну

**[ODOO][S1]** Значение `Many2one` — `recordset` размером 0 или 1.

```text
0 записей → связь не задана
1 запись  → связь указывает на одну запись целевой модели
```

Пример:

```python
partner_id = fields.Many2one('res.partner')
```

Для одной записи текущей модели:

```python
record.partner_id
```

возвращает либо пустой `res.partner` recordset, либо набор из одной записи (`singleton`) `res.partner`.

---

## 4. `comodel_name`

**[ODOO][S1]** `comodel_name` задаёт техническое имя связанной модели.

```python
partner_id = fields.Many2one(
    comodel_name='res.partner',
)
```

Обычно параметр записывается позиционно:

```python
partner_id = fields.Many2one('res.partner')
```

`comodel_name` обязателен, кроме документированных случаев `related`-поля или расширения существующего поля.

Полная семантика `related` принадлежит `ORM-06`.

---

## 5. Запись значения `Many2one`

**[ODOO][S1]** Для `write()` ожидаемое значение `Many2one` — идентификатор записи базы данных.

```python
record.write({
    'partner_id': partner.id,
})
```

Чтобы очистить необязательную связь, используется ложное значение:

```python
record.write({
    'partner_id': False,
})
```

При чтении при этом мы снова получаем `recordset`, а не число:

```text
запись через vals → ID / False
чтение через атрибут → recordset размером 0 или 1
```

**[ВЫВОД]** Формат значения в `vals` и объект, возвращаемый при чтении поля через ORM, — не одно и то же представление.

---

## 6. `ondelete`

**[ODOO][S1]** `Many2one` поддерживает параметр `ondelete` со значениями:

```text
set null
restrict
cascade
```

Он определяет реакцию связи на удаление записи, на которую ссылается `Many2one`.

Концептуально:

```text
удаляется целевая запись
        │
        ├── set null → ссылка очищается
        ├── restrict → удаление ограничивается
        └── cascade  → зависимая запись удаляется каскадно
```

**[ВЫВОД]** `ondelete` — часть целостности связи, а не настройка отображения формы.

Выбор конкретного поведения должен соответствовать смыслу бизнес-модели.

---

## 7. `domain` и `context` на связном поле

**[ODOO][S1][S2]** Для связных полей можно задать `domain`, ограничивающий допустимые записи при выборе на стороне клиента, и `context`, используемый клиентом при работе с полем.

```python
instructor_id = fields.Many2one(
    'res.partner',
    domain=[('instructor', '=', True)],
)
```

Но:

```text
domain поля
≠
полная модель безопасности
```

**[ВЫВОД]** Ограничение вариантов в интерфейсе нельзя считать заменой ACL и правил записей (`record rules`).

Полная безопасность принадлежит `SEC-01`.

---

## 8. `bypass_search_access`: только граница безопасности

**[ODOO][S1]** Связные поля имеют параметр `bypass_search_access`, который определяет, обходятся ли права поиска на связанной модели при соответствующих операциях.

В этом уроке фиксируется только наличие такого параметра.

**[ВЫВОД]** Любой механизм с явным обходом проверок доступа относится к чувствительному с точки зрения безопасности поведению и не должен использоваться как обычная настройка удобства.

Полный разбор — `SEC-01`.

---

## 9. `check_company`: только предварительное упоминание

**[ODOO][S1]** `Many2one` и `Many2many` имеют параметр `check_company`, связанный с проверкой совместимости компаний.

Полная семантика:

- `company_id`;
- активные компании;
- `_check_company()`;
- `company_dependent`;
- согласованность записей разных компаний

принадлежит `EXT-04`.

**[ВЫВОД]** Наличие `check_company=True` нельзя понимать без общей модели multi-company.

---

## 10. `delegate`: связь с `_inherits`, но не сам урок наследования

**[ODOO][S1]** У `Many2one` есть параметр `delegate=True`, соответствующий механизму `_inherits`.

Это лишь точка соприкосновения.

```text
Many2one delegate=True
        ↓
аспект делегированного наследования
        ↓
полный владелец → EXT-01
```

`ORM-05` не объясняет `_inherits` и композиционное наследование.

---

# Часть II. `One2many`

## 11. `One2many` — обратная сторона конкретного `Many2one`

**[ODOO][S1]** `One2many` возвращает все записи `comodel_name`, у которых поле `inverse_name` равно текущей записи.

Пример:

```python
class Order(models.Model):
    _name = 'example.order'

    line_ids = fields.One2many(
        'example.order.line',
        'order_id',
    )


class OrderLine(models.Model):
    _name = 'example.order.line'

    order_id = fields.Many2one('example.order')
```

Связь читается так:

```text
example.order.line.order_id
        │
        └── хранит ссылку на заказ

example.order.line_ids
        │
        └── показывает все строки,
            у которых order_id = текущий заказ
```

---

## 12. Почему `One2many` называют виртуальной обратной связью

**[ODOO][S2]** Официальный учебник прямо называет `One2many` виртуальной связью, обратной `Many2one`, и предупреждает, что в целевой модели обязательно должен существовать соответствующий `Many2one`.

То есть:

```text
One2many
НЕ создаёт сам по себе независимую ссылку

он опирается на
Many2one inverse field
```

**[ВЫВОД]** Основная хранимая ссылка пары `Many2one` / `One2many` находится на стороне `Many2one`.

---

## 13. `comodel_name` и `inverse_name`

**[ODOO][S1]** Для обычного `One2many` задаются:

- `comodel_name` — целевая модель;
- `inverse_name` — имя обратного `Many2one` в целевой модели.

```python
line_ids = fields.One2many(
    'example.order.line',
    'order_id',
)
```

Здесь:

```text
comodel_name = example.order.line
inverse_name = order_id
```

Оба параметра обязательны, кроме документированных случаев `related`-поля или расширения поля.

---

## 14. Значение `One2many` — набор записей

**[ODOO][S1]** Значение `One2many` — `recordset` всех связанных записей.

```python
for line in order.line_ids:
    print(line.name)
```

Может быть:

```text
0 строк
1 строка
N строк
```

**[ВЫВОД]** `One2many` не является Python-списком ID как основной абстракцией чтения.

---

# Часть III. `Many2many`

## 15. `Many2many`: многие записи с обеих сторон

**[ODOO][S1][S2]** `Many2many` связывает набор записей текущей модели с набором записей другой модели.

Пример:

```python
tag_ids = fields.Many2many('example.tag')
```

```text
Запись A ──┬── Метка 1
           ├── Метка 2
           └── Метка 3

Запись B ──┬── Метка 1
           └── Метка 4
```

При чтении:

```python
record.tag_ids
```

возвращает `recordset` модели `example.tag`.

---

## 16. Таблица отношения `Many2many`

**[ODOO][S1]** `Many2many` может задавать:

```text
relation
column1
column2
```

- `relation` — имя таблицы, хранящей отношение;
- `column1` — колонка для записей текущей модели;
- `column2` — колонка для записей связанной модели.

Если параметры не указаны, Odoo может сформировать имена автоматически при выполнении документированных условий.

**[ВЫВОД]** `Many2many` отличается от `One2many`: здесь существует отдельная таблица отношения, а не обратное чтение одного `Many2one`.

---

## 17. Ограничение неявной таблицы `Many2many`

**[ODOO][S1]** ORM не допускает несколько `Many2many` на одной модели к одной и той же целевой модели с одинаковыми неявно сгенерированными параметрами отношения, потому что они попытались бы использовать одну и ту же таблицу отношения.

Документация указывает исключения, в частности когда параметры отношения заданы явно или когда хотя бы одна модель имеет `_auto=False`.

**[ВЫВОД]** Автоматическое именование таблицы отношения удобно, но не отменяет необходимость явно различать несколько разных смысловых связей между одними и теми же моделями.

---

# Часть IV. Именование связных полей

## 18. Официальное соглашение `_id` / `_ids`

**[ODOO][S3]** Coding Guidelines рекомендуют:

- `Many2one` заканчивать на `_id`;
- `One2many` и `Many2many` заканчивать на `_ids`.

Примеры:

```python
partner_id = fields.Many2one('res.partner')
line_ids = fields.One2many('example.line', 'order_id')
tag_ids = fields.Many2many('example.tag')
```

Это соглашение делает кардинальность связи видимой уже из имени.

---

## 19. `_id` в имени поля не означает, что Python-значение — число

Coding Guidelines одновременно различают:

```text
partner_id       → имя поля Many2one
partner_id       → имя переменной, если в ней действительно integer ID
partner          → разумное имя переменной, если в ней recordset
```

Например:

```python
partner = record.partner_id
partner_id = partner.id
```

**[ВЫВОД]** Суффикс `_id` у ORM-поля — соглашение имени поля, но чтение `record.partner_id` всё равно возвращает `recordset`.

---

# Часть V. Изменение `One2many` и `Many2many`

## 20. Для `One2many` и `Many2many` используется `Command`

**[ODOO][S1]** При записи `One2many` и `Many2many` ожидают список специальных команд `Command`.

В Python документация рекомендует использовать именованные функции:

```python
fields.Command.create(...)
fields.Command.update(...)
fields.Command.delete(...)
fields.Command.unlink(...)
fields.Command.link(...)
fields.Command.clear()
fields.Command.set(...)
```

Всего команд семь.

---

## 21. Внутренний формат команды

**[ODOO][S1]** Внутренне каждая команда представлена тройкой:

```text
(command, record_id_or_0, values_or_ids_or_0)
```

Числовые коды:

```text
0 CREATE
1 UPDATE
2 DELETE
3 UNLINK
4 LINK
5 CLEAR
6 SET
```

В Python предпочтительны именованные `fields.Command.*`, потому что они читаются однозначнее.

---

## 22. RPC и `Command`

**[ODOO][S1]** Через RPC нельзя использовать Python-функции `Command` или их именованные константы; требуется передавать буквальную тройку с числовым кодом команды.

Это важно разделять:

```text
Python-код ORM
→ fields.Command.create(...)

данные RPC
→ буквальное представление тройки из трёх элементов
```

Подробная внешняя API-интеграция не входит в этот урок.

---

## 23. `Command.create(values)`

**[ODOO][S1]** `Command.create(values)` создаёт новую запись связанной модели и связывает её с текущими записями.

При этом семантика различается:

```text
Many2many
→ создаётся одна новая связанная запись,
  которая связывается со всеми записями self

One2many
→ для каждой записи self создаётся своя новая запись,
  связанная именно с ней
```

**[ВЫВОД]** Одна и та же команда может иметь различающуюся кардинальную семантику для `One2many` и `Many2many`.

---

## 24. `Command.update(id, values)`

**[ODOO][S1]** Обновляет указанную связанную запись.

```python
fields.Command.update(line.id, {
    'name': 'Новое имя',
})
```

Связь при этом сохраняется; меняются значения самой связанной записи.

---

## 25. `Command.delete(id)`

**[ODOO][S1]** Удаляет связанную запись из базы и убирает связь.

Для `Many2many` удаление самой записи может быть запрещено, если она всё ещё связана с другими записями.

**[ВЫВОД]** `delete` — не просто «отвязать».

---

## 26. `Command.unlink(id)`

**[ODOO][S1]** Удаляет связь между текущей записью и связанной записью.

Для `One2many` дальнейшее поведение зависит от `ondelete` обратного `Many2one`:

- при `cascade` связанная запись удаляется;
- иначе обратный `Many2one` очищается, а запись сохраняется.

**[ВЫВОД]** `unlink` отношения и удаление самой записи — разные операции, хотя при `One2many` конкретный `ondelete` может привести к удалению записи.

---

## 27. `Command.link(id)`

**[ODOO][S1]** Добавляет существующую запись к отношению.

```python
fields.Command.link(tag.id)
```

Новая запись связанной модели при этом не создаётся.

---

## 28. `Command.clear()`

**[ODOO][S1]** Удаляет все связи текущего поля и семантически ведёт себя как `unlink` для каждой связанной записи.

```python
fields.Command.clear()
```

**[ВЫВОД]** `clear()` не следует автоматически читать как «DELETE всех связанных строк»; конкретный результат для `One2many` зависит в том числе от `ondelete` обратной связи.

---

## 29. `Command.set(ids)`

**[ODOO][S1]** Полностью заменяет текущий набор связей указанными ID.

Концептуально:

```text
текущий набор
   ↓
удалить связи, которых нет в новом наборе
   ↓
добавить новые связи
   ↓
получить ровно заданный набор ID
```

Пример:

```python
record.write({
    'tag_ids': [fields.Command.set([tag1.id, tag2.id])],
})
```

**[ВЫВОД]** `set()` — операция замены множества, а не добавления одного элемента.

---

## 30. Не путать `delete`, `unlink`, `clear`, `set`

Минимальная таблица:

| Команда | Что делает в первую очередь |
|---|---|
| `create` | создать связанную запись и связать |
| `update` | изменить связанную запись |
| `delete` | удалить связанную запись из базы |
| `unlink` | убрать конкретную связь |
| `link` | добавить существующую связь |
| `clear` | убрать все текущие связи |
| `set` | заменить набор связей заданным |

Точная семантика `One2many` дополнительно зависит от обратного `Many2one` и его `ondelete`.

# Часть VI. Переходы по связям в `domain`

## 31. Точечная нотация через `Many2one`

**[ODOO][S1]** Выражение поля (`field_expr`) в `Domain` может переходить по `Many2one` через точечную нотацию.

Например:

```python
Domain('partner_id.country_id.code', '=', 'NL')
```

или в обычной форме списка:

```python
[
    ('partner_id.country_id.code', '=', 'NL'),
]
```

**[ВЫВОД]** `domain` способен фильтровать текущую модель по значениям полей связанных записей, не превращаясь при этом в ручной SQL `JOIN`.

---

## 32. `any` и `not any`

**[ODOO][S1]** Операторы `any` и `not any` позволяют проверить, удовлетворяет ли хотя бы одна запись в связном поле (`Many2one`, `One2many`, `Many2many`) вложенному `domain`.

Концептуально:

```text
есть ли среди связанных записей
хотя бы одна,
которая удовлетворяет условию?
```

Примерная форма:

```python
Domain(
    'line_ids',
    'any',
    Domain('price_unit', '>', 1000),
)
```

**[ВЫВОД]** Для коллекционных связей не нужно сводить всю фильтрацию к ручному обходу записей в Python.

---

## 33. `any!`: вариант с обходом проверок доступа

**[ODOO][S1]** `any!` и `not any!` похожи на `any` / `not any`, но обходят проверки доступа при соответствующем переходе.

В этом уроке мы только фиксируем существование оператора.

**[ВЫВОД]** Символ `!` здесь означает не просто синтаксическую вариацию, а чувствительное с точки зрения безопасности поведение.

Полный разбор принадлежит `SEC-01`.

---

## 34. `child_of` и `parent_of`

**[ODOO][S1]** Операторы `child_of` и `parent_of` используют иерархическую семантику модели и поле, указанное через `_parent_name`.

`ORM-03` уже определил:

```text
_parent_name
_parent_store
parent_path
```

Теперь связь:

```text
иерархический Many2one
        │
        ▼
child_of / parent_of
        │
        ▼
поиск по дереву записей
```

**[ВЫВОД]** Иерархия в Odoo строится поверх семантики связи между записями, а не только как визуальное дерево в интерфейсе.

---

# Часть VII. Границы со следующими уроками

## 35. `related` — не часть текущего владельца

Связанное поле (`related`) проходит по цепочке других полей и будет разбираться в `ORM-06` вместе с вычисляемыми полями.

Важно не смешивать два термина:

```text
связное поле
→ Many2one / One2many / Many2many

related-поле
→ поле, значение которого берётся через цепочку других полей
```

**[ВЫВОД]** Связное поле и `related`-поле — не синонимы.

---

## 36. `check_company` не превращает этот урок в multi-company

`check_company` существует на связных полях, но полная модель компаний требует:

- `Environment.company` / `companies`;
- `company_id`;
- совместимость записей;
- общие записи и записи конкретной компании;
- `company_dependent`;
- правила записей (`record rules`) и контекст (`context`).

Владелец — `EXT-04`.

---

## 37. Связь не равна безопасности доступа

Даже если `domain` ограничивает варианты выбора:

```text
domain поля
        ≠
ACL
        ≠
правило записи
```

**[ВЫВОД]** Связь отвечает за структуру данных, а не за полную политику авторизации.

---

## 38. Связь не равна наследованию

`delegate=True` и `_inherits` используют связь как часть механизма композиционного наследования, но:

```text
Many2one
≠
автоматически наследование
```

Наследование моделей — `EXT-01`.

---

## 39. Связь не равна физической SQL-схеме целиком

У разных типов связи разная физическая реализация:

```text
Many2one
→ хранимая ссылка на стороне текущей модели

One2many
→ обратное представление существующего Many2one

Many2many
→ отдельная таблица отношения
```

Но полный разбор SQL-планов, индексов и производительности остаётся `RUN-01`.

---

## 40. Минимальная модель

```text
                      СВЯЗНЫЕ ПОЛЯ
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
    Many2one            One2many           Many2many
        │                  │                  │
   0 или 1 запись       0..N записей       0..N записей
        │                  │                  │
 хранимая ссылка      обратная сторона    таблица отношения
                        Many2one
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                    чтение → recordset
                           │
            запись One2many / Many2many
                           │
                     fields.Command
```

---

## Что нельзя заключать

- `Many2one` при чтении возвращает integer ID — нет;
- `One2many` хранит самостоятельный список ID в записи родителя — нет;
- `One2many` может существовать без соответствующего `Many2one` в обычном случае — нет;
- `Many2many` и `One2many` физически хранятся одинаково — нет;
- `domain` поля является механизмом авторизации — нет;
- `check_company` уже объясняет всю multi-company модель — нет;
- `delegate=True` уже объясняет `_inherits` — нет;
- `Command.delete()` и `Command.unlink()` — одно и то же — нет;
- `Command.clear()` всегда физически удаляет связанные записи — нет;
- `Command.set()` только добавляет новые связи — нет;
- `_id` в имени поля означает, что `record.partner_id` является числом — нет;
- связное поле и `related`-поле — одно и то же — нет;
- точечный `domain` по `Many2one` означает, что разработчик пишет SQL `JOIN` вручную — нет.
