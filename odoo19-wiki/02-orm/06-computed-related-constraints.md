# ORM-06. Вычисляемые и связанные поля, зависимости и Python-ограничения

> ID урока: `ORM-06`  
> Версия: Odoo 19.0  
> Проверено: 2026-08-13  
> Предпосылки: `ORM-05`  
> Канонический владелец: `compute`; `@api.depends`; `@api.depends_context`; `inverse`; `related`; `precompute`; `compute_sudo`; `recursive`; поиск по вычисляемому полю; `@api.constrains`  
> Владельцы аспектов: кэш, очередь перевычисления, `flush` и производительность → `RUN-01`; безопасность `compute_sudo` → `SEC-01`; транзакционные последствия ошибок ограничений → `ORM-07`; `onchange` → `UI-03`  
> Предварительное упоминание: перевычисление сохранённых вычисляемых полей  
> Отложено: внутренняя очередь перевычисления; кэш и предзагрузка (`prefetch`); `flush`; `savepoint`/`rollback`; полная семантика режима суперпользователя; `onchange`; оптимизация массовых вычислений  
> Область редакции: семантика ORM-платформы; доступность конкретных приложений здесь не определяется  
> Источники: `S1`, `S2`, `S3`

## Цель

Понять, как значение поля в Odoo может **выводиться из других данных**, как ORM узнаёт о зависимостях между полями, как сделать вычисляемое поле записываемым и как задаются проверки бизнес-инвариантов на Python.

После предыдущих уроков у нас уже есть:

```text
ORM-04 → обычные поля
ORM-05 → связи между моделями
```

Теперь добавляем производные значения:

```text
ПОЛЕ ORM
   │
   ├── обычное сохранённое значение
   │
   ├── вычисляемое поле (`compute`)
   │       ├── зависимости (`@api.depends`)
   │       ├── сохранение (`store`)
   │       ├── обратная запись (`inverse`)
   │       └── поиск (`search`)
   │
   └── связанное поле (`related`)
           └── частный случай вычисляемого поля
```

Отдельно от полей рассматриваем:

```text
@api.constrains
→ Python-проверка инварианта записи
```

# Часть I. Вычисляемые поля

## 1. `compute`: значение задаёт метод

**[ODOO][S1]** Поле можно сделать вычисляемым с помощью параметра `compute`. Он содержит имя метода, который должен присвоить значение этому полю.

```python
from odoo import api, fields, models

class Example(models.Model):
    _name = 'example.model'

    value = fields.Float()
    tax = fields.Float()
    total = fields.Float(compute='_compute_total')

    @api.depends('value', 'tax')
    def _compute_total(self):
        for record in self:
            record.total = record.value + record.value * record.tax
```

Ключевой контракт:

```text
метод `compute`
      │
      └── обязан присвоить значение
          вычисляемому полю для записей self
```

**[ВЫВОД]** Вычисляемое поле — не SQL generated column и не «формула интерфейса». Это поле ORM, значение которого задаётся методом модели.

---

## 2. Метод вычисления работает с `recordset`

Из `ORM-01` известно, что `self` в методе модели — набор записей (`recordset`).

Поэтому нормальная форма вычисления:

```python
def _compute_total(self):
    for record in self:
        record.total = ...
```

**[ВЫВОД]** Нельзя по умолчанию писать метод вычисления так, будто ORM всегда вызывает его для одной записи.

Пакетная производительность и механика предзагрузки (`prefetch`) принадлежат `RUN-01`.

---

## 3. `@api.depends`: декларация зависимостей

**[ODOO][S1]** Декоратор `@api.depends(...)` задаёт поля, от которых зависит метод вычисления.

```python
@api.depends('value', 'tax')
def _compute_total(self):
    ...
```

Смысл:

```text
value / tax изменились
        │
        ▼
ORM знает, что total зависит от них
        │
        ▼
вычисляемое значение должно быть актуализировано
```

Внутреннюю очередь перевычисления здесь не моделируем.

**[ВЫВОД]** Зависимости — часть декларативного контракта поля с ORM, а не комментарий к методу.

---

## 4. Зависимости могут проходить по связям

**[ODOO][S1]** `@api.depends` принимает пути полей через точку.

```python
@api.depends('partner_id.name', 'partner_id.is_company')
def _compute_partner_name(self):
    ...
```

Также возможна зависимость через коллекционную связь:

```python
@api.depends('line_ids.value')
def _compute_total(self):
    for record in self:
        record.total = sum(line.value for line in record.line_ids)
```

Связи уже определены в `ORM-05`.

**[ВЫВОД]** Граф зависимостей вычисляемого поля может пересекать границу текущей модели через связные поля.

---

## 5. `@api.depends` описывает входы, но не заменяет само вычисление

Неверная модель:

```text
@api.depends
= формула вычисления
```

Правильно:

```text
@api.depends
= декларация зависимостей

метод `compute`
= алгоритм получения значения
```

**[ВЫВОД]** ORM должна знать не только как посчитать значение, но и какие изменения делают его потенциально неактуальным.

---

## 6. Зависимости можно задавать функцией

**[ODOO][S1]** Вместо списка строк `@api.depends` допускает одну функцию; ORM вызывает её с моделью поля и получает набор зависимостей.

Это продвинутый вариант объявления зависимостей.

**[ВЫВОД]** Базовый и наиболее читаемый случай — явные имена полей; функциональная форма нужна только когда список зависимостей действительно должен формироваться программно.

---

## 7. По умолчанию вычисляемые поля не сохраняются

**[ODOO][S1]** Для вычисляемых полей `store=False` является значением по умолчанию. Такое поле вычисляется при необходимости и не ведёт себя как обычная сохранённая колонка модели.

```python
total = fields.Float(compute='_compute_total')
```

Концептуально:

```text
store=False
→ значение получает ORM через `compute`
→ отдельное сохранённое значение поля в БД
  не является базовым источником истины
```

---

## 8. `store=True`: вычисляемое значение можно сохранять

**[ODOO][S1]** При `store=True` вычисляемое поле сохраняется в базе данных. Документация также указывает, что такое поле автоматически становится доступным для обычного поиска и группировки.

```python
total = fields.Float(
    compute='_compute_total',
    store=True,
)
```

```text
compute + store=True
        │
        ├── значение вычисляет ORM
        └── результат сохраняется в БД
```

**[ВЫВОД]** `store=True` не превращает вычисляемое поле в ручное обычное поле: его значение по-прежнему принадлежит вычислительному контракту.

---

## 9. Сохранённое вычисляемое поле требует корректных зависимостей

**[ODOO][S2]** Официальный Server Framework 101 предупреждает: у сохранённых вычисляемых полей зависимости важны, а цепочки вычисляемых зависимостей могут приводить к большому числу перевычислений и проблемам производительности.

В этом уроке фиксируем только архитектурную часть:

```text
store=True
+
неполные или неверные зависимости
=
риск неактуального производного значения
```

Количество запросов, пакетное перевычисление, кэш, предзагрузка и профилирование принадлежат `RUN-01`.

---

## 10. Несохранённое вычисляемое поле не ищется как обычная колонка

**[ODOO][S1]** Для вычисляемого поля можно задать параметр `search` — имя метода, который преобразует условие поиска по этому полю в эквивалентный `domain`.

```python
upper_name = fields.Char(
    compute='_compute_upper',
    search='_search_upper',
)
```

```python
def _search_upper(self, operator, value):
    if operator == 'like':
        operator = 'ilike'
    return [('name', operator, value)]
```

Концептуально:

```text
domain по вычисляемому полю
        │
        ▼
метод `search` поля
        │
        ▼
эквивалентный domain по данным,
которые ORM умеет искать
```

**[ВЫВОД]** Метод `search` не должен вычислять значения всех записей и затем фильтровать их в Python; его контракт — вернуть эквивалентный домен поиска.

---

## 11. `search` и `compute` — разные стороны поля

```text
compute
→ как получить значение поля

search
→ как преобразовать условие поиска по полю
```

**[ВЫВОД]** Наличие `compute` не означает автоматической возможности искать по несохранённому полю как по обычной колонке.

# Часть II. Обратная запись через `inverse`

## 12. Вычисляемые поля по умолчанию только для чтения

**[ODOO][S1]** Вычисляемые поля по умолчанию `readonly`. Чтобы разрешить запись значения, задаётся параметр `inverse`.

```python
document = fields.Char(
    compute='_compute_document',
    inverse='_inverse_document',
)
```

---

## 13. `inverse` — обратное преобразование, а не второй `compute`

Если `compute` отвечает на вопрос:

> какое значение поля получается из исходных данных?

то `inverse` отвечает:

> что нужно изменить в исходных данных, если в вычисляемое поле записали новое значение?

Концептуально:

```text
исходные поля
    │
    ├── compute ─────► вычисляемое поле
    │
    └── inverse ◄──── запись нового значения поля
```

Простой учебный пример:

```python
amount = fields.Float()
rate = fields.Float(default=2.0)
converted = fields.Float(
    compute='_compute_converted',
    inverse='_inverse_converted',
)

@api.depends('amount', 'rate')
def _compute_converted(self):
    for record in self:
        record.converted = record.amount * record.rate

def _inverse_converted(self):
    for record in self:
        if record.rate:
            record.amount = record.converted / record.rate
```

**[ВЫВОД]** `inverse` делает вычисляемое представление записываемым за счёт изменения его источников.

---

## 14. `inverse` не означает «сохранить введённое значение как есть»

Вычисляемое поле остаётся производным.

Нормальная модель:

```text
запись нового значения вычисляемого поля
        │
        ▼
inverse
        │
        ▼
изменяются исходные данные
        │
        ▼
compute снова определяет производное значение
```

**[ВЫВОД]** Если значение должно жить независимо и не выводиться из других данных, возможно, это вообще не вычисляемое поле.

---

## 15. Один `compute` может обслуживать несколько полей

**[ODOO][S1]** Несколько полей могут использовать один и тот же метод вычисления, если он присваивает значения всем этим полям.

```python
discount_value = fields.Float(compute='_compute_discount')
total = fields.Float(compute='_compute_discount')

@api.depends('value', 'discount')
def _compute_discount(self):
    for record in self:
        discount = record.value * record.discount
        record.discount_value = discount
        record.total = record.value - discount
```

Это полезно, когда значения естественно вычисляются вместе.

---

## 16. Один общий `inverse` для нескольких полей — опасная конструкция

**[ODOO][S1]** ORM Reference прямо предупреждает, что использовать один метод `inverse` для нескольких полей не рекомендуется.

Во время выполнения `inverse` поля, использующие этот метод, защищены от вычисления. Если одно из них в этот момент отсутствует в кэше, ORM может вернуть для него `False`, а метод получит неверное представление соседних значений.

Детали кэша принадлежат `RUN-01`, но правило этого урока простое:

> общий метод `compute` допустим; общий метод `inverse` для нескольких вычисляемых полей документация не рекомендует.

# Часть III. `precompute`, `compute_sudo`, `recursive`

## 17. `precompute`: вычислить до вставки записи

**[ODOO][S1]** Параметр `precompute=True` позволяет вычислить поле до вставки записи в базу данных, если вычисление может быть выполнено на этом этапе.

```python
value = fields.Float(
    compute='_compute_value',
    precompute=True,
)
```

Но это **не универсальная оптимизация**.

---

## 18. Явное значение или `default` отключают предварительное вычисление

**[ODOO][S1]** Предварительное вычисление происходит только если в `create()` не передано явное значение поля и у поля нет значения `default`. Даже наличие `default` отключает `precompute` для такого создания.

**[ВЫВОД]** `precompute=True` — условный режим жизненного цикла вычисления, а не гарантия «всегда считать до INSERT».

---

## 19. `precompute` может ухудшить производительность

**[ODOO][S1]** ORM Reference предупреждает: если записи создаются по одной, предварительное вычисление может быть менее эффективно, чем пакетное вычисление позднее. Документация отмечает, что `precompute` может быть полезен, например, для строк `One2many`, которые ORM часто создаёт пакетно.

В этом уроке вывод только такой:

> включать `precompute=True` только потому, что слово звучит как «быстрее», нельзя.

Практическая оценка производительности принадлежит `RUN-01`.

---

## 20. `compute_sudo`: вычисление в режиме суперпользователя

**[ODOO][S1]** Параметр `compute_sudo` определяет, должно ли поле перевычисляться в режиме суперпользователя с обходом прав доступа. По документации значение по умолчанию различается: `True` для сохранённых вычисляемых полей и `False` для несохранённых.

Это важная техническая семантика, но полная модель безопасности принадлежит `SEC-01`.

**[ВЫВОД]** Значение вычисляемого поля может зависеть не только от формулы и зависимостей, но и от режима прав, в котором выполняется вычисление.

---

## 21. `compute_sudo` нельзя воспринимать как безобидный флаг

```text
compute_sudo=True
→ вычисление может видеть данные,
  которые обычный пользователь сам читать не может
```

Точные последствия для ACL, правил записей (`record rules`) и multi-company будут разбираться в `SEC-01` и `EXT-04`.

В `ORM-06` достаточно помнить: это **аспект безопасности вычисления**.

---

## 22. `recursive=True`: рекурсивные зависимости нужно объявлять явно

**[ODOO][S1]** Если поле имеет рекурсивную зависимость вида `parent_id.X`, параметр `recursive=True` должен быть указан явно, чтобы ORM могла корректно обрабатывать перевычисление.

```text
X зависит от parent_id.X
        │
        ▼
recursive=True
```

**[ВЫВОД]** Рекурсивный граф производных значений является отдельным случаем; нельзя рассчитывать, что ORM всегда сама выведет такую рекурсивность из тела Python-метода.

# Часть IV. Зависимости от контекста

## 23. Не все вычисления зависят только от полей записи

Иногда значение зависит от контекста `Environment`.

Например:

```text
цена
может зависеть от
pricelist в env.context
```

Для таких несохранённых вычислений Odoo предоставляет `@api.depends_context`.

---

## 24. `@api.depends_context`

**[ODOO][S1]** `@api.depends_context(*args)` задаёт ключи контекста, от которых зависит **несохранённый** метод вычисления.

```python
price = fields.Float(compute='_compute_price')

@api.depends_context('pricelist')
def _compute_price(self):
    for product in self:
        ...
```

Все значения зависимостей контекста должны быть хешируемыми (`hashable`).

**[ВЫВОД]** `@api.depends` и `@api.depends_context` описывают разные источники зависимости:

```text
@api.depends
→ значения полей

@api.depends_context
→ ключи context
```

---

## 25. Контекстная зависимость и сохранённое поле — разные модели

`@api.depends_context` документирован для несохранённых вычисляемых полей.

```text
одна и та же запись
+
разный context
→ может иметь разное эффективное значение
```

**[ВЫВОД]** Значение, зависящее от текущего контекста выполнения, нельзя бездумно превращать в одну глобально сохранённую величину записи.

# Часть V. Связанные поля (`related`)

## 26. `related` — частный случай вычисляемого поля

**[ODOO][S1]** Связанное поле (`related`) — специальный прокси-вариант вычисляемого поля, который получает значение другого поля через цепочку связей.

```python
nickname = fields.Char(
    related='user_id.partner_id.name',
)
```

Цепочка читается так:

```text
текущая запись
    │
    └── user_id
          │
          └── partner_id
                 │
                 └── name
```

Значение `nickname` получается из конечного `name`.

---

## 27. `related` не является разновидностью связного поля

Различие из `ORM-05`:

```text
связное поле
→ Many2one / One2many / Many2many
→ создаёт отношение между записями

поле `related`
→ производное поле
→ читает значение по уже существующей цепочке полей
```

**[ВЫВОД]** Связное поле и связанное (`related`) поле — разные механизмы ORM.

---

## 28. Атрибуты `related`-поля частично наследуются от источника

**[ODOO][S1]** Если они не переопределены, от исходного поля могут автоматически копироваться такие атрибуты, как `string`, `help`, `groups`, `digits`, `size`, `translate`, `sanitize`, `selection`, `comodel_name`, `domain`, `context`; `required` копируется только при выполнении документированных условий по всей цепочке.

**[ВЫВОД]** `related` — не просто Python-сокращение для `compute`: ORM знает источник поля и может переносить часть его метаданных.

---

## 29. Значения `related` по умолчанию не сохраняются

**[ODOO][S1]** По умолчанию связанные поля:

- не сохраняются;
- не копируются при дублировании;
- только для чтения;
- вычисляются в режиме суперпользователя.

При необходимости можно указать:

```python
nickname = fields.Char(
    related='user_id.partner_id.name',
    store=True,
)
```

и сохранить производное значение.

---

## 30. Сохранённое `related` автоматически перевычисляется по зависимостям

**[ODOO][S1]** Сохранённое `related`-поле автоматически перевычисляется при изменении его зависимостей.

При необходимости можно сузить зависимости:

```python
nickname = fields.Char(
    related='partner_id.name',
    store=True,
    depends=['partner_id'],
)
```

В таком случае изменение `partner_id` считается причиной перевычисления, а изменение `partner.name` само по себе не входит в эту явно суженную зависимость.

**[ВЫВОД]** `depends` у сохранённого `related` позволяет управлять тем, какие изменения считаются причиной перевычисления.

---

## 31. `Many2many` и `One2many` нельзя произвольно цеплять внутри `related`

**[ODOO][S1]** ORM Reference предупреждает: нельзя строить цепочки `related`, проходящие через `Many2many` или `One2many` как через промежуточные звенья, ожидая автоматической агрегации результата.

Например, не поддерживается модель вида:

```text
m2m_ids.m2m_ids
```

или:

```text
o2m_ids.o2m_ids
```

Если нужна такая агрегация, документация рекомендует собственное вычисляемое поле.

---

## 32. `Many2one` может быть промежуточным звеном к коллекционной связи

**[ODOO][S1]** Допустима цепочка через `Many2one`, после которой конечным полем является `One2many` или `Many2many`.

Концептуально:

```text
current.m2o_id.m2m_ids
```

может быть допустимым `related`.

Но:

```text
current.m2m_ids.m2m_ids
```

не является поддерживаемой автоматической агрегацией.

**[ВЫВОД]** Ограничение относится не к самому факту, что конечное поле коллекционное, а к попытке пройти через коллекционную связь как через промежуточный одиночный путь.

# Часть VI. Python-ограничения (`@api.constrains`)

## 33. Ограничение — проверяемый инвариант

Инвариант — условие, которое должно оставаться истинным для допустимой записи.

Например:

```text
дата окончания >= дата начала
```

или:

```text
процент находится в допустимом диапазоне
```

Для проверок, требующих Python-логики, Odoo предоставляет `@api.constrains`.

---

## 34. `@api.constrains` вызывается на наборе изменённых записей

**[ODOO][S1][S3]** Python-ограничение — метод, декорированный `@api.constrains(...)`. Он вызывается на наборе записей, где изменилось одно из указанных полей, и должен поднять `ValidationError`, если инвариант нарушен.

```python
from odoo import api, fields, models
from odoo.exceptions import ValidationError

class Example(models.Model):
    _name = 'example.model'

    date_start = fields.Date()
    date_end = fields.Date()

    @api.constrains('date_start', 'date_end')
    def _check_dates(self):
        for record in self:
            if (
                record.date_start
                and record.date_end
                and record.date_end < record.date_start
            ):
                raise ValidationError(
                    'Дата окончания не может быть раньше даты начала.'
                )
```

---

## 35. `@api.constrains` и `models.Constraint` — разные механизмы

Из `ORM-03`:

```text
models.Constraint(...)
→ ограничение на уровне SQL/схемы

@api.constrains(...)
→ Python-метод ORM
```

**[ODOO][S3]** Официальный tutorial прямо разделяет SQL-ограничения и Python-ограничения как два способа автоматически проверять инварианты.

**[ВЫВОД]** Выбор между ними зависит не от слова constraint, а от того, где и каким механизмом может быть выражен инвариант.

---

## 36. `@api.constrains` указывает поля-триггеры проверки

```python
@api.constrains('name', 'description')
def _check_description(self):
    ...
```

**[ODOO][S1]** Метод вызывается для записей, где изменилось одно из перечисленных полей.

**[ВЫВОД]** Список в `@api.constrains` — контракт автоматического запуска проверки, а не просто перечень всех полей, которые метод читает.

---

## 37. В `@api.constrains` поддерживаются только простые имена полей

**[ODOO][S1]** Декоратор не поддерживает пути через точку вида:

```text
partner_id.customer
```

Такие имена полей отношений в аргументах `@api.constrains` игнорируются.

**[ВЫВОД]** Нельзя переносить синтаксис путей из `@api.depends` в `@api.constrains` и ожидать одинакового поведения.

---

## 38. `@api.constrains` автоматически запускается только при наличии поля в `create()`/`write()`

**[ODOO][S1]** ORM Reference предупреждает: `@api.constrains` запускается только если объявленные поля входят в вызов `create()` или `write()`.

Следствие документации: если нужно гарантированно проверять, например, **отсутствие** значения, а поле вообще не было передано при создании, может потребоваться переопределение `create()`.

**[ВЫВОД]** `@api.constrains('field')` нельзя автоматически читать как «этот метод гарантированно сработает при абсолютно любом создании записи».

---

## 39. Имена полей ограничения тоже можно задавать функцией

**[ODOO][S1]** Вместо явных аргументов `@api.constrains` допускает одну функцию; ORM вызывает её с экземпляром модели и получает имена полей.

Как и с `@api.depends`, это продвинутый вариант. Для обычных проверок явный список имён проще читать и проверять.

---

## 40. При нарушении ограничения поднимается `ValidationError`

**[ODOO][S1][S3]** При нарушении инварианта Python-ограничение должно поднять `ValidationError`.

```python
if invalid:
    raise ValidationError('Понятное сообщение пользователю')
```

Транзакционное поведение исключения и отката будет разбираться в `ORM-07`.

---

## 41. Ограничение не должно молча «чинить» запись

Контракт `@api.constrains` — **проверить** инвариант и отклонить недопустимое состояние.

**[ВЫВОД]** Если метод вместо ошибки тихо переписывает пользовательские данные, это уже другая бизнес-логика и её не следует маскировать под проверку инварианта.

---

# Часть VII. Границы с другими механизмами

## 42. Вычисляемое поле ≠ `onchange`

`onchange` имеет отдельного владельца `UI-03`.

**[ODOO][S2]** Server Framework 101 подчёркивает: вычисляемые поля работают и вне формы, тогда как `onchange` автоматически запускается только в контексте формы. Официальный tutorial рекомендует не помещать бизнес-логику, которая должна соблюдаться всегда, исключительно в `onchange`.

В этом уроке достаточно границы:

```text
compute
→ часть модели / ORM

onchange
→ реакция формы
```

Полный `onchange` будет позже.

---

## 43. Вычисляемое поле ≠ Python-ограничение

```text
compute
→ получить производное значение

@api.constrains
→ проверить допустимость состояния
```

**[ВЫВОД]** Не нужно использовать вычисляемое поле как скрытый механизм валидации, если задача — запретить недопустимое состояние.

---

## 44. `inverse` ≠ `onchange`

```text
inverse
→ обратная запись вычисляемого поля в его источники

onchange
→ реакция интерфейса формы на изменение поля
```

`inverse` относится к полю ORM и не требует формы как канонической среды выполнения.

---

## 45. `related` ≠ ручное дублирование данных

Если нужно просто проксировать значение по существующей цепочке связей, `related` выражает эту зависимость декларативно.

**[ВЫВОД]** Ручное копирование одного и того же значения между моделями через произвольные `write()` без явной причины создаёт два потенциально расходящихся источника истины.

Это не означает, что любое денормализованное поле должно быть `related`: конкретная бизнес-модель может требовать исторически фиксируемую копию значения.

---

## 46. Вычисляемое поле ≠ исторический снимок

Пример:

```text
текущая цена партнёра
```

и:

```text
цена, зафиксированная в документе в момент операции
```

— разные бизнес-смыслы.

**[ERP-КЛАССИФИКАЦИЯ]** Производное поле, которое всегда следует за текущим источником, не заменяет исторически зафиксированный транзакционный факт.

Эта граница станет особенно важной в предметных ERP-моделях.

# Часть VIII. Минимальная модель

```text
                         ПОЛЕ
                           │
               ┌───────────┴───────────┐
               │                       │
          обычное значение       производное значение
                                       │
                         ┌─────────────┴─────────────┐
                         │                           │
                    compute                      related
                         │                           │
                @api.depends                 цепочка полей
             @api.depends_context                  │
                         │                     store=True?
                  store=True?                      │
                         │                         │
                    search?                        │
                         │                         │
                   inverse?                        │
                         └─────────────┬───────────┘
                                       │
                              актуализация ORM

ОТДЕЛЬНО:

@api.constrains
→ проверка инварианта
→ ValidationError при нарушении
```

## Что нельзя заключать

- вычисляемое поле = SQL generated column — нет;
- `@api.depends` = тело формулы — нет;
- `store=True` превращает вычисляемое поле в ручное обычное поле — нет;
- несохранённое вычисляемое поле автоматически ищется как колонка — нет;
- `search` вычисляемого поля должен перебрать все записи в Python — нет;
- `inverse` = второй `compute` — нет;
- один общий `inverse` для многих полей является рекомендуемым шаблоном — нет;
- `precompute=True` всегда ускоряет работу — нет;
- `compute_sudo=True` не имеет последствий для безопасности — нет;
- `related` = `Many2one`/`One2many`/`Many2many` — нет;
- через `Many2many`/`One2many` можно произвольно строить цепочки `related` с автоматической агрегацией — нет;
- `@api.constrains` поддерживает пути через точку как `@api.depends` — нет;
- `@api.constrains` гарантированно вызывается при любом `create()`, даже если поле отсутствовало в значениях — нет;
- `models.Constraint` и `@api.constrains` — один механизм — нет;
- `onchange` и `compute` взаимозаменяемы как универсальная бизнес-логика — нет.
